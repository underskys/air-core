# AIR v0.18 RFC: Compact Storage Types and Packed Tables

Status: accepted first slice for v0.19 packed static tables; broader storage
work remains RFC/P1

Target milestone: v0.19 first slice for packed static tables; future
implementation for load/store, buffers, slices, and range analysis

## Purpose

AIR needs a performance and memory path for dense package data without bloating
Core with a C-like integer type system. This RFC defines compact storage and
layout types for future tables, buffers, slices, records, bounded facts, and
command streams.

Main decision: do not add `i8`, `u8`, `i16`, or `u16` as full SSA value types
yet. Keep AIR computation simple and explicit, and use compact storage types at
layout boundaries.

## Rationale

WebAssembly value types are `i32`, `i64`, `f32`, and `f64`. Eight-bit and
sixteen-bit integers exist as memory load/store forms, not as normal local value
types. AIR should follow that shape: `i32` remains the computation carrier, and
compact storage types define how data is stored, loaded, reported, and audited.

This keeps arithmetic and verifier rules small while still enabling packed
static data, compact fact snapshots, and lower memory pressure.

## Value Types vs Storage Types

AIR value types remain:

- `i32`;
- `i64`;
- `f32`;
- `f64`;
- `bool`.

Storage/layout types are future layout annotations:

- `u8`;
- `i8`;
- `u16`;
- `i16`;
- `u32`;
- `i32`;
- `f32`.

Rule: `u8`, `i8`, `u16`, and `i16` are storage types. Loading them materializes
an `i32` SSA value. AIR code computes on the loaded `i32`, not on a distinct
`u8` or `u16` SSA value.

## Proposed Operations (Future Only)

v0.19 implements only the static table subset:

- `table name:u8 = [...]`
- `table name:u16 = [...]`
- `table name:i16 = [...]`
- `table.get.u8 @name, idx -> i32`
- `table.get.u16 @name, idx -> i32`
- `table.get.i16 @name, idx -> i32`

Those operations are fixed-length, readonly, scalar-only, and package/report
visible. They do not add full `u8`/`u16`/`i16` SSA values.

The following operation families remain future candidates only:

### Raw Memory

- `load.u8 ptr, off -> i32`
- `load.i8 ptr, off -> i32`
- `load.u16 ptr, off -> i32`
- `load.i16 ptr, off -> i32`
- `store.u8 ptr, off, value`
- `store.i8 ptr, off, value`
- `store.u16 ptr, off, value`
- `store.i16 ptr, off, value`

### Slices

- `slice.load.u8`
- `slice.load.i8`
- `slice.load.u16`
- `slice.load.i16`
- `slice.store.u8`
- `slice.store.i8`
- `slice.store.u16`
- `slice.store.i16`

### Typed Buffers

- `buffer<u8,N>`
- `buffer<i8,N>`
- `buffer<u16,N>`
- `buffer<i16,N>`
- `buffer<i32,N>`
- `buffer<f32,N>`

### Static Tables

- `table name:u8 = [...]`
- `table name:u16 = [...]`
- `table name:i16 = [...]`
- `table.get.u8 @name, idx -> i32`
- `table.get.u16 @name, idx -> i32`
- `table.get.i16 @name, idx -> i32`

## Range Validation

The v0.19 packed static table first slice validates literal table initializers:

- `u8` values must be in `0..255`;
- `u16` values must be in `0..65535`;
- `i16` values must be in `-32768..32767`.

Broader future verifier work should track integer ranges where practical.

Range sources:

- constants;
- `table.get.u8`, `table.get.u16`, and `table.get.i16`;
- `load.u8`, `load.u16`, and `load.i16`;
- `i32.and` masks;
- `clamp_i32`;
- `select` of known ranges.

Rules:

- `store.u8` requires value range `0..255` when statically known;
- `store.i8` requires value range `-128..127`;
- `store.u16` requires value range `0..65535`;
- `store.i16` requires value range `-32768..32767`;
- if dynamic range is unknown, a future implementation may warn or require a
  runtime trap;
- canonical examples must not rely on silent truncation.

No silent truncation is allowed. If an implementation cannot prove a value fits,
it must preserve that uncertainty as a diagnostic, runtime guard, or explicit
policy decision.

## Lowering

The v0.19 packed table first slice lowers compact static tables to deterministic
data segments where supported:

- `table.get.u8` -> Wasm `i32.load8_u`;
- `table.get.u16` -> Wasm `i32.load16_u`;
- `table.get.i16` -> Wasm `i32.load16_s`.

Future raw-memory and slice lowering should map compact operations to
WebAssembly load/store width forms:

- `load.u8` -> Wasm `i32.load8_u`;
- `load.i8` -> Wasm `i32.load8_s`;
- `load.u16` -> Wasm `i32.load16_u`;
- `load.i16` -> Wasm `i32.load16_s`;
- `store.u8` and `store.i8` -> Wasm `i32.store8`;
- `store.u16` and `store.i16` -> Wasm `i32.store16`;
- `table<u8/u16/i16>` -> compact data segments plus `load8`/`load16`.

Loaded values become `i32` SSA values. Store operations consume `i32` values
after verifier range checks or runtime guards.

## Audit and Report Visibility

Reports should show:

- static table element type;
- table length;
- table byte size;
- packed storage savings compared to `i32`;
- memory load/store byte width;
- unknown-range store warnings;
- candidate hints where repeated `i32` literals fit `u8` or `u16`.

This visibility matters because compact storage is a layout decision. It should
be reviewable, deterministic, and explainable to AI repair loops.

## Anti-Slop Integration

Future reviewPolicy integration should connect compact storage to existing
anti-slop signals:

- repeated small literals should suggest static packed tables;
- slot-family globals should suggest fixed pools or tablegroups;
- material, tile, flags, and color fields should suggest packed storage where
  safe;
- large frame functions remain governed by existing reviewPolicy gates.

These hints should remain advisory until compact storage operations and range
analysis are implemented.

## Relation to Bounded Facts

Bounded facts may use compact storage types in a future slice. For example,
task status IDs, flags, and bounded enum IDs may be stored as `u8` or `u16`
while still materializing as `i32` when AIR reads them.

The current v0.18 facts schema validator remains an `i32`/`bool` first slice.
Compact storage is a future storage/layout optimization. It is not a runtime
object model, dynamic map system, or arbitrary JSON representation.

## Non-Goals

- No full `u8`/`u16` scalar arithmetic.
- No C-like integer promotion zoo.
- No silent truncation.
- No dynamic maps.
- No GC.
- No host objects.
- No demo-specific field layout.
- No raw memory load/store `u8`/`u16` implementation in the v0.19 packed table
  first slice.
- No generic `table<T>` type system beyond the accepted `table name:u8`,
  `table name:u16`, and `table name:i16` static table forms.
- No buffers implementation in this RFC patch.
- No tablegroups implementation in this RFC patch.
- No range analysis implementation in this RFC patch.

## Use Cases

- Tile IDs as a `u8` table.
- Material IDs as a `u16` table.
- Flags as a `u8` buffer.
- Sprite command packed fields.
- Task status IDs as `u8` or `u16` storage.
- Bullet/enemy fixed pool candidate layouts.

These examples are pressure evidence for generic storage/layout mechanisms, not
demo-specific Core APIs.

## Acceptance Path

### Phase 1: RFC and Packed Static Table First Slice

- Keep AIR scalar value types unchanged.
- Implement only readonly packed static tables for `u8`, `u16`, and `i16`.
- Materialize compact table reads as `i32` through `table.get.u8`,
  `table.get.u16`, and `table.get.i16`.
- Keep AIR ABI at `0.10`.
- Keep Host ABI at `0.10`.
- Keep raw memory `load/store`, buffers, slices, tablegroups, range analysis,
  and compact storage migration work deferred.

### Phase 2: Storage Operations

- Implement `load/store` `u8`, `i8`, `u16`, and `i16`.
- Extend compact table syntax only if a generic table type form is separately
  accepted.
- Add verifier range tests.
- Add lowering tests for Wasm load/store width forms.
- Add report tests for byte size and savings.

### Phase 3: Migration and Measurement

- Migrate downstream demo/static data to packed tables where appropriate.
- Measure WAT size.
- Measure Wasm size.
- Measure static table bytes.
- Measure draw command count where relevant.
- Measure host calls per frame where relevant.
- Measure reviewPolicy diagnostics before and after migration.

## ABI Policy

AIR ABI remains `0.10` while compact storage is RFC-only or source-level sugar
over existing scalar table/runtime representation.

AIR ABI `0.11` is considered only if compact storage changes executable runtime
representation, calling convention, memory/data layout, package entrypoint
semantics, or runtime-required package metadata.

Host ABI remains `0.10` because compact storage types do not add host imports or
host authority.

## Open Questions

- Should compact static tables be accepted before raw memory `load/store`
  operations?
- Should unknown dynamic ranges warn, fail, or require explicit runtime traps?
- Should `u32` be a storage type only, or remain equivalent to `i32` storage in
  reports?
- Which reviewPolicy diagnostic code should represent packed-storage
  opportunities?
- Should bounded facts schemas add storage type annotations before AIR source
  syntax does?
