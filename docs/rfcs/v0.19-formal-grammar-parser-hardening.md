# AIR v0.19 RFC: Formal Grammar and Parser Hardening

Status: draft RFC / planning only

Target milestone: v0.19 planning, future implementation

## Purpose

AIR is a verifier-first IR. As the surface grows, parser, verifier, formatter,
report, and lowerer drift becomes a release risk. v0.19 should define a formal
grammar and parser hardening path before adding broader syntax.

The immediate pressure comes from recent surface growth such as package graphs,
bounded facts metadata, Output Contract manifests, and compact static tables.
The goal is to make AIR syntax admission reviewable and testable without
rewriting the parser in this RFC.

## Current Problem

AIR currently uses a hand-written parser. That is acceptable for a compact IR,
but every new syntax feature increases the risk that docs, parser behavior,
formatter output, verifier expectations, report metadata, and lowering behavior
diverge.

Specific risks:

- hand-written parser rules may accept syntax that docs do not describe;
- docs may describe syntax that the parser does not accept;
- verifier and lowerer may assume AST shapes that parser changes silently
  break;
- formatter may lose syntax detail or fail to roundtrip new constructs;
- negative parse behavior may drift without a dedicated malformed corpus;
- new syntax like compact tables increases the need for explicit feature
  admission gates.

## Grammar

The grammar target is an EBNF-style specification for the accepted AIR source
language. It should be checked into docs or spec before broad syntax expansion.

The grammar should define canonical tokens:

- whitespace and comments;
- identifiers;
- module names;
- package-local import paths;
- host import names;
- value names;
- function references;
- numeric literals;
- boolean literals;
- string literals;
- punctuation and separators.

Identifier rules should distinguish:

- module identifiers;
- local value identifiers such as `%value`;
- function names;
- constant names;
- table names;
- block labels;
- struct names;
- capability names;
- host import names with dot-separated namespaces.

Number literal rules should define:

- signed integer literals;
- decimal `f32`/`f64` literals;
- unsupported forms such as hex, binary, exponent notation, separators, and
  suffixes unless explicitly accepted later.

Table syntax must include current static table forms:

```ebnf
table_decl       ::= "table" ident ":" table_type table_len? "=" "[" table_values? "]"
table_type       ::= "i32" | "i64" | "f32" | "f64" | "bool" | "u8" | "u16" | "i16"
table_len        ::= "[" positive_int "]"
table_values     ::= table_value ("," table_value)*
table_value      ::= number_lit | bool_lit | ident
compact_get      ::= "table.get.u8" table_ref "," value_ref
                  | "table.get.u16" table_ref "," value_ref
                  | "table.get.i16" table_ref "," value_ref
table_get        ::= "table.get" table_ref "," value_ref
```

Import/use syntax must cover:

- `use std.module`;
- `use "./package-local.air"`;
- optional aliases;
- generated/package-local source import paths;
- rejected raw runtime imports.

Function and block syntax must cover:

- exported and private functions;
- parameters and return types;
- function-level effects;
- requires/ensures contracts;
- basic block labels;
- assignment instructions;
- terminators;
- compact call syntax;
- generic instruction fallback only where intentionally accepted.

## AST Schema

The parser should document the normalized AST shape it produces. At minimum:

### Module

- `name`;
- `uses`;
- `constants`;
- `tables`;
- `capabilities`;
- `effects`;
- `requires`;
- `ensures`;
- `structs`;
- `globals`;
- `externs`;
- `functions`.

### Imports

- import kind: bundle or source;
- name/path;
- alias;
- source location;
- imported/generated markers after source import resolution.

### Constants

- name;
- type;
- parsed literal value;
- source location.

### Tables

- name;
- storage/value type;
- fixed length;
- literal initializer values;
- source location;
- generated/manual origin derivable from source path;
- compact storage metadata after verification/reporting.

### Functions

- name;
- params;
- return type;
- exported flag;
- effects;
- requires/ensures;
- blocks;
- source location.

### Externs

- host import name;
- params;
- return type;
- generated/imported flags;
- source location.

### Capabilities, Effects, and Contracts

- explicit capabilities;
- generated capabilities;
- effect budgets;
- module-level contracts;
- function-level contracts.

## Roundtrip Law

The formatter must obey:

```text
parse(format(parse(x))) == parse(x)
```

The equality target is semantic AST equivalence, not byte-for-byte preservation
of comments or whitespace.

Roundtrip tests should cover:

- canonical examples;
- compact static tables;
- source imports;
- host imports;
- contracts/effects;
- structs/globals;
- arrays/buffers;
- generated modules;
- malformed input rejected before formatting.

## Golden Tests

The parser hardening suite should include positive and negative golden corpora.

Positive corpus:

- existing public examples;
- stdlib modules;
- package fixture modules;
- compact static table fixtures;
- generated handle modules;
- source import modules;
- minimal modules for each accepted syntax form.

Negative corpus:

- malformed AIR;
- unsupported type syntax;
- malformed table declarations;
- malformed `use` declarations;
- unknown compact table access forms;
- invalid block labels;
- invalid value names;
- malformed contracts/effects;
- unterminated strings;
- bad comments around strings.

Whitespace/comment corpus:

- weird indentation;
- blank lines;
- trailing comments;
- comments inside strings;
- comma spacing variations;
- multiple functions and declarations.

Numeric literal corpus:

- signed integers;
- decimal floats;
- out-of-range table values;
- rejected hex/binary/exponent/suffix forms unless separately accepted;
- negative zero behavior if relevant.

Unicode/path safety corpus:

- non-ASCII identifiers should be rejected unless explicitly accepted later;
- source paths should be package-local and normalized;
- path escape attempts should be rejected at package/import analysis;
- host object handle names must remain rejected.

## Fuzzing Plan

Parser fuzzing:

- generate token streams from the grammar;
- generate malformed token streams near accepted forms;
- assert parse success/failure is deterministic;
- assert parser errors include useful locations.

Verifier fuzzing:

- generate AST-valid but semantically invalid modules;
- assert verifier failures are deterministic and categorized;
- preserve stable diagnostics where available.

Lowerer differential tests later:

- compare verifier-accepted modules against lowering support;
- ensure every lowerable feature has explicit WAT/Wasm tests;
- ensure unsupported lowering fails clearly and does not claim success.

## Feature Admission Checklist

Every new AIR language feature must update:

- grammar docs;
- parser;
- formatter;
- verifier;
- report output;
- lowering if executable behavior is affected;
- package-check if package behavior is affected;
- tests;
- diagnostics;
- LSP-lite / Full LSP diagnostics.

The feature owner must also state whether the feature changes AIR ABI, Host ABI,
stdlib behavior, package metadata, generated artifacts, or reviewPolicy gates.

## Non-goals

- No parser rewrite in this RFC.
- No grammar generator requirement yet.
- No syntax changes in this RFC.
- No compiler semantics change.
- No AIR ABI change.
- No Host ABI change.
- No demo changes.

## Acceptance Tests

Future implementation should include:

- EBNF document exists and is linked from active docs;
- AST schema document exists and matches current parser output;
- positive parser golden corpus passes;
- negative parser corpus fails deterministically;
- formatter roundtrip law test covers accepted syntax;
- compact table grammar tests cover `u8`, `u16`, and `i16`;
- package fixture parse tests cover source imports and generated modules;
- fuzz seed corpus runs in CI or an explicit non-blocking workflow;
- parser/verifier/lowerer admission checklist is referenced by feature status
  or merge policy.

## Open Questions

- Should the EBNF live under `spec/` or `docs/rfcs/` until accepted?
- Should AST schema be documented as JSON-ish shape or TypeScript-style
  interfaces?
- Should grammar tests become a required release gate or a separate nightly
  fuzzing lane?
- How much generic instruction fallback should remain once grammar coverage is
  formalized?
