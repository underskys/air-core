# RFC: v0.32 AI Authoring Eval

Status: implemented replay first slice

## Purpose

Define a deterministic replay-mode eval harness for AI-authored AIR packages.
The goal is to measure authoring quality and repair behavior without requiring
live model calls, network access, or nondeterministic CI behavior.

## Replay Mode

Replay mode consumes checked-in prompts, candidate outputs, repair attempts,
diagnostics, and expected outcomes. It does not call a live model in P0.

Command:

```sh
node bin/airc.js eval-ai evals/ai_authoring --json
```

The command emits `kind: "air.aiAuthoringEvalReport"` with `mode: "replay"`.

Replay mode must be:

- deterministic;
- offline;
- free of wall-clock timestamps in report output;
- free of secrets, tokens, private text, raw URLs, and host authority;
- grounded in existing compiler/package-check diagnostics.

## Metrics

Required P0 metrics:

- first-pass verify rate;
- first-pass package-check rate;
- repair success at 1;
- repair success at 3;
- average repair iterations;
- forbidden surface rate;
- diagnostic code coverage;
- hallucination category counts;
- top diagnostic codes.

Metrics should be emitted in stable JSON and summarized in review/evidence docs
where appropriate.

## Inputs

Replay fixtures may include:

- prompt ID;
- expected package shape;
- generated AIR/package candidate;
- diagnostics from verify/package-check;
- repair attempt metadata;
- expected final status.

Fixtures must not include private payloads or live host authority.

Implemented directory shape:

```text
evals/ai_authoring/
  prompts/
  captured/model_outputs/
  captured/repair_transcripts/
  expected/constraints.json
  reports/
```

`expected/constraints.json` is the source of truth for case IDs and package-local
fixture paths. Captured outputs and repair transcripts are deterministic JSON
fixtures. The first slice records normalized verify/package-check statuses,
diagnostic codes, and hallucination categories; it does not store raw private
prompts, API responses, timestamps, or absolute paths.

## Live Model Mode

Live model eval is P1 and must remain optional. It is not used by the P0 command
and must not be part of required Core CI unless explicitly approved later with
network, cost, privacy, and flakiness controls.

## Diagnostics Boundary

The eval harness must use existing normalized diagnostics. It must not create a
parallel diagnostics engine or rewrite errors into incompatible codes.

## Non-goals

- no benchmark-style performance claims;
- no live model calls in P0;
- no automatic code actions;
- no package registry;
- no secrets or private prompt payloads;
- no runtime JSON/object model.

## Acceptance Checklist

- deterministic replay command or fixture runner;
- stable JSON output;
- metrics listed above;
- negative examples for forbidden surfaces;
- no live network dependency;
- no ABI changes.

Implemented P0 coverage:

- incident policy module;
- bounded `output.emit` module;
- fixed state module;
- structured IO module;
- hallucination negative case.
