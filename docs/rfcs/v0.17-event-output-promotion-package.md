# AIR v0.17 RFC: Event/Output Promotion Package

Status: draft evidence plan

Target milestone: v0.17

## Purpose

Define the evidence package required before AIR promotes any event/output Host
ABI candidate. This RFC does not implement `output.emit`, `output.event`,
`audio.event`, or Host ABI `0.11`. It defines what must be proven before a
separate Host ABI approval can be considered.

The goal is to keep event/output work generic, capability-gated,
profile-visible, report-visible, and conformance-testable across multiple
domains. Demo pressure may contribute evidence, but does not define Core scope.

## Promotion Rule

Host ABI `0.11` is not part of v0.17 by default.

`output.emit` remains a candidate only. Any Host ABI import for output/events
requires explicit separate approval through:

- RFC update or new RFC;
- Host ABI spec update;
- host profile support matrix;
- package-check/report diagnostics;
- conformance fixtures;
- negative tests;
- ABI decision record.

Without that approval, v0.17 may only prepare manifests, fixtures, reports, and
validation plans.

## Required Evidence Domains

Promotion requires evidence from at least two domains:

1. Interactive domain
   - game-like, UI, simulation, visual, or audio-adjacent output pressure;
   - must avoid game-specific Core APIs;
   - must prove output semantics are declared rather than inferred from host
     state, filenames, or debug metrics.

2. DevOps/SRE/policy/dashboard domain
   - alerts, audit events, pipeline notifications, policy violations, or
     dashboard outputs;
   - must prove the contract is not a visual/game effects API;
   - must prove scalar event arguments are sufficient for first promotion.

Both domains must use the same generic contract shape. A domain-specific import
such as `audio.event` is insufficient evidence for a generic Host ABI.

## Output-Events Manifest Draft

Promotion requires an output-events manifest draft with:

- `schemaVersion`;
- stable numeric event IDs;
- stable event names;
- channels;
- required capabilities;
- scalar argument schema;
- optional resource bindings;
- optional profile constraints.

Validation evidence must include:

- duplicate event ID failure;
- duplicate event name failure;
- unknown channel failure or explicit experimental-channel handling;
- missing required capability failure when linked to package-check;
- missing declared resource failure;
- manifest/source mismatch failure once AIR usage data exists.

The manifest remains tooling/planning only until a Host ABI import is accepted.
It must not allow AIR modules to emit events by itself.

## Generated Handles Plan

Promotion requires a generated handles plan before stable emission code is
accepted.

The plan must define:

- generated AIR handle module names;
- deterministic handle generation from output-events manifests;
- stale/missing generated handle checks;
- report visibility for generated event IDs;
- no authority grant from generated files;
- compatibility with existing generated artifact freshness checks.

Generated handles may provide symbolic IDs, but they must not create host
authority or bypass capability/profile checks.

## Package-Check Visibility

Package-check evidence must show:

- declared event manifests are discovered;
- declared channels are profile-checked;
- required capabilities are checked;
- unsupported channels/imports fail deterministically;
- manifest mismatches fail or warn according to policy;
- `debug.metric` event-bus misuse remains a reviewPolicy diagnostic, not a host
  event path.

Diagnostics must be machine-readable and use stable codes before promotion.

## Report Visibility

Reports must expose:

- declared output/event manifests;
- event IDs and names;
- channels;
- required capabilities;
- profile support status;
- generated handle status;
- output/event diagnostics;
- package/module origins when available.

Reports must make it clear whether output/event support is absent, tooling-only,
or backed by an accepted Host ABI import.

## Conformance Output Stream Fixture

Promotion requires conformance fixture planning and at least one fixture once an
emission candidate exists.

The future output stream model should record deterministic tuples:

```text
channel, id, args, flags, origin
```

The conformance fixture must cover:

- expected output stream matches;
- missing event;
- extra event;
- wrong channel;
- wrong ID;
- wrong scalar arguments;
- unsupported profile.

No pixel comparison, audio playback comparison, browser/GPU automation, or
host-inferred events are required for the first promotion gate.

## Profile Unsupported Tests

Promotion requires tests showing:

- profile declares supported output channels/imports;
- supported channel passes package-check;
- unsupported channel fails package-check;
- unsupported Host ABI import fails when the future import exists;
- profile support appears in surface/report output.

Profiles must not imply support for all output categories. Supporting visual
outputs does not imply support for audio, alerts, pipeline notifications, or
dashboard events.

## Debug.metric Negative Tests

Promotion requires negative tests showing:

- `debug.metric` used as event-like pulse emits
  `air.review.debug_metric_event_bus`;
- release-candidate `reviewPolicy` can fail that diagnostic;
- normal stable diagnostic metric usage is not over-rejected where the detector
  can distinguish it;
- hosts do not infer event/output semantics from `debug.metric`.

`debug.metric` remains diagnostics-only.

## Manifest Mismatch Tests

Promotion requires tests for:

- AIR references unknown event ID;
- manifest declares event unused by AIR when usage data exists;
- manifest event requires missing capability;
- manifest resource binding references missing resource;
- manifest channel unsupported by selected profile;
- generated event handle module is stale or missing.

## Candidate ABI Status

The preferred future candidate remains scalar-only:

```text
output.emit(channel:i32, id:i32, a0:i32, a1:i32, a2:i32, a3:i32, flags:i32)
```

This candidate is not implemented in v0.17.

The first candidate must not include:

- strings;
- dynamic payload maps;
- binary blobs;
- runtime object payloads;
- host object handles;
- runtime imports.

## Explicit Non-goals

- no `output.emit` implementation;
- no `output.event` implementation;
- no `audio.event` implementation;
- no `effect.event` implementation;
- no Host ABI `0.11` by default;
- no AIR ABI change;
- no game-specific Core APIs;
- no `draw_actor`;
- no `draw_contra_enemy`;
- no platformer water APIs;
- no voxel-specific Core APIs;
- no `debug.metric` event bus;
- no hidden host authority.

## Acceptance Checklist

Before Host ABI `0.11` can be proposed, all items must exist:

- interactive evidence package;
- DevOps/SRE/policy/dashboard evidence package;
- output-events manifest draft;
- generated handles plan;
- package-check visibility;
- report visibility;
- conformance output stream fixture plan or fixture;
- profile unsupported tests;
- `debug.metric` negative tests;
- manifest mismatch tests;
- explicit ABI decision record.

## ABI Impact

v0.17 impact:

- AIR ABI remains `0.10`;
- Host ABI remains `0.10`;
- no new host imports;
- no event/output runtime contract.

Future impact:

- Host ABI `0.11` is required only if a new output/event host import is
  accepted;
- AIR ABI `0.11` is required only if package calling convention, memory/data
  layout, entrypoint semantics, or runtime package metadata contract changes.
