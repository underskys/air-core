# RFC v0.37: Readonly Tablegroups First Slice

Status: implemented / first slice

Target milestone: v0.37

## Purpose

Define readonly grouped scalar table data for AIR without adding runtime JSON,
objects, host object handles, mutation, dynamic row counts, or game-specific
APIs.

Readonly tablegroups are intended to replace AI-authored slop patterns such as:

- long `select` chains pretending to be static tables;
- parallel scalar tables with implicit equal-length assumptions;
- table-like slot families that hide bounds and ownership;
- demo-local table conventions leaking into Core vocabulary.

The first slice implements parser, formatter, verifier, lowering,
report/evidence metadata, and tests for readonly tablegroups. It does not
change AIR ABI, Host ABI, mutable runtime representation, host authority, or
object/JSON semantics.

## Design Principle

Tablegroups are grouped readonly scalar data, not objects.

They are a verifier-visible way to say:

```text
these static scalar fields have the same row count
these fields are read together by bounded index
the index must be in bounds
the data is immutable package data
```

They are not records with identity, methods, dynamic shape, object references,
host handles, or runtime allocation.

## Pressure Sources

### AIRON

AIRON needs grouped readonly scalar tables for level data such as:

- level sections;
- platforms;
- collision rectangles;
- water volumes;
- visual layers;
- enemy anchors;
- pickup anchors;
- resource id sets.

AIRON is pressure evidence only. AIRON platformer rules, rendering, assets,
input, browser/WebGPU behavior, and gameplay APIs remain demo-local.

### FlowDesk and lan-observer

FlowDesk and lan-observer need bounded structured facts and summaries without
runtime objects. Tablegroups may provide a static readonly table form for data
that is package-authored or fixture-authored, while Bounded Structured IO
continues to cover schema-driven host-shaped facts.

### reviewPolicy

Existing reviewPolicy warnings such as `select-chain-as-table` and
table-like/slot-family patterns need a canonical recommendation path. A
readonly tablegroup can become that recommendation once implemented.

## Model

A readonly tablegroup is a named package-local data group with:

- a fixed row count;
- one or more scalar fields;
- equal field lengths;
- readonly package data;
- no runtime mutation;
- no dynamic row allocation;
- verifier-visible indexed reads;
- report/evidence/package-diff visibility.

## Allowed Field and Storage Types

First-slice candidates:

| Type | Status | Notes |
| --- | --- | --- |
| `i32` | accepted candidate | Canonical first-slice field type. |
| `bool` | conditional candidate | Allowed only if already supported by the surrounding static table machinery. |
| `u8` / `u16` / `i16` | deferred unless already accepted | May be considered only if existing static table storage already supports it without new ABI/runtime semantics. |

Rejected for first slice:

- strings;
- raw URLs;
- private text;
- nested records;
- dynamic arrays;
- maps;
- objects;
- host object handles;
- runtime JSON or `any`;
- pointer/slice/reference fields.

## Source of Truth

The package tablegroup declaration, schema, or metadata is the source of truth.

Generated handles or editor metadata, if added later, are derived artifacts.
They must not become semantic source of truth.

## Declaration Syntax Alternatives

v0.37 does not choose parser syntax. It records candidates for future
implementation review.

### Option A: Metadata-first tablegroup

```json
{
  "tablegroups": [
    {
      "name": "platforms",
      "rows": 32,
      "fields": [
        { "name": "x", "type": "i32" },
        { "name": "y", "type": "i32" },
        { "name": "w", "type": "i32" },
        { "name": "h", "type": "i32" }
      ]
    }
  ]
}
```

Pros:

- avoids parser change in first implementation;
- fits package-check/report/evidence tooling;
- keeps generated bindings derived from metadata;
- aligns with Bounded Structured IO first-slice approach.

Cons:

- less compact for AI-authored AIR source;
- needs clear generated handle conventions later.

### Option B: AIR source declaration

```air
tablegroup platforms[32] {
  x:i32 = [0, 16, 32]
  y:i32 = [120, 120, 96]
  w:i32 = [16, 16, 32]
  h:i32 = [8, 8, 8]
}
```

Pros:

- compact and readable;
- closer to authored static table intent;
- easier for formatter/LSP roundtrip once implemented.

Cons:

- requires parser and formatter work;
- must avoid becoming object or record syntax;
- needs stronger syntax gates before implementation.

### Option C: Group existing static tables

```json
{
  "tablegroups": [
    {
      "name": "platforms",
      "fields": {
        "x": "platform_x",
        "y": "platform_y",
        "w": "platform_w",
        "h": "platform_h"
      }
    }
  ]
}
```

Pros:

- lowest lowering risk;
- explicitly lowers to existing static tables;
- makes equal-length checks a package-check/verifier overlay.

Cons:

- still leaves authored parallel table definitions;
- weaker AI-facing ergonomics.

## Access Operation

Candidate operation:

```air
%x:i32 = tablegroup.get.i32 @platforms.x, %idx
```

Equivalent syntax may be accepted later if it is consistent with parser and
formatter conventions.

Requirements:

- `@platforms.x` names a declared readonly tablegroup field;
- `%idx` is an `i32` index;
- return type is the field value type, represented as `i32` for compact integer
  and enum/id fields where applicable;
- static out-of-bounds indices are rejected;
- dynamic indices require deterministic bounds check or deterministic trap
  behavior once lowering is implemented.

## Equal-length Validation

Package-check/verifier obligations:

- every field in a tablegroup must have the same declared row count;
- every backing static table must have the same length;
- missing fields are errors;
- duplicate field names are errors;
- empty tablegroups are errors unless a future RFC accepts them explicitly;
- mismatched parallel tables must produce a stable diagnostic.

Candidate diagnostics:

- `air.tablegroup.invalid`;
- `air.tablegroup.field_type_invalid`;
- `air.tablegroup.length_mismatch`;
- `air.tablegroup.index_out_of_bounds`;
- `air.tablegroup.mutable_rejected`;
- `air.tablegroup.dynamic_rows_rejected`.

## Bounds Validation

Bounds policy:

- fixed row count is required;
- statically visible out-of-bounds access is a verifier/package-check error;
- dynamic index behavior must be deterministic before lowering is accepted;
- if dynamic bounds cannot be implemented safely through existing static table
  machinery, implementation must stop.

## Report, Evidence, Diff, and Replay Visibility

Package report should expose:

- tablegroup name;
- row count;
- field names;
- field types;
- backing static table ids if applicable;
- generated artifact freshness if generated handles are added later;
- diagnostics.

Verification evidence should expose:

- tablegroup names;
- row counts;
- field summaries;
- read operations if available;
- no raw private payloads by default.

Package diff should expose:

- added/removed tablegroups;
- row count changes;
- field additions/removals/type changes;
- generated artifact freshness changes if applicable.

Replay/conformance summaries should expose:

- tablegroup metadata used by the package;
- mismatch diagnostics for row count or field shape changes;
- no raw demo assets or host private data.

## Lowering Model

Preferred first implementation lowering:

- tablegroup fields lower to existing static table machinery;
- tablegroup access lowers to a checked static table load or equivalent existing
  safe path;
- no new AIR ABI contract;
- no new Host ABI import;
- no host-visible tablegroup runtime object;
- no mutation.

AIR ABI remains `0.10` if tablegroups are only package-local static data lowered
through existing static tables and no external executable/runtime contract
changes.

If implementation requires a new executable representation, calling convention,
runtime export, or package ABI contract, implementation must stop and request an
AIR ABI decision before changing it.

## LSP Diagnostics

LSP should eventually surface:

- unknown tablegroup;
- unknown tablegroup field;
- field type invalid;
- row count missing;
- row count mismatch;
- index statically out of bounds;
- tablegroup mutation attempt;
- dynamic row count attempt;
- generated handle stale/missing if generated handles are added later.

Diagnostics must be stable and suitable for AI repair prompts.

## reviewPolicy Integration

reviewPolicy routes:

- `select-chain-as-table` to "Consider a readonly tablegroup if these
  values are related by row.";
- parallel table length mismatch to `air.tablegroup.length_mismatch` or
  equivalent;
- table-like/slot-family warnings to tablegroup or declared-pool routing,
  depending on whether the data is readonly or mutable.

Declared mutable pools are not tablegroups. They remain a separate future
PRO-gated feature.

The distinction is mandatory:

- readonly related static data -> readonly tablegroup;
- mutable repeated state -> declared pool future;
- generated handle constants -> generated handles;
- command/output streams -> command buffers or bounded `output.emit`.

reviewPolicy must not present tablegroups as the fix for mutable slot families.
Those patterns indicate future declared-pool pressure, not readonly data.

## AIRON Level-data Fixture

A future fixture may model AIRON-style readonly level data generically:

- platform rectangles;
- collision rectangles;
- water volumes;
- visual layer ids;
- enemy anchor ids;
- pickup anchor ids;
- resource ids.

The fixture must not include:

- AIRON source import;
- AIRON art/assets;
- browser/WebGPU code;
- platformer-specific Core APIs;
- game-specific host authority.

## Explicit Rejections

Readonly tablegroups must not become:

- runtime JSON;
- dynamic objects;
- maps;
- object identity;
- methods;
- nested records;
- mutable pools;
- dynamic row storage;
- host object handles;
- host-side table references;
- ORM/DB model;
- game-specific platformer APIs;
- output/event payload model.

## ABI Decision

AIR ABI remains `0.10` if first implementation lowers to existing static table
machinery and does not change executable/package runtime contracts.

Host ABI remains unchanged. Tablegroups are package-local readonly data and do
not require host imports.

Host ABI `0.11` remains limited to bounded `output.emit`.

## Kill Criteria

Stop if the design or implementation needs:

- runtime JSON;
- dynamic row counts;
- mutable tablegroups;
- object identity;
- tablegroup methods;
- host object handles;
- host authority;
- demo-specific platformer APIs;
- generated artifacts as semantic source of truth;
- AIR ABI or Host ABI changes without explicit ABI review.

## Acceptance Checklist Before Implementation

Before implementing tablegroups after v0.37:

- first-slice syntax or metadata model accepted;
- scalar-only field set finalized;
- equal-length validation diagnostics accepted;
- dynamic bounds behavior specified;
- report/evidence/diff/replay shape accepted;
- LSP diagnostics named;
- reviewPolicy routing accepted;
- AIRON fixture reduced to generic readonly table data;
- API gates updated with executable checks;
- AIR ABI and Host ABI decisions reaffirmed.
