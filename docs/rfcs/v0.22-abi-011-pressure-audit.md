# AIR v0.22 RFC: ABI 0.11 Pressure Audit

Status: RFC / architecture audit

Purpose: audit whether AIR ABI `0.11` or Host ABI `0.11` is justified after
v0.16-v0.21 advanced package, tooling, report, conformance, diagnostics, and
API gate layers while keeping executable AIR ABI and Host ABI at `0.10`.

This RFC does not change AIR ABI, Host ABI, compiler semantics, host imports, or
runtime behavior. It does not implement `output.emit`, `output.event`,
`audio.event`, `effect.event`, or any host-side action execution.

## 1. Current ABI Status

- Project milestone: `v0.21` / `v0.22`.
- AIR ABI: `0.10`.
- Host ABI: `0.10`.

Keeping ABI versions at `0.10` through v0.16-v0.21 was intentional. Most shipped
work changed reviewable metadata, package tooling, diagnostics, reports, and
conformance evidence rather than executable runtime contracts or public host
imports.

Prior milestones did not require an AIR ABI or Host ABI bump because these
surfaces are outside the executable scalar import/export ABI:

- package metadata and `air.package.json` fields describe package-local
  contracts but do not change compiled function signatures;
- report schemas and reviewPolicy output are machine-readable audit artifacts,
  not runtime values;
- verification evidence JSON is emitted by tooling and can represent pass,
  fail, or not-run without changing executable ABI;
- bounded facts and bounded rowset schemas are package metadata / tooling
  contracts; AIR does not receive arbitrary JSON objects;
- Output Contract manifests declare possible output intents but do not create a
  runtime event stream or host import;
- command buffers are metadata/conformance records in v0.20, not standardized
  runtime memory layout or Host ABI behavior;
- diagnostics-only LSP and LSP-lite output reuse normalized diagnostics and do
  not affect package execution;
- API gates and release/review checks prevent new forbidden surfaces but do not
  define runtime semantics.

These surfaces can be validated, reported, and consumed by tooling without
changing package entrypoint semantics, calling convention, host import registry,
runtime value representation, or AIR-owned executable memory layout.

## 2. AIR ABI 0.11 Candidates

| Candidate | Current status | Evidence needed | Required tests | Decision |
| --- | --- | --- | --- | --- |
| Fixed Bounded State Segment runtime layout | v0.22 RFC/gates only. No parser, verifier, lowering, or state runtime exists. | Accepted RFC, verifier model, conformance evidence, per-execution-instance semantics, memory/lowering design, and ABI decision. | Init/reset determinism, bounds, read/write budgets, no pointer escape, final-state digest, no host direct access. | Keep `0.10`; candidate only if runtime layout becomes package-visible. |
| Command buffer runtime contract | v0.20 command buffers are package metadata / conformance output-intent records. | Proof that runtime producers/consumers need a standardized memory layout rather than metadata/conformance records. | Output ID validation, capacity bounds, deterministic ordering, conformance replay, no host-side action execution. | Keep `0.10`; candidate only if command buffer layout becomes executable/runtime contract. |
| Tablegroups if runtime-visible | RFC/deferred source ergonomics only. | Clear lowering/runtime representation, package compatibility, and proof that source-only sugar is insufficient. | Parser/verifier/lowering tests, static shape tests, no object identity, no GC, compatibility tests. | Keep `0.10`; candidate only if runtime-visible. |
| Compact state if runtime-visible | Not implemented. v0.19 compact static tables are readonly storage/layout only. | Accepted compact state RFC, range validation, no silent truncation, report/evidence model, and runtime layout decision. | Range failures, load materialization as `i32`, no truncation, byte accounting, ABI compatibility. | Keep `0.10`; deferred. |
| Linked executable package runtime contract | v0.16 first slice exists for simple package-local linked output. | Runtime contract spec for entrypoints, linked memory/data layout, imports, exports, compatibility, and conformance. | Multi-module packages, profile compatibility, deterministic evidence, migration tests. | Keep `0.10`; candidate only with accepted runtime contract. |
| Standard package entrypoint semantics | Package manifests and exported functions exist, but no universal entrypoint ABI has been accepted. | Two or more package classes requiring the same entrypoint shape, profile behavior, verification evidence, and migration plan. | Entry dispatch, missing entry diagnostics, profile mismatch, source compatibility. | Keep `0.10`; deferred. |
| Component/WIT executable contract | Existing WIT/report surfaces are tooling and host compatibility aids. | Accepted component contract, host/runtime requirements, profile compatibility, and migration path. | WIT/component compatibility, host runtime loading, conformance, rollback. | Keep `0.10`; deferred. |

AIR ABI `0.11` should be considered only when a change affects executable
runtime/package contract: entrypoints, calling convention, memory/data layout,
runtime-required metadata, import/export semantics, or AIR-owned value/payload
representation.

Host ABI `0.11` should be considered only when a new public host import family
or host import semantics are required and cannot be represented by existing Host
ABI `0.10`, package metadata, command buffers, conformance, or host-owned
implementation improvements.

## 4. Voxel / Native Performance Pressure

Native or voxel performance pressure is architecture evidence, not an ABI
decision by itself.

Open questions:

- Is native slower than WebGPU/WebGL because Host ABI `0.10` lacks a needed
  import shape?
- Or is the bottleneck host implementation, batching, pipeline setup, debug
  mode, buffer uploads, command granularity, asset preflight, renderer state
  churn, or non-representative measurement?
- Does the same pressure appear outside one demo or renderer?
- Can package metadata, command buffers, compact static tables, linked output,
  or host implementation changes resolve the bottleneck without Host ABI
  changes?

Host ABI might not be the cause. Required metrics before any ABI decision:

- host calls per frame;
- draw commands per frame;
- buffer uploads per frame;
- CPU time;
- GPU time if available;
- Wasm execution time;
- JS/Wasm/native boundary crossings;
- debug mode vs release mode;
- command buffer size;
- binary size;
- package-check/report time.

Performance claims must include benchmark fixtures, environment details, stable
JSON output, and enough breakdown to distinguish AIR execution time from host
renderer time and upload/pipeline overhead.

## 5. Promotion Gates

Host ABI `0.11` may be accepted only if:

- two independent domains need the same narrow public host shape;
- package-check can see it;
- report and verification evidence can describe it;
- conformance can replay it;
- LSP diagnostics can surface misuse;
- API gates prevent slop;
- rollback and compatibility path exists.

AIR ABI `0.11` may be accepted only if:

- runtime/executable contract changes;
- package entrypoint, memory layout, data layout, calling convention, or
  runtime-required metadata changes;
- host/runtime must understand new executable metadata or representation;
- compatibility strategy exists.

ABI bumps must not be used as milestone markers. The project milestone version
can advance while AIR ABI and Host ABI stay fixed.

## 6. Recommendation

Recommendation: keep AIR ABI `0.10` and Host ABI `0.10` for now.

Current v0.16-v0.21 work is strong preparation for future ABI decisions, but it
does not yet force a runtime ABI bump:

- verification evidence, bounded rowsets, Output Contracts, command buffers,
  batch conformance, LSP diagnostics, API gates, and pressure requests are
  reviewable tooling/package/conformance surfaces;
- no accepted public host import requires Host ABI `0.11`;
- no accepted executable entrypoint/memory/calling-convention change requires
  AIR ABI `0.11`;
- performance pressure needs measurement and attribution before ABI design.

Possible next actions:

- keep Host ABI `0.11` behind the existing promotion gate;
- keep Fixed Bounded State Segment behind v0.22+ RFC and AIR ABI decision;
- create benchmark evidence before claiming graphics/native ABI bottlenecks;
- consider an experimental ABI/profile only if it is explicitly marked
  non-canonical and cannot be mistaken for public Host ABI.

No candidate is accepted for promotion by this audit.

## 7. Non-Goals

Do not propose or implement:

- raw `chrome.*`;
- DOM, React, IndexedDB, Jira, or fetch authority in AIR;
- host object handles;
- dynamic JSON runtime values;
- dynamic maps;
- GC or reflection;
- promises, callbacks, or async/await in AIR;
- runtime imports;
- game-specific Core APIs;
- `output.emit` without promotion evidence;
- Host ABI `0.11` because a project milestone advanced;
- AIR ABI `0.11` because a project milestone advanced.

## ABI Status

- AIR ABI remains `0.10`.
- Host ABI remains `0.10`.
- This RFC adds no implementation.
