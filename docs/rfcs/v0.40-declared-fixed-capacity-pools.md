# RFC v0.40: Declared Fixed-Capacity Pools / Slot Groups

Status: proposed / planning / gates

Milestone: v0.40

This RFC defines the boundary for declared fixed-capacity pools. It does not
implement pool syntax, verifier rules, lowering, runtime storage, generated
handles, or host APIs.

## Problem

AIR authors sometimes need repeated mutable runtime state with a known maximum
capacity. Today that pressure tends to appear as scalar slot families:

```text
projectile_0_active
projectile_0_x
projectile_0_y
projectile_1_active
projectile_1_x
projectile_1_y
...
```

reviewPolicy correctly treats many of these patterns as suspicious table-like
or slot-family slop. Some are accidental. Some are intentional bounded runtime
collections. AIR needs a vocabulary that distinguishes those cases without
becoming a dynamic object language.

AIRON is the immediate pressure source for projectiles, enemy bullets, enemies,
pickups, particles/effects, boss projectiles, and transient UI notifications.
That pressure is generic bounded mutable state pressure, not a platformer API
request.

## Model Split

The v0.40 vocabulary must keep three similar-looking surfaces separate:

- fixed state = named scalar mutable values such as counters, flags, scores, or
  individual handles;
- readonly tablegroup = static grouped readonly rows with equal-length scalar
  fields and no mutation;
- declared pool = bounded mutable repeated state with declared capacity,
  declared scalar fields, deterministic update, and verifier-visible slot
  bounds.

A pool is not a dynamic array, map/dictionary, object, tablegroup mutation, heap
allocation, GC-managed collection, or host object handle.

## Declared Pool Model

A declared pool is bounded mutable AIR state with:

- a fixed capacity literal;
- a positive capacity;
- a fixed scalar field list;
- a required active flag unless PRO explicitly rejects that requirement before
  implementation;
- deterministic update semantics;
- verifier-visible bounds;
- report-visible ownership.

A pool is not:

- a readonly tablegroup;
- a dynamic array;
- a map/dictionary;
- an object model;
- a host object handle;
- a heap allocation;
- a GC-managed collection;
- a platformer/game-specific API.

## Difference From Tablegroup

Readonly tablegroups are static grouped scalar data. They represent authored
static rows such as level sections, collision rectangles, visual layers, or
resource ID sets. They have fixed length and no mutation.

Declared pools are mutable runtime state. They represent a bounded number of
runtime slots that AIR may update deterministically. A pool may have row-like
fields, but mutability, active-slot handling, and loop budget accounting make it
separate from tablegroups.

Tablegroups answer: "Are these static fields related by row?"

Pools answer: "Is this repeated mutable state intentionally bounded?"

## Difference From Fixed State

Fixed state is the existing scalar state baseline. It works well for individual
counters, flags, scores, and small named values.

A declared pool is a structured declaration over repeated fixed state slots. It
does not introduce dynamic allocation. It gives the verifier and review surface
one bounded owner for a repeated mutable state family.

Fixed state remains source-level scalar state. Pool declarations, if accepted in
a future milestone, become the source of truth for repeated mutable slots.

## First-Slice Constraints

The future first implementation candidate, not v0.40 itself, must stay within:

- fixed capacity literal only;
- capacity greater than zero;
- active flag required unless PRO explicitly rejects that requirement before
  implementation;
- scalar fields only;
- `i32` and `bool` only unless another scalar state type is separately
  accepted;
- deterministic update;
- verifier-visible field and index bounds;
- report-visible ownership;
- no pointer/slice/reference escape;
- no runtime JSON;
- no dynamic maps;
- no object identity;
- no host object handles;
- no GC;
- no platformer-specific API.

The candidate must stop before implementation if `i32`/`bool` are insufficient
and accepting another field type would require broad parser, verifier, lowering,
or ABI changes.

## Source Of Truth

The pool declaration is the semantic source of truth.

Generated pool handles, generated host binding metadata, and any generated
storage layout are derived artifacts. Generated artifacts must not become the
semantic source of truth and must not introduce fields, capacity, authority, or
ownership absent from the declaration.

## Verifier Obligations

Future implementation must define verifier checks for:

- capacity proof: capacity is a fixed positive literal and is not derived from a
  parameter, host value, runtime state value, table length, or generated
  artifact;
- field access proof: every field access targets a declared pool field with an
  accepted scalar type;
- index bounds proof: every slot index is statically in bounds or guarded by a
  deterministic bounds check the verifier can recognize;
- active flag semantics: allocation, iteration, and update behavior must define
  how inactive slots are skipped, activated, deactivated, and reported;
- no pool slot pointer/slice/reference escapes;
- no pool methods/object behavior;
- no dynamic row count/capacity;
- no JSON/map/object field type;
- no host object handles or host-owned object identity;
- loop budget accounting covers worst-case capacity iteration and rejects loops
  whose accepted upper bound exceeds the declared budget;
- package report/evidence ownership is stable and deterministic.

The verifier must reject any design where pool safety depends on a host object,
GC, hidden heap, runtime JSON shape, or unchecked dynamic capacity.

## Report, Evidence, Diff, Replay

Pool metadata should be visible as metadata only:

- pool name;
- owner module;
- capacity;
- fields and scalar types;
- active field;
- state/storage footprint summary;
- generated artifact freshness if generated handles exist;
- diagnostics;
- replay mismatch categories if pool state affects replay.

Reports must not dump raw private slot values by default. Evidence should show
the boundary and ownership, not private payloads.

Package diff should identify changes to:

- pool added/removed;
- capacity changed;
- field added/removed/type changed;
- active flag rule changed;
- storage footprint changed;
- generated binding freshness changed;
- diagnostics changed.

Replay should distinguish:

- pool metadata validation;
- pool state digest match/mismatch if state digest is available;
- output/conformance mismatch caused by pool behavior.

## reviewPolicy Behavior

Declared pools should suppress accidental slot-family warnings only for the
declared owner and declared fields. This lets AIR tell reviewers:

```text
intentional bounded mutable pool
```

instead of:

```text
accidental repeated scalar slop
```

Undeclared slot families remain warnings or errors. Mutable slot families that
look pool-like should get repair hints pointing to declared pools once
implementation exists.

Mutable slot families must not get readonly tablegroup suggestions, because
readonly tablegroups cannot model runtime mutation. Readonly related static
data should continue to suggest tablegroups, not pools. Generated handles should
remain handles. Command streams should remain command buffers.

## Planned Diagnostics

Stable diagnostic codes should include:

- `air.pool.invalid`
- `air.pool.capacity_invalid`
- `air.pool.field_type_invalid`
- `air.pool.index_out_of_bounds`
- `air.pool.active_flag_missing`
- `air.pool.dynamic_capacity_rejected`
- `air.pool.object_model_rejected`
- `air.pool.pointer_escape`
- `air.pool.loop_budget_exceeded`

Diagnostics must be deterministic and grouped by authored module/package owner
where package composition metadata is available.

Additional diagnostics may be proposed later for generated artifact freshness,
undeclared slot-family repair hints, or privacy/reporting violations, but the
codes above are the minimum planned first-slice set.

## ABI Decision

AIR ABI remains `0.10` for v0.40 because this milestone is planning/docs/gates
only.

A future implementation may also keep AIR ABI `0.10` only if pools lower to
existing fixed state/static scalar machinery without changing executable calling
conventions or runtime contracts.

An AIR ABI review is required if pools need:

- new executable runtime contract;
- new calling convention;
- new memory/state representation visible outside existing AIR runtime rules;
- host/runtime-visible object or handle contract.

Host ABI remains unchanged. Declared pools must not add Host ABI imports.
Future Host ABI impact exists only if new host imports are accepted through a
separate Host ABI review.

## Kill Criteria

Stop the design or implementation if it requires:

- dynamic allocation;
- dynamic capacity;
- heap/GC;
- runtime JSON;
- dynamic maps/dictionaries;
- object identity;
- nested objects as runtime values;
- host object handles;
- tablegroup mutation;
- platformer/game-specific APIs;
- hidden host gameplay authority;
- raw host authority;
- generated artifacts as source of truth;
- verifier inability to prove bounds.

## Acceptance Checklist For Future Implementation

Before implementation:

- exact syntax or metadata form is accepted;
- scalar field type set is fixed;
- active flag semantics are accepted;
- capacity and bounds rules are verifier-checkable;
- loop budget accounting is specified;
- report/evidence/diff/replay fields are specified;
- diagnostics are stable;
- negative tests for JSON/object/GC/dynamic-map drift are planned;
- AIRON-style projectile pool is represented only as pressure sketch;
- AIR ABI and Host ABI no-change path is documented.
