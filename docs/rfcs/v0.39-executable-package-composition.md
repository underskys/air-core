# RFC v0.39: Executable Package Composition / Authored Graph Runtime

Status: accepted / first slice implemented

Target milestone: v0.39

## Purpose

Define how AIR can produce executable package output from authored package
modules while preserving authored module ownership in reports, evidence,
diagnostics, and review bundles.

The problem is generic package/runtime pressure. It is not a platformer API,
demo bundler, host adapter, package registry, or asset-pipeline feature.

## Motivation

Larger AIR consumers increasingly author packages as multiple modules, then
flatten them into generated AIR files before execution. AIRON currently does
this with generated `game/platformer.air`, which hides authored ownership and
keeps the frame monolithic.

Flattening is acceptable as a temporary local workaround, but it should not be
the canonical Core package path. Reviewers need to know:

- which authored module owns each decision or output;
- which imports are public, private, unresolved, or generated;
- whether executable output is fresh and deterministic;
- whether evidence maps back to authored source instead of only a flattened
  file.

## Definitions

### Authored graph

The authored graph is the package source graph written or generated as package
source intent. It includes authored modules, their imports, exported symbols,
private symbols, output contracts, structured IO schemas, tablegroups, command
buffers, and package metadata.

The authored graph is the source, review, and ownership surface. It is the
semantic source of truth for package authorship. Reviewers should be able to
approve or reject package behavior from the authored graph plus evidence
without treating a flattened executable artifact as the only meaningful source.
Capability declarations, effect declarations, output contracts, tablegroups,
structured IO schemas, command buffers, and package policy ownership originate
from the authored graph.

### Executable graph

The executable graph is the deterministic linked package output that can be
verified, lowered, executed, replayed, and packaged. It may contain generated or
linked modules, but it must preserve mapping back to authored ownership.

The executable graph is deterministic derived output. It must not become the
semantic source of truth. If an executable artifact disagrees with authored
modules, package metadata, output contracts, schemas, tablegroups, or declared
capabilities/effects, the authored graph wins and package-check must report the
executable graph as stale or invalid.

The executable graph cannot introduce new capabilities, effects, output
contracts, tablegroups, structured IO schemas, command buffers, imports, or
exports absent from the authored graph. If generated executable output contains
such a surface, package-check must treat it as drift from authored authority.

### Linked executable package output

Linked executable package output is the stable build artifact produced from the
authored graph. It must be deterministic in file names, ordering, symbol names,
metadata, diagnostics, and review reports. It must not include timestamps,
absolute paths, local machine data, secrets, or raw private payloads.

## P0 Model

v0.39 defines and implements a first slice where package tooling can:

1. Load the authored package graph.
2. Validate imports, exports, private symbols, and package metadata.
3. Produce or validate a deterministic executable graph.
4. Package-check authored graph and executable graph consistency.
5. Preserve authored ownership in reports and evidence.
6. Run a generic multi-module conformance fixture without demo-local
   flattening.
7. Reject unresolved imports and private import leakage with stable
   diagnostics.

The implementation reuses existing module graph, link-plan/link-symbol, linked
package, package-check, report/evidence, and scalar Wasm lowering surfaces. It
does not add a second package graph model, new host-visible executable graph
contract, AIR ABI change, or Host ABI change.

## First-slice Implementation Target

The smallest executable first slice is a generic package fixture, not an
AIRON-specific package. It should contain:

- at least two authored modules;
- one public import between authored modules;
- one private symbol that is not importable by another authored module;
- deterministic linked executable output derived from the authored graph;
- package report/evidence that preserves authored ownership after linking;
- a conformance replay proving the executable output path;
- a negative unresolved module import case;
- a negative unresolved symbol import case;
- a negative private symbol import attempt;
- no demo-local flattening in the canonical fixture path.

Implemented fixture path:

```text
test/fixtures/package_composition/basic_multi_module/
test/fixtures/package_composition/conformance_multi_module/
test/fixtures/package_composition/private_import/
test/fixtures/package_composition/unresolved_module/
test/fixtures/package_composition/unresolved_symbol/
```

The first slice should prefer existing package/linking surfaces before adding a
new representation. If existing linker output cannot preserve ownership
metadata, the implementation should stop at the smallest ownership metadata
extension rather than introducing package registry, host adapter, or ABI
semantics.

## Ownership in Reports and Evidence

Reports and evidence should expose:

- authored module id/path normalized relative to package root;
- executable module id/path normalized relative to package root;
- authored-to-executable mapping for each linked module or symbol;
- exported symbols and owning authored module;
- imported symbols and resolved authored/executable owner;
- private symbols that are not importable;
- generated artifacts and freshness status;
- output contracts and owning authored module;
- tablegroups, structured IO schemas, command buffers, and capabilities by
  authored owner;
- effects by authored owner;
- diagnostics grouped by authored module when possible.

Reports must not collapse ownership to only a flattened generated file.

Minimum report/evidence fields for the first slice:

| Field | Meaning |
| --- | --- |
| `authoredGraph.modules[]` | Authored module id/path normalized relative to package root. |
| `executableGraph.modules[]` | Executable module id/path normalized relative to package root. |
| `authoredToExecutable[]` | Mapping from authored module/symbol id to executable module/symbol id. |
| `exports[]` | Exported symbols and authored owner. |
| `imports[]` | Imported symbols, requested module/symbol, and resolved owner. |
| `privateSymbols[]` | Private symbols that are intentionally not importable. |
| `capabilities[]` | Declared capabilities and authored owner. |
| `effects[]` | Declared effects and authored owner. |
| `outputContracts[]` | Output contract ids and owning authored module. |
| `tableGroups[]` | Tablegroup name/fields and owning authored module. |
| `structuredIO[]` | Record/rowset/output summary schemas and owning authored module. |
| `diagnostics[]` | Stable diagnostics with authored module id when known. |

Raw local absolute paths must not appear in any of these fields. Paths are
package-relative and use `/` as the serialized separator.

Implemented first-slice fields:

- `authoredGraph`;
- `executableGraph`;
- `authoredToExecutable`;
- `ownershipMap`;
- `linkDiagnostics`;
- `generatedExecutableFreshness`.

## Package-check Obligations

Package-check should be able to reject or report:

- unresolved authored imports;
- unresolved executable imports;
- private symbol import attempts;
- duplicate exported symbol ownership;
- generated executable graph stale relative to authored graph;
- executable graph missing authored source ownership metadata;
- executable graph containing symbols or surfaces absent from the authored
  graph;
- absolute paths or timestamps in linked output metadata;
- generated artifacts becoming source of truth.

Diagnostics are stable and specific. Generic package-check collapse should
not hide a known unresolved/private import diagnostic.

Implemented diagnostic codes:

| Code | Condition |
| --- | --- |
| `air.package_graph.unresolved_module_import` | Authored module import references a module not present in the authored graph. |
| `air.package_graph.unresolved_symbol_import` | Authored import references a symbol not exported by the resolved module. |
| `air.package_graph.private_symbol_import` | Authored import attempts to import a private symbol from another module. |
| `air.package_graph.duplicate_public_export` | More than one authored module claims the same package-level public export. |
| `air.package_graph.executable_stale` | Executable graph was generated from different authored graph inputs or stale generated metadata. |
| `air.package_graph.ownership_metadata_missing` | Executable graph lacks required authored ownership metadata. |
| `air.package_graph.capability_drift` | Executable graph introduces a capability/effect absent from authored graph declarations. |
| `air.package_graph.absolute_path_rejected` | Linked output metadata contains an absolute local path. |
| `air.package_graph.timestamp_rejected` | Linked output metadata contains timestamp data. |

The implementation keeps legacy module graph diagnostics for compatibility and
adds the `air.package_graph.*` codes as the stable v0.39 ownership/executable
graph diagnostic layer.

## Determinism Requirements

Executable output must be stable across runs with the same inputs:

- stable file ordering;
- stable module ordering;
- stable symbol ordering;
- stable diagnostic ordering;
- stable package hash inputs;
- no timestamps;
- no absolute paths;
- no host-specific path separators in serialized reports;
- no nondeterministic generated names.

Package hashes and review bundle inclusion must be based on normalized
package-relative paths and stable serialized metadata. Generated output must not
depend on filesystem traversal order.

## Conformance Fixture

The P0 fixture is generic and small. It demonstrates:

- at least two authored modules;
- one public import between modules;
- one private symbol that cannot be imported;
- deterministic linked executable output;
- package report/evidence preserving authored ownership;
- successful package report/evidence plus linked package build/execute path;
- negative unresolved import case;
- negative private import case.

The fixture must not use AIRON-specific gameplay APIs, browser/Vite bundling,
assets, or external demo code.

## Negative Tests

Implemented negative cases:

- unresolved module import;
- unresolved symbol import;
- private symbol imported by another module;
- duplicate public export ownership;
- stale generated executable graph;
- generated executable graph introducing a capability/effect not present in
  authored metadata;
- absolute path in linked output metadata;
- timestamp in linked output metadata.

Executable graph missing ownership metadata remains a package-check obligation
for future persisted executable graph artifacts. The current first slice emits
ownership metadata directly in link-plan, linked build sidecars, package
reports, and verification evidence.

## Relationship to Existing Surfaces

### Module graph and linker

The implementation reuses existing module graph and linker machinery.

The preferred implementation path reuses:

- existing `src/module_graph.js` ownership and import/export graph logic;
- existing package-check graph validation rather than a second parallel package
  graph model;
- existing `src/lower_wasm.js` scalar Wasm lowering path rather than a broad
  lowering rewrite;
- existing package report, verification evidence, and conformance report
  surfaces for ownership metadata.

Rejected implementation approaches:

- building a second parallel package graph model with different ownership
  semantics;
- a large `lower_wasm` rewrite for package composition;
- treating generated executable graph metadata as semantic authority;
- requiring the host/runtime to understand ownership metadata in order to
  execute;
- adding package composition through demo-specific flattening scripts.

If reuse of the existing module graph, package-check graph, and lowering path
is not possible without a broad rewrite, implementation must stop and report
the gap before adding new architecture.

Implementation touch points:

- `src/module_graph.js` for authored graph ownership and import/export
  resolution;
- `src/link_plan.js`, `src/link_symbols.js`, and `src/linked_package.js` for executable graph
  output;
- `src/package_graph_ownership.js` for ownership metadata and stable package
  graph diagnostics;
- `src/sdk.js` for package-check/report ownership fields;
- `src/verification_evidence.js` for ownership-preserving evidence;
- link-plan and linked-package tests for the generic multi-module fixture;
- CLI package/report paths only if an existing command cannot expose the first
  slice.

Parser, verifier, lowering, AIR ABI, and Host ABI were not changed for this
first slice.

### Package diff

P1 may add authored/executable graph deltas. P0 only needs to define how those
deltas should be represented.

### Evidence review

Evidence should preserve authored ownership for decisions, outputs, imports,
and diagnostics. A generated executable graph is reviewable only when it can be
traced back to authored modules.

### Consumer evidence

Consumer evidence can cite package composition pressure, but demos remain
pressure rather than authority. No demo can define Core ABI or package runtime
semantics directly.

### AIRON boundary

AIRON flattening is valid pressure evidence because it shows that authored
multi-module packages need a canonical executable output path. It does not
define Core API or package runtime semantics.

Core may accept generic multi-module package composition. Core must not
implement AIRON-specific frame semantics, platformer game-loop semantics,
asset slicing, rendering, browser/Vite bundling, WebGPU presentation behavior,
or platformer-specific helper APIs as part of this milestone.

Demo-specific bundling remains outside Core. AIRON may later consume the generic
composition path, but the generic path must be useful without AIRON.

## Non-goals

- package registry;
- native installer;
- demo-specific bundlers;
- browser/Vite host bundling;
- asset pipeline rewrite;
- AIRON-specific gameplay APIs;
- real host adapters;
- host authority;
- declared mutable pools;
- tablegroup expansion;
- Host ABI change;
- AIR ABI change unless a later executable contract requires separate ABI
  review.

## ABI Decision

AIR ABI remains `0.10` for the first slice. The first slice must reuse existing
AIR module, linker, lowering, runtime, and scalar Wasm conventions.

Host ABI remains unchanged. Host ABI `0.11` remains limited to bounded
`output.emit`.

If implementation requires a new executable/runtime contract, external calling
convention, host import, or host-visible package layout, the work must stop and
produce an ABI review instead of silently changing ABI.

Examples that require ABI review:

- a new calling convention;
- a new host/runtime-visible executable graph contract;
- a new module linking runtime ABI;
- new required import/export semantics;
- requiring the host/runtime to understand ownership maps to execute;
- changing lowered Wasm exports/imports beyond existing conventions.

## Kill Criteria

Stop if the design requires:

- game-specific Core APIs;
- host authority;
- new Host ABI imports;
- mutable pools;
- tablegroup expansion;
- runtime JSON/object model;
- package registry semantics;
- external demo source import;
- nondeterministic generated executable output;
- reports that hide authored ownership behind a flattened generated file.

## Acceptance Checklist Before Implementation

Before implementation starts, confirm:

- exact files/modules expected to change are identified;
- diagnostic codes and fallback behavior are defined;
- generic multi-module fixture shape is defined;
- report/evidence fields are defined;
- no-ABI-change path is viable with existing module/linker/scalar Wasm
  conventions;
- kill criteria are accepted;
- AIRON remains pressure evidence only and does not define Core API;
- no external demo source code is required;
- package composition implementation can be reviewed independently from
  package registry, host adapter, tablegroup expansion, and declared pools.
