# AIR v0.21 RFC: Host ABI 0.11 Promotion Gate

Status: RFC / promotion gate

Purpose: define exact conditions for promoting output and host interaction from
tooling/command-buffer contracts to public Host ABI `0.11`.

This RFC does not implement Host ABI `0.11`, `output.emit`, `output.event`,
`audio.event`, `effect.event`, or any host-side action execution. Host ABI
remains `0.10`; AIR ABI remains `0.10`.

## 1. Current State

AIR already has reviewable output and host-interaction preparation surfaces:

- Output Contract manifests exist as tooling/package metadata;
- command buffers exist as bounded scalar output-intent metadata;
- verification evidence JSON exists for machine-readable package claims;
- deterministic conformance and replay fixtures exist for scalar and batch
  pressure;
- package-check and report surfaces can expose package metadata, diagnostics,
  fingerprints, and compatibility;
- diagnostics-only LSP can surface package/check/report diagnostics;
- Host ABI remains `0.10`.

Current command buffers are intents only. Host policy owns execution and
side-effect authorization.

## 2. Candidate Promotions

Candidate Host ABI `0.11` promotions may include:

- `output.emit`;
- `output.event`;
- narrowly scoped extension command intents;
- other bounded scalar output-intent imports that have passed this gate.

`audio.event` and `effect.event` remain explicitly deferred unless each has a
separate justification, promotion package, tests, and host-policy boundary.

Any candidate must remain scalar-only unless a separate AIR ABI/runtime
contract change is accepted. Strings, arbitrary JSON, dynamic maps, host object
handles, binary blobs, promises, callbacks, and runtime imports are not allowed
as a shortcut.

## 3. Required Evidence Before Host ABI 0.11

Host ABI `0.11` requires evidence from at least two independent domains:

- interactive/game-like;
- DevOps/SRE/FlowDesk/policy/dashboard.

Required evidence:

- package-check visibility for every proposed import/channel/intent;
- report visibility for output IDs, channels, capabilities, args, diagnostics,
  fingerprints, and profile compatibility;
- verification evidence that records package identity, ABI hash, output
  contracts, command buffers, diagnostics, and profile status;
- deterministic conformance replay that can compare expected output streams or
  command records;
- mock host / policy executor proving that host policy remains the owner of
  execution and side effects;
- privacy boundary showing raw text, URLs, tokens, secrets, browser state, and
  private notes do not cross into AIR without explicit host policy;
- LSP diagnostics for unsupported imports, profile mismatch, manifest mismatch,
  missing output IDs, and deprecated event-bus patterns;
- negative tests against `debug.metric` as an event bus.

Promotion evidence must include both positive fixtures and negative tests.
Examples or demos alone are not authority; they are pressure evidence only.

## 4. Rejected

The Host ABI `0.11` path must not introduce:

- raw `chrome.*`;
- DOM, React, IndexedDB, Jira, or fetch authority in AIR;
- automatic host-side action execution;
- host object handles;
- arbitrary JSON runtime data;
- dynamic maps;
- GC or reflection;
- async-await, promises, or callbacks in AIR;
- runtime imports;
- private text, raw URLs, tokens, secrets, or browser permissions as AIR-owned
  authority.

These remain host-owned or rejected from AIR Core.

## 5. Decision Tree

### Host ABI Stays 0.10

Keep Host ABI at `0.10` when:

- the need can be represented by Output Contract manifests plus command buffers;
- the behavior is package-check/report/conformance tooling only;
- host policy can consume verification evidence without a runtime host import;
- only one domain has proven the shape;
- privacy, profile, LSP, or negative-test coverage is incomplete;
- the proposal relies on debug metrics, raw browser authority, host objects, or
  arbitrary runtime JSON.

### Host ABI 0.11 Is Justified

Host ABI `0.11` may be justified only when:

- at least two independent domains prove the same bounded scalar shape;
- package-check, report, verification evidence, conformance, and LSP all expose
  the contract;
- profile support and unsupported-profile failures are tested;
- mock host / policy executor tests prove no automatic action execution;
- negative tests fail `debug.metric` event-bus misuse;
- compatibility behavior for Host ABI `0.10` packages is documented;
- a separate decision record accepts the import names, signatures, profile
  rules, and diagnostics.

### AIR ABI 0.11 Is Required

AIR ABI `0.11` is required only if promotion changes executable package/runtime
representation, calling convention, memory/data layout, entrypoint semantics,
runtime-required package metadata, or AIR-owned value/payload semantics.

A scalar Host ABI import using existing AIR ABI `0.10` scalar import
conventions does not automatically require AIR ABI `0.11`.

### Rollback / Compatibility Strategy

Any Host ABI `0.11` promotion must define:

- Host ABI `0.10` package behavior;
- package-check diagnostics for unsupported Host ABI imports;
- profile compatibility failures;
- feature flags or profile gates where applicable;
- conformance fixtures for both supported and unsupported profiles;
- migration docs from command buffers/tooling contracts to Host ABI imports;
- a rollback path that keeps Output Contract manifests and command buffers
  valid tooling surfaces if runtime promotion is delayed or reverted.

## ABI Status

- Host ABI remains `0.10`.
- AIR ABI remains `0.10`.
- This RFC adds no implementation.
