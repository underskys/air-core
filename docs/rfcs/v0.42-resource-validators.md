# RFC v0.42: Resource Validators

Status: planning

## Summary

Define a deterministic Core resource validator model for package-check/report
surfaces. The first goal is to move safe, generic parts of demo-local validation
into Core without changing AIR language semantics, AIR ABI, Host ABI, host
authority, or demo source code.

## Motivation

Downstream pressure shows repeated validation needs:

- runtime asset roots must stay inside declared package roots;
- manifest references can become stale or point at missing files;
- generated handles can drift from their source contracts;
- demo-local checks often mix generic package validation with domain-specific
  policy.

v0.42 separates generic package/resource validation from demo-local validation.

## Generic vs Demo-Local Validators

P0 generic Core validators:

- manifest references use only allowed runtime roots;
- forbidden runtime roots are rejected;
- referenced manifest files exist when they are included in the package;
- generated handle freshness checks;
- resource manifest/schema shape checks;
- no fallback to missing textures/resources in release profile when represented
  in a manifest;
- report/evidence summaries for validator status.

P1/optional candidates, only if deterministic and low-risk:

- PNG alpha not empty;
- accidental dark/black color-key transparency;
- audio non-silence;
- tiny header-only audio file rejection.

Demo-local validators:

- platformer water correctness;
- sprite art style;
- boss animation frames;
- visual layer meaning unless represented as a generic manifest policy;
- gameplay-specific asset naming;
- browser/Vite bundling checks;
- full media quality analysis;
- production asset pipeline rules;
- demo-specific runtime policy.

Core validators may validate package/resource contracts. They must not encode
domain meaning such as "this sprite looks correct" or "this water layer behaves
correctly."

## Registry Model

The resource validator registry should define:

- validator id;
- scope;
- severity;
- profile applicability;
- deterministic inputs;
- report fields;
- diagnostics;
- repair hint;
- owner layer.

Example shape:

```json
{
  "id": "air.resource.missing_reference",
  "scope": "package",
  "severity": "error",
  "profiles": ["release", "review"],
  "inputs": ["air.package.json", "manifest resource references"],
  "reportFields": ["resource", "manifest", "profile", "expectedPath"],
  "repairHint": "Add the referenced resource to the package or remove the manifest reference."
}
```

Validators must not depend on:

- network;
- external services;
- wall-clock time;
- nondeterministic filesystem ordering;
- private raw data;
- large media committed to the Core review bundle.

## Package-Check Hooks

Package-check should invoke validators after package metadata and manifests are
loaded and before report/evidence generation.

Validator failures should be machine-readable diagnostics. Validator warnings
may remain warnings unless a release gate marks them as hard failures.

Resource validation is a package-check/report layer. It is not AIR source
syntax, verifier semantics, lowering semantics, AIR ABI, or Host ABI.

## Freshness

Manifest reference freshness should detect:

- missing referenced files;
- stale generated handles;
- generated artifacts newer/older than source contract when metadata exists;
- references outside allowed roots;
- forbidden roots such as build outputs, raw logs, or unreviewed demo bundles.

Generated handles remain derived artifacts. Schemas, contracts, manifests, and
source declarations remain source of truth.

## Stable Diagnostics

Planned diagnostic codes:

- `air.resource.forbidden_root`;
- `air.resource.missing_reference`;
- `air.resource.generated_stale`;
- `air.resource.release_fallback_rejected`.

Diagnostic payloads should include package-local paths only. They must not
include local absolute paths or raw private data.

## Baseline Debt

Known baseline debt may be represented explicitly as:

- validator id;
- affected path or manifest item;
- current status;
- accepted reason;
- owner;
- planned cleanup or expiration if known.

Baseline debt must not hide new regressions.

## Report/Evidence

Reports and evidence should expose:

- `resourceValidationResults[]`;
- diagnostics;
- affected manifests/resources;
- profile applicability;
- baseline debt entries;
- regression status;
- privacy/safety notes.

Reports must avoid raw private data and large media content by default.

## Non-Goals

- no language syntax changes;
- no AIR ABI change;
- no Host ABI change;
- no network or external services;
- no demo-specific Core APIs;
- no browser/Vite bundling;
- no asset pipeline rewrite;
- no runtime resource loading;
- no package registry;
- no native installer;
- no host authority.

## Kill Criteria

Stop if a validator design requires:

- nondeterminism;
- network or external service calls;
- raw private data ingestion;
- large media in the Core review bundle;
- runtime JSON/object model;
- host object handles;
- Host ABI expansion;
- AIR ABI expansion;
- demo-specific Core semantics.
