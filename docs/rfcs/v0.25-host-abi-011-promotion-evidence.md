# AIR v0.25 RFC: Host ABI 0.11 Promotion Evidence

Status: design / planning

Purpose: define the evidence required before any Host ABI `0.11` import can be
accepted.

This RFC is documentation only. It does not implement Host ABI `0.11`, add
`output.emit`, add host imports, change AIR ABI, change Host ABI, or add raw
host authority.

## 1. Promotion Principle

Host adapters may be rich. Public Host ABI must remain small, canonical,
versioned, capability-scoped, and conformance-tested.

A Host ABI import is promoted only when it has generic semantics across
independent domains and can be verified, audited, reported, tested, and rolled
back.

## 2. Two-Domain Evidence Requirement

At least two independent domains must support the same semantics:

1. Non-game policy/ops domain.
   - Example pressure: AirOps-style incident diagnostics.
   - Required proof: bounded facts, deterministic AIR decision, Output
     Contracts, command buffers, verification evidence, conformance replay, and
     host policy decision evidence.
2. Interactive/visual domain.
   - Example pressure: dashboard, visual command policy, UI/tool interaction,
     or graphics package command intent.
   - Required proof: same command/evidence semantics without borrowing
     game-specific or browser-specific authority.

One project, one demo, or one host adapter is not enough evidence.

## 2.1 v0.25 Fixture Evidence

v0.25 adds deterministic fixture evidence for both required domains without
adding Host ABI `0.11`, `output.emit`, host imports, raw platform authority, or
real side effects.

| Domain | Fixture | Evidence |
| --- | --- | --- |
| Non-game policy/ops | `test/fixtures/conformance_batch/airops/` | AirOps-style bounded incident facts, Output Contract, command buffer, mock host policy, and expected `air.hostInteractionEvidence`. |
| Interactive/visual-like | `test/fixtures/host_interaction/visual_panel/` | Synthetic panel command intents using the `visual` output channel, Output Contract, command buffer, mock host policy, allowed evidence, and denied-output evidence. |

The visual fixture is intentionally not a game demo and does not grant renderer,
GPU, Canvas, DOM, or browser authority. It proves the same command-buffer and
host-policy semantics in a second domain while keeping execution host-owned.

## 3. Required Evidence Before Host ABI `0.11`

Before any Host ABI `0.11` import is accepted, the proposal must provide:

- generic semantics and stable naming;
- capability model;
- effect model;
- package-check visibility;
- report and verification evidence visibility;
- selected host profile support;
- conformance fixtures;
- negative tests for unsupported profiles and raw authority leakage;
- reference mock host / policy executor evidence;
- privacy rules for arguments and diagnostics;
- deterministic replay checksum;
- rollback/compatibility path for Host ABI `0.10` packages;
- migration notes explaining why command buffers are insufficient.

## 4. Candidate: `output.emit`

`output.emit` is a plausible future candidate only if evidence proves that a
runtime emit import is necessary.

It must not be implemented in v0.25 P0 because current command buffers already
support:

- bounded output intent metadata;
- Output Contract validation;
- deterministic conformance replay;
- verification evidence;
- host policy decision planning;
- offline/reference host simulation.

The missing evidence is whether runtime emit semantics are generic and safe
across independent domains.

## 5. Candidate Conditions For Host ABI `0.11`

Host ABI `0.11` becomes justified only if:

- a runtime host import is required, not just package metadata;
- command buffers cannot express the needed interaction with bounded intent;
- host policy decisions remain explicit and reviewable;
- failure modes are deterministic;
- unsupported hosts fail package-check before runtime;
- no raw authority leaks into AIR Core;
- no runtime JSON/object model or host object handles are introduced.

## 6. Rejection Conditions

Reject or defer the promotion if the proposal depends on:

- raw `chrome.*`;
- DOM/React/IndexedDB/Jira/fetch authority;
- DB/cloud SDK imports;
- host object handles;
- runtime JSON/object model;
- automatic host-side side effects;
- secrets, tokens, credentials, raw URLs, raw logs, or private text;
- one domain only;
- one host implementation only;
- missing negative tests;
- missing rollback path.

## 7. Rollback And Compatibility

Any Host ABI `0.11` candidate must preserve Host ABI `0.10` package behavior.
Host ABI `0.10` packages keep using Output Contracts, command buffers,
verification evidence, and conformance replay.

If a package opts into a future Host ABI `0.11` import, unsupported hosts must
fail package-check with clear diagnostics. A downgrade path to command-buffer
intent metadata should exist where practical.

## 8. v0.25 Decision

v0.25 should continue with promotion evidence only.

Do not implement Host ABI `0.11` or `output.emit` in v0.25 P0. Use the
milestone to define the reference host contract, mock policy executor evidence,
two-domain promotion evidence, and negative raw-authority tests.
