# RFC: v0.45 Public Showcase & Host Composition

Status: planning

Target milestone: v0.45

## Summary

v0.45 defines the first showcase-oriented milestone for AIR Core after public
npm release. The goal is to demonstrate AIR as a verifier-first language and
toolchain for bounded deterministic components that hosts compose into larger
systems.

This RFC does not add language features, change AIR ABI, change Host ABI, or
move demo-specific APIs into Core.

## Motivation

The public package can currently be installed as `@underskys/air-core`, and the
CLI is `airc`. The next public work should make the value proposition visible:

- AI can author compact `.air` components.
- AIR verifies capabilities, effects, bounds, and host boundaries before
  execution.
- Hosts compose verified components into tools, simulations, dashboards,
  games, robotics policies, and 2D/3D scenes without giving AIR platform
  authority.

The showcase must avoid two errors:

- presenting AIR as only tiny policy snippets;
- presenting AIR as a full engine, robotics stack, CAD/Adobe/Blender
  replacement, or general-purpose application language.

## Showcase Tracks

### 1. Anti-Hallucination / Safety Demo

This track should show a deterministic failure before execution for at least
one unsafe or invented surface, such as:

- invented stdlib/API call;
- undeclared host authority;
- unbounded recursion or unsupported unbounded execution shape;
- invalid capability/effect use;
- invalid memory/resource lifetime pattern.

The demo must have:

- copy-paste command;
- expected failing diagnostic;
- short explanation of why the rejection matters;
- no secrets, raw private data, network access, or external service calls.

### 2. AIR MathLab / 3D Math Scene Demo

This track should show AIR as deterministic math/control logic that a host can
compose into a visual or 3D scene.

AIR may own:

- numeric scoring or transforms;
- bounded update rules;
- deterministic control decisions;
- capability/effect declarations;
- evidence report surface.

The host owns:

- renderer;
- scene graph or engine objects;
- assets/materials;
- frame loop;
- IO and platform authority.

The demo can be linked if it lives outside the npm package, but the Core docs
must describe the AIR/Host boundary and the verification/evidence command.

### 3. Simulation/Game/AirWorld Slice Demo

This track should show a host-composed interactive slice where AIR contributes
bounded deterministic components without becoming a game-specific API.

Required boundary:

- AIR owns rules/policies/components that are portable and verifier-checked.
- Host owns gameplay loop, rendering, assets, input devices, networking, audio,
  persistence, and deployment.
- Consumer pressure from the slice enters the request ledger if it asks for
  Core, stdlib, package, or Host ABI changes.

## Allowed in v0.45

- docs;
- `examples/public/` improvements;
- demo portfolio index;
- kit/stdlib pressure notes;
- bugfixes;
- package/evidence polish;
- public claims and overclaim hygiene;
- request ledger updates for new pressure;
- no ABI expansion unless separately approved.

## Not Allowed in v0.45

- runtime JSON/object model;
- dynamic maps or dictionaries;
- host object handles;
- robotics hardware ABI;
- full scene graph in AIR Core;
- CAD, Adobe, Blender, full-engine, or general-purpose application-language
  replacement claims;
- demo-specific Core APIs;
- new Host ABI imports;
- AIR ABI expansion;
- Host ABI expansion;
- npm publish from Codex;
- tag creation from planning work.

## Host Boundary

AIR owns deterministic logic, capabilities, effects, bounded execution under
the verifier model, package/evidence surfaces, and declared output intents.

The host owns rendering, IO, assets, UI, hardware, networking, platform
authority, device access, real-world actions, and policy decisions for host
effects.

Showcase docs must include an `AIR owns / Host owns` table so readers do not
infer hidden host authority inside AIR.

## Acceptance Criteria

v0.45 implementation work is acceptable only when:

- `npm install -g @underskys/air-core@alpha` works;
- README quickstart works;
- external VM smoke or equivalent clean-environment smoke passes;
- at least one anti-hallucination / safety demo works;
- at least one evidence report demo works;
- at least one AIR MathLab / 3D math host-composed demo exists or is linked;
- any new consumer pressure has a request ledger entry or explicit no-pressure
  rationale;
- `npm run check:public-claims` passes;
- no AIR ABI change occurs;
- no Host ABI change occurs.

## Versioning

- Target package release: `v0.45.0`.
- npm dist-tag: `alpha`.
- No 1.0 compatibility promise yet.
- AIR ABI remains `0.10`.
- Host ABI remains `0.11` latest, limited to bounded `output.emit`.

## Kill Criteria

Stop v0.45 showcase work and open a separate RFC if the work requires:

- new AIR syntax or semantics;
- new Host ABI import;
- runtime object/JSON/map model;
- host object handle support;
- AIR-owned renderer/scene graph;
- robotics hardware control ABI;
- demo-specific Core API;
- claims that cannot be reproduced from public docs and commands.
