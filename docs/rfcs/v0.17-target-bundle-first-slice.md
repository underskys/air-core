# AIR v0.17 RFC: Target Bundle First Slice

Status: accepted first-slice design

Target milestone: v0.17

## Purpose

Define the first folder-based AIR target bundle slice. v0.16 introduced
metadata-only `airpkg` artifacts; v0.17 should define how those artifacts can be
assembled with target metadata, linked output when available, declared
resources, and host profile evidence into deterministic development bundles.

This RFC defines development bundle folders only. It does not define native
installers, production web deploys, stores, registry behavior, or demo-specific
bundle formats.

## Targets

Initial target ids:

- `web-dev`
- `native-dev`

Both targets are folder layouts intended for local validation, host integration,
and CI evidence. They are not final product distribution formats.

## Non-goals

- no macOS `.app`;
- no Windows installer or `.exe` packaging;
- no Linux AppImage;
- no Steam packaging;
- no package registry;
- no remote fetching;
- no runtime Node, npm install, Python, Codex, source repo, or build script
  requirement;
- no demo-specific bundle;
- no Host ABI change;
- no AIR ABI change.

## Bundle Layouts

`web-dev`:

```text
dist/web-dev/
  airpkg.json
  linked.wasm or linked.wat if available
  assets/ if referenced
  host_profile.json
  bundle.json
  README.md
```

`native-dev`:

```text
dist/native-dev/
  airpkg.json
  linked.wasm or linked.wat if available
  assets/ if referenced
  host_profile.json
  bundle.json
  README.md
```

The first slice may use the same file layout for both targets. The target id is
still meaningful because host profile compatibility, runtime notes, and future
host launchers differ by target.

## Bundle Manifest Schema

`bundle.json` should be deterministic JSON:

```json
{
  "schemaVersion": "0.17",
  "kind": "air.targetBundle",
  "target": "web-dev",
  "package": {
    "name": "example",
    "version": null,
    "airpkg": {
      "path": "airpkg.json",
      "hash": "sha256:..."
    }
  },
  "abi": {
    "airAbiRequired": "0.10",
    "hostAbiRequired": "0.10"
  },
  "hostProfile": {
    "id": "browser-webgpu",
    "path": "host_profile.json",
    "hash": "sha256:..."
  },
  "linkedOutput": {
    "status": "available",
    "kind": "wasm",
    "path": "linked.wasm",
    "hash": "sha256:..."
  },
  "resources": [
    {
      "kind": "asset",
      "path": "assets/example.png",
      "hash": "sha256:...",
      "source": "copied"
    }
  ],
  "boundary": {
    "runtimeRequires": [],
    "buildTimeOnly": [],
    "forbiddenAtRuntime": [
      "Node",
      "npm install",
      "Python",
      "source AIR repo",
      "Codex",
      "build scripts"
    ]
  }
}
```

Required fields:

- `schemaVersion`;
- `kind`;
- `target`;
- package identity;
- `airpkg.path` and `airpkg.hash`;
- AIR ABI requirement;
- Host ABI requirement;
- host profile id/path/hash;
- linked output status/kind/path/hash when available;
- resource entries when runtime resources are copied into the bundle;
- build-time/runtime boundary fields.

## Included Files

Required files:

- `bundle.json`;
- `airpkg.json`;
- `host_profile.json`;
- `README.md`.

Conditional files:

- `linked.wasm` when linked Wasm is available;
- `linked.wat` when linked WAT is the selected linked output;
- `assets/**` when runtime resources are copied into the bundle.

`README.md` must state that the folder is a development target bundle, not a
native installer or production deploy.

## Copied vs Referenced Resources

The first slice should prefer copied runtime resources inside the bundle. Copied
resources make validation source-independent and avoid local checkout coupling.

If a resource remains referenced instead of copied, the bundle manifest must say
so explicitly:

```json
{
  "path": "assets/example.png",
  "source": "referenced"
}
```

Referenced resources are allowed only for development evidence and must not use
absolute paths. Production-like bundles should require copied resources.

## Hash Validation

Bundle validation must check:

- `airpkg.json` hash matches `bundle.json`;
- `host_profile.json` hash matches `bundle.json`;
- linked output hash matches when linked output is declared;
- copied resource hashes match;
- missing declared files fail;
- hash mismatches fail.

All hashes use `sha256:` prefixes over normalized file bytes.

## Host Profile Compatibility

Bundle validation must check:

- selected host profile exists in the bundle;
- host profile id matches `bundle.json`;
- host profile Host ABI satisfies the airpkg Host ABI requirement;
- host profile supports required capabilities and host imports recorded in the
  airpkg artifact;
- target id is compatible with the selected host profile or explicitly marked as
  development-only.

Host profile compatibility does not add Host ABI imports and does not execute
host code.

## Build-Time / Runtime Boundary

Bundle runtime metadata must not require:

- Node;
- npm install;
- Python;
- source AIR repo;
- Codex;
- build scripts;
- local absolute paths.

Build tools may exist in the source repository and CI, but they must not be
encoded as runtime requirements in `bundle.json` or `airpkg.json`.

See [Build-Time vs Runtime Boundary](../BUILD_RUNTIME_BOUNDARY.md).

## Determinism Rules

- no timestamps;
- no absolute paths;
- deterministic JSON key ordering;
- deterministic file list ordering;
- stable `/` path separators;
- stable hashes;
- target-specific output must not depend on current user, machine path, locale,
  branch name, or temporary directory.

## Command Candidates

Preferred command shapes:

```sh
airc bundle <airpkg> --target web-dev -o dist/web-dev
airc bundle <airpkg> --target native-dev -o dist/native-dev
airc check-bundle <dir> --json
```

Implemented first-slice command shapes:

```sh
node bin/airc.js bundle <airpkg-file> --target web-dev -o dist/web-dev
node bin/airc.js bundle <airpkg-file> --target native-dev -o dist/native-dev
node bin/airc.js check-bundle dist/web-dev --json
```

Alternative if implementation needs the source package to locate linked output
or resources in the first slice:

```sh
airc bundle <package-dir> --airpkg dist/app.airpkg.json --target web-dev -o dist/web-dev
```

The preferred long-term input is an `airpkg` artifact, not a source package.

## Acceptance Tests

- `web-dev` bundle created from a valid `airpkg`;
- `native-dev` bundle created from a valid `airpkg`;
- `check-bundle` passes on valid bundles;
- missing `airpkg.json` fails;
- missing linked output fails when declared;
- linked output hash mismatch fails;
- missing copied resource fails;
- absolute path in `bundle.json` fails;
- timestamp-like field in `bundle.json` fails;
- runtime requirement on Node, npm install, Python, source repo, Codex, or build
  scripts fails;
- deterministic `bundle.json` across repeated builds;
- AIR ABI remains `0.10`;
- Host ABI remains `0.10`.

## Risks

- development folders may be mistaken for complete product bundles;
- referenced resources may couple bundles back to the source checkout;
- target-specific host conveniences may leak into AIR Core semantics;
- demos may try to make their asset/tooling needs Core bundle requirements.

## Open Questions

- Should `bundle` accept only `airpkg` artifacts in v0.17, or also source
  package directories as a convenience?
- Should copied resources be required for both targets in P0?
- Should `web-dev` include a static host shell in v0.17, or only metadata and
  runtime artifacts?
- Should `native-dev` include a host executable in v0.17, or only metadata and
  runtime artifacts?
