# RFC: v0.15 Diagnostic Code Registry

Status: accepted v0.15 first slice

Target milestone: AIR v0.15

## Summary

AIR needs stable diagnostic codes for anti-slop reports, reviewPolicy gates, and
LSP-lite/editor repair loops. v0.15 introduces the first implemented registry
slice of machine-readable diagnostic codes without changing AIR Core semantics,
Host ABI, or package runtime behavior.

The registry gives AI/Codex tools a stable surface for repair loops:

- identify the same issue across text and JSON reports;
- gate selected warnings through package `reviewPolicy`;
- map diagnostics to editor squiggles and quick-fix prompts;
- avoid relying on brittle human-readable message text.

## Non-goals

- No new Host ABI.
- No new Core syntax.
- No demo-specific diagnostic names.
- No automatic rewrites.
- No LLM API calls.
- No claim that every warning is a verifier error.

## Code Format

Diagnostic codes use:

```text
air.<domain>.<name>
```

Rules:

- lowercase ASCII only;
- domains and names use `snake_case`;
- codes are stable once released;
- message text may change, but code meaning must not drift;
- removed codes must remain documented as deprecated rather than reused.

Allowed domains:

| Domain | Meaning |
| --- | --- |
| `parser` | Syntax and parse-shape diagnostics. |
| `verifier` | Type, capability, memory, contract, and semantic verifier diagnostics. |
| `package` | Package graph, package metadata, authority, and package-check diagnostics. |
| `review` | Anti-slop and structural review diagnostics. |
| `generated` | Generated artifact freshness, traceability, and determinism diagnostics. |
| `manifest` | Resource/manifest schema, path, ID, and consistency diagnostics. |
| `profile` | Host profile compatibility diagnostics. |
| `surface` | Allowed/rejected surface and hallucinated API diagnostics. |
| `trend` | Historical/report trend diagnostics across runs. |

## Diagnostic Shape

JSON reports should use this common shape where practical:

```json
{
  "code": "air.review.large_function",
  "category": "review",
  "severity": "warn",
  "gateable": true,
  "message": "function update has 120 statements",
  "repairHint": "split the function into package-local helpers while preserving explicit capabilities",
  "file": "main.air",
  "module": "main.air",
  "range": { "startLine": 12, "startColumn": 1, "endLine": 90, "endColumn": 1 },
  "fields": {
    "function": "update",
    "statements": 120,
    "threshold": 80
  }
}
```

Required top-level fields:

- `code`;
- `category`;
- `severity`;
- `gateable`;
- `message`;
- `repairHint` when a useful repair exists.

Source location fields are optional only when unavailable. Reports should prefer
`file`, `module`, and `range` for editor/LSP-lite integration.

Severity values:

- `info`;
- `warn`;
- `fail`.

`fail` means the current checker rejects the package/module under the selected
mode or policy. `warn` means the package can remain valid unless a package
policy promotes the code to a failure.

## Gateability

`gateable: true` means package `reviewPolicy` or release gates may promote the
diagnostic to a failure.

`gateable: false` means the diagnostic is informational or already enforced by
a lower-level parser/verifier/package-check rule. A non-gateable diagnostic may
still appear in reports for explanation and repair.

## Repair Hint Style

Repair hints must be:

- imperative or direct;
- layer-aware;
- free of demo vocabulary;
- specific enough for an AI repair loop;
- careful not to suggest forbidden features.

Good examples:

- `split the function into package-local helpers while preserving explicit capabilities`;
- `regenerate generated handles from the package manifest`;
- `vendor the kit as a package-local import; do not use std.* for host wrappers`.

Bad examples:

- `make it cleaner`;
- `use a game engine pattern`;
- `add gfx.draw_sprite_transform`;
- `ignore this warning`.

## Text Report Mapping

Human-readable reports should include diagnostic codes next to message text:

```text
WARN air.review.large_function main.air update: function has 120 statements
```

Text output may be compact, but JSON output is the source of truth for repair
loops and LSP-lite.

## reviewPolicy Schema Integration

v0.15 `reviewPolicy` may use diagnostic codes directly while preserving legacy
camelCase gate aliases during migration:

```json
{
  "reviewPolicy": {
    "schemaVersion": "0.15",
    "pathClassOrder": ["authored", "generated", "vendor"],
    "gates": {
      "air.review.large_entry": "fail",
      "largeFunctionStatements": "warn"
    },
    "waivers": [
      {
        "code": "air.review.large_function",
        "file": "generated/**/*.air",
        "reason": "generated table module is intentionally dense",
        "expires": "2026-12-31"
      }
    ]
  }
}
```

Rules:

- Gates may use stable `air.<domain>.<name>` codes or legacy aliases such as
  `largeEntryFunction`.
- Path classification is deterministic. More specific path patterns win; equal
  specificity is reported as an ambiguity and resolved by `pathClassOrder` or
  built-in order.
- Waivers apply only to `air.review.*` diagnostics and must include `reason`.
- Parser, verifier, capability, Host ABI, package/profile, generated, and
  resource hard errors cannot be waived by review policy.
- Expired waivers are visible in reports. They become failures only in
  release-candidate checks.

## Implemented v0.15 First Slice

The active v0.15 implementation emits canonical codes through package-check,
report, reviewPolicy, trend baseline comparison, generated/manifest diagnostics,
and LSP-lite JSON diagnostics. Parser and verifier diagnostics use coarse
compatibility wrapper codes in this slice.

## Acceptance Tests

v0.15 implementation should add tests that prove:

- each registered code can be emitted in JSON shape when the corresponding
  diagnostic exists;
- package `reviewPolicy` can gate gateable review/generated/manifest codes;
- non-gateable package contract failures remain failures independent of style
  policy;
- text output includes codes without relying on message text;
- LSP-lite/editor adapters can map `code`, `file`, `range`, and `repairHint`
  deterministically;
- deprecated or unknown codes are rejected by diagnostic-registry tests.

## Future Questions

These questions are not blockers for v0.15 RC. Treat them as future/v0.16+
registry refinement work.

- Should parser/verifier legacy errors be migrated into the same registry in
  v0.15, or should v0.15 focus first on review/package/report diagnostics?
- Should `severity` include `error`, or should AIR keep `fail` to match
  package-check status language?
- Should trend diagnostics be stored in package reports, external CI history,
  or both?
