# RFC: v0.33 Verifier Safety Deepening

Status: proposed for v0.33 P0

Milestone: v0.33

Layer: verifier safety evidence / deterministic fuzz scaffold / review surface

## Purpose

v0.33 expands the deterministic `fuzz-safety` scaffold and makes verifier
safety coverage more visible to reviewers. The goal is to catch verifier,
lowering, import, signature, bounds, and forbidden-surface regressions in a
small supported subset.

This RFC does not claim formal verification.

## Current Baseline

v0.32 added:

- [Verifier Safety Contract](../VERIFIER_SAFETY_CONTRACT.md);
- deterministic `fuzz-safety` command;
- tiny generated valid and invalid module cases;
- checks for unexpected traps, imports, signatures, and bounds mismatches;
- explicit non-goals for business correctness, host correctness, performance
  optimality, and malicious host protection.

v0.33 deepens coverage without expanding language authority.

The first v0.33 expansion adds deterministic families for:

- arithmetic valid and invalid type cases;
- fixed state valid get/set/len-style usage and static out-of-bounds rejection;
- bounded `output.emit` valid static ID cases and invalid dynamic ID rejection;
- structured IO valid package-check cases;
- structured IO invalid JSON/object/string field cases;
- generated handle constant cases;
- generated structured IO handle missing/stale metadata rejection.

## P0 Fuzz/Safety Domains

The deterministic scaffold should expand coverage for:

- small arithmetic;
- fixed state get/set and bounds behavior;
- bounded `output.emit`;
- structured IO schema cases;
- generated handles.

The scaffold must remain seed-driven and deterministic. It must not depend on
wall-clock time, network, live providers, API keys, local environment data, or
nondeterministic host behavior.

## Valid Case Expectations

Generated valid cases should:

- verify successfully;
- pass package-check when package metadata is present;
- lower to Wasm if the subset supports lowering;
- instantiate with the mock host when host imports are required;
- execute a simple exported function;
- avoid unexpected traps;
- avoid unexpected imports;
- avoid signature mismatches;
- avoid bounds mismatches.

Expected fail-fast behavior must be documented. A deterministic declared trap is
not the same as an unexpected verifier/lowering mismatch.

## Invalid Case Expectations

Generated invalid cases should be rejected before lowering when they violate:

- undeclared host import policy;
- fixed state bounds;
- structured IO bounds or schema shape;
- output contract IDs;
- dynamic `output_id` policy;
- runtime JSON/object payload policy;
- host authority boundaries.

Invalid cases should produce stable diagnostics where possible.

## Verifier Safety Coverage Report

v0.33 should add a reviewable safety coverage report that summarizes:

- generated case count;
- valid case pass/fail;
- invalid case rejection pass/fail;
- exercised feature categories;
- exercised diagnostic codes;
- unexpected trap/import/signature/bounds mismatch counts;
- minimized or logged failing case reference when feasible;
- limitations.

The report must be deterministic, path-normalized, and free of raw private
payloads.

The implemented report shape includes:

- `seed`;
- `cases`;
- top-level `passed`, `failed`, and `skipped`;
- `families` with total/pass/fail/skip and valid/invalid counts;
- `diagnostics`;
- `minimizedCase`, currently a stable failing case reference when available or
  `null` when all cases pass.

## No Formal Verification Claim

The safety scaffold provides regression evidence only. It does not prove:

- business correctness;
- recommendation quality;
- host policy correctness;
- performance optimality;
- protection against malicious hosts;
- full semantic equivalence across all AIR programs.

Docs and reports must not describe fuzz coverage as formal verification.

## Structured IO Boundary

Structured IO coverage remains limited to the accepted first slice:

- scalar-only;
- fixed-shape;
- bounded rows;
- schemas as source of truth;
- generated bindings as derived artifacts;
- metadata/report/evidence visibility without raw row values by default.

The scaffold must not add runtime JSON, dynamic objects, nested records,
strings, host object handles, tablegroups syntax, or declared pools.

## Host ABI Boundary

Host ABI `0.11` remains limited to bounded `output.emit`. v0.33 safety work
must not add host imports, output event surfaces, or host authority.

Host ABI `0.10` remains the default/baseline compatibility target for packages
that do not use `output.emit`.

## P1 Planning

P1 may plan:

- deeper fuzz corpus;
- parser roundtrip fuzz;
- coverage trend comparison;
- safety report pretty-printing;
- AI repair transcript viewer integration.

P1 must not add nondeterministic CI, live AI calls, automatic code actions,
automatic repair, or new language syntax.

## Kill Criteria

Stop or split into a separate architecture review if the work requires:

- new parser syntax;
- verifier semantics beyond accepted surfaces;
- lowering changes that affect AIR ABI;
- host imports or Host ABI expansion;
- runtime JSON/object model;
- tablegroups implementation;
- declared pools;
- hidden host authority;
- formal verification claims unsupported by the implementation.

## Acceptance Criteria

Before v0.33 closes, verifier safety deepening should provide:

- expanded deterministic fuzz/safety domains;
- generated valid and invalid case coverage;
- stable JSON report shape;
- explicit unexpected trap/import/signature/bounds mismatch counts;
- stable diagnostics for high-value invalid cases where available;
- documentation of limitations and non-guarantees.

## ABI Impact

No AIR ABI change is expected.

No Host ABI change is expected.

Verifier safety evidence exercises existing verifier/package/lowering surfaces
and must not create new executable or host compatibility contracts.
