# AIR v0.16 RFC: Target Bundles

Status: skeleton RFC

Target milestone: v0.16

## Purpose

Define how verified AIR package artifacts become target host bundles without
pretending AIR compiles complete applications directly into native binaries.

Pipeline:

```text
AIR source -> verified AIR package -> package artifact -> target host bundle -> shipped product
```

## Scope

- target bundle vocabulary and boundaries;
- build-time tool allowance vs runtime product requirements;
- web/native-dev skeleton expectations;
- relationship between package artifacts, host implementations, and declared
  resources.

## Non-goals

- No full native installer implementation.
- No Steam packaging.
- No Unity/Godot adapter implementation.
- No package registry.
- No hidden host gameplay/presentation authority.
- No Host ABI changes.
- No game-specific bundle fields.

## Build-Time / Runtime Boundary

Build-time tooling may use Node, npm, Python, CI, Codex, asset generation,
review bundle tooling, or transitional generators.

Runtime target bundles must not require Node, npm install, Python, Codex, source
AIR repo checkout, or build scripts.

Target bundles bind an AIR package artifact to a target host implementation and
declared resources. Hosts implement declared profile capabilities; they do not
invent undeclared semantics from assets, filenames, debug metrics, or demo
state.

## ABI Impact

Target bundle metadata does not automatically change AIR ABI or Host ABI.

AIR ABI review is required if a target bundle contract changes executable
entrypoint semantics, import/export layout, memory/data representation, or
runtime-required metadata.

Host ABI review is required only for accepted new/changed host imports or
host-visible event/output contracts.

## Acceptance Tests

- RFC defines expected bundle inputs and outputs;
- bundle metadata distinguishes build-time tools from runtime requirements;
- runtime requirements do not include source repo tools;
- host profile compatibility remains visible;
- linked build status remains explicit and cannot be inferred silently.

## Risks

- target bundle skeletons may be mistaken for complete product bundling;
- host-specific conveniences may leak into Core package semantics;
- demo adoption bundles may accidentally become Core release authority.

## Deferred Items

- web dist implementation;
- native-dev folder bundle implementation;
- macOS `.app`, Linux tar/AppImage, and Windows folder/exe;
- installer/signing/notarization policy;
- public demo/adoption bundle.
