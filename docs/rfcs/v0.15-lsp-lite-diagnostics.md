# AIR v0.15 RFC: LSP-lite Diagnostics

Status: accepted v0.15 first slice
Target milestone: v0.15
Scope: CLI diagnostic envelope and editor-friendly JSON output

## Purpose

AIR needs editor and AI-repair integrations before a full JSON-RPC language
server exists. v0.15 should define a small deterministic diagnostics command
that exposes parser, verifier, package, review, generated-artifact, manifest,
and profile diagnostics in one canonical JSON shape.

This RFC defines the active v0.15 LSP-lite slice: CLI JSON diagnostics via
`airc check <file-or-package> --lsp-json`. It does not define or implement a
full JSON-RPC LSP server.

## Non-goals

- No JSON-RPC LSP server.
- No background workspace indexer.
- No completions, hover, go-to-definition, or incremental workspace
  diagnostics.
- No Host ABI changes.
- No new AIR syntax.
- No editor-specific protocol extensions.
- No hidden rewrite or autofix engine.
- No runtime package execution.

## Command

```sh
airc check <file-or-package> --lsp-json
```

Behavior:

- If `<file-or-package>` is an `.air` file, `kind` is `file`.
- If `<file-or-package>` is a package directory containing
  `air.package.json`, `kind` is `package`.
- Output is deterministic JSON.
- Exit code should follow current AIR command policy:
  - `0` when status is `pass` or `warn`;
  - non-zero when status is `fail`.
- The command should not require linked Wasm output.
- Package checks should use authored module graph diagnostics, not flattened
  generated output as the primary review source.

## Output Envelope

```json
{
  "schemaVersion": "0.15",
  "target": "examples/policy_audit_package",
  "kind": "package",
  "status": "pass",
  "diagnostics": []
}
```

Fields:

| Field | Required | Meaning |
| --- | --- | --- |
| `schemaVersion` | yes | LSP-lite diagnostics schema version. |
| `target` | yes | Input path exactly as checked or normalized package path. |
| `kind` | yes | `file` or `package`. |
| `status` | yes | `pass`, `warn`, or `fail`. |
| `diagnostics` | yes | Stable ordered diagnostic list. |

## Diagnostic Shape

Each diagnostic uses the normalized v0.15 diagnostic code registry shape:

```json
{
  "file": "src/main.air",
  "line": 12,
  "col": 3,
  "endLine": 12,
  "endCol": 28,
  "severity": "warn",
  "code": "air.review.large_function",
  "message": "function update has 120 statements",
  "repairHint": "split the function into smaller helpers or package-local modules",
  "source": "ai-review",
  "category": "review",
  "pathClass": "authored",
  "gateAction": "warn",
  "packageStatusImpact": "warn",
  "module": "src/main.air",
  "symbol": "update",
  "metric": "statements",
  "value": 120,
  "threshold": 80,
  "fields": {
    "baseline": 80,
    "delta": 40
  },
  "related": []
}
```

Required keys must be present even when values are unknown. Unknown locations use
`null`, not omitted fields.

| Field | Required | Meaning |
| --- | --- | --- |
| `file` | yes | Package-local file path or absolute/relative file input. May be `null` for package-level diagnostics. |
| `line` | yes | 1-based start line, or `null`. |
| `col` | yes | 1-based start column, or `null`. |
| `endLine` | yes | 1-based end line, or `null`. |
| `endCol` | yes | 1-based end column, or `null`. |
| `severity` | yes | `info`, `warn`, or `fail`. |
| `code` | yes | Stable code such as `air.verifier.type_mismatch`. |
| `message` | yes | Human-readable diagnostic summary. |
| `repairHint` | yes | Repair guidance, or `null` when none is available. |
| `source` | yes | Producer such as `parser`, `verifier`, `package-check`, `ai-review`, or `manifest`. |
| `category` | yes | Registry domain: `parser`, `verifier`, `package`, `review`, `generated`, `manifest`, `profile`, `surface`, or `trend`. |
| `pathClass` | yes | `authored`, `generated`, `vendor`, or `null`. |
| `gateAction` | yes | `warn`, `fail`, `off`, or `null`. |
| `packageStatusImpact` | yes | `none`, `warn`, or `fail`. |
| `module` | yes | AIR module path/name when known, else `null`. |
| `symbol` | yes | Function/global/table/import symbol when known, else `null`. |
| `metric` | yes | Measured metric name for budget diagnostics, else `null`. |
| `value` | yes | Measured value for budget diagnostics, else `null`. |
| `threshold` | yes | Configured threshold for budget diagnostics, else `null`. |
| `fields` | yes | Deterministic JSON object containing structured producer-specific data, or `{}`. |
| `related` | yes | Stable list of related locations or context objects. |

`fields` must be JSON-serializable and deterministic. Producers should use it
for structured repair data that does not fit the common top-level fields, such
as waiver metadata, trend `baseline`/`delta`, or
`fields.diagnosticCode` for diagnostic-count trend comparisons.

## Supported Diagnostic Sources

### Parser Diagnostics

Parser failures should return `kind: "file"` for direct file checks and
`kind: "package"` for package checks. Range information should be included when
the parser can identify it. Parser diagnostics are hard failures and cannot be
waived by `reviewPolicy`.

Example categories:

- invalid token;
- malformed instruction;
- invalid declaration;
- unsupported syntax.

### Verifier Diagnostics

Verifier diagnostics include type, capability, memory, effect, contract, table,
and Host ABI signature errors. They are hard failures and cannot be waived by
`reviewPolicy`.

Examples:

- type mismatch;
- undeclared capability for host import;
- unsupported host import;
- static table out-of-bounds;
- effect budget violation.

### Package-check Diagnostics

Package diagnostics cover package metadata, module graph, package/profile
compatibility, capability propagation, host import origins, and hidden authority.
Package-level diagnostics may have `file: null` when the issue is global.

Examples:

- unresolved import;
- private cross-module call;
- package/profile mismatch;
- hidden authority;
- linked Wasm deferred warning.

### reviewPolicy Diagnostics

Review diagnostics are advisory unless package `reviewPolicy` gates promote them
to warning or failure. These diagnostics may be waived only when their code is
under `air.review.*` and the waiver includes a reason.

Examples:

- large function;
- large entry/frame/main;
- repeated literal;
- select-chain-as-table;
- slot-family state;
- debug.metric event-bus smell.

### Generated Artifact Diagnostics

Generated artifact diagnostics report missing, stale, or untraced generated
files. They are package-check diagnostics, not style diagnostics, and cannot be
waived by `reviewPolicy`.

Examples:

- missing `generated/assets.air`;
- stale handle module;
- generated header references omitted generator.

### Manifest and Resource Diagnostics

Manifest/resource diagnostics report invalid active runtime manifest content.
They cannot be waived by `reviewPolicy`.

Examples:

- missing runtime resource path;
- forbidden runtime path such as `tmp_unused` or `assets_candidate`;
- manifest ID missing from AIR/generated data;
- unused manifest entry warning.

### Package-level Diagnostics Without File Range

Some diagnostics describe package-wide state:

- profile mismatch;
- linked Wasm deferred;
- graph complexity trend;
- ownership imbalance;
- generated artifact summary.

These should use:

```json
{
  "file": null,
  "line": null,
  "col": null,
  "endLine": null,
  "endCol": null
}
```

Do not invent fake file locations.

## Ordering

Diagnostics must be sorted deterministically:

1. severity impact: `fail`, then `warn`, then `info`;
2. `file`, with package-level `null` after file diagnostics;
3. `line`;
4. `col`;
5. `code`;
6. `message`.

The same input and policy must produce byte-stable JSON.

## Relationship to Diagnostic Registry

`airc check --lsp-json` must use the stable codes defined in
[v0.15 Diagnostic Code Registry](./v0.15-diagnostic-code-registry.md).

Legacy IDs may appear in internal reports during migration, but LSP-lite output
should prefer `code`.

## Relationship to reviewPolicy

For package targets:

- `reviewPolicy` thresholds and gates are applied before diagnostics are emitted.
- `gateAction` records the action selected by policy.
- `packageStatusImpact` records whether the diagnostic changes package status.
- `reviewPolicy` waivers are reflected in diagnostic fields or related metadata
  when the implementation supports waiver reporting.
- Hard parser/verifier/package/profile/generated/resource failures remain hard
  failures even if a waiver tries to match them.

## Acceptance Tests

Implementation should add tests for:

- file parser error produces LSP-lite envelope;
- file verifier error produces LSP-lite envelope;
- package graph error produces package diagnostics;
- reviewPolicy warning appears with code, threshold, and pathClass;
- generated artifact failure appears and cannot be waived;
- manifest missing resource appears;
- package-level profile mismatch has no fake file range;
- output is deterministic across repeated runs.

## Deferred

- Full JSON-RPC LSP server.
- VS Code extension.
- Completions.
- Hover.
- Go-to-definition.
- Incremental document updates.
- Workspace cache/index.
- Code actions/autofix protocol.
- Cross-package registry resolution.
