# RFC: v0.31 Bounded Structured IO

Status: proposed/planning

## Purpose

Define a safe architecture path for bounded structured input and output in AIR
without adding runtime JSON, dynamic objects, maps, ORM behavior, host object
handles, or raw host authority.

Real consumers need better ergonomics:

- FlowDesk needs bounded task/status/link/note summaries without dozens of
  scalar parameters;
- demos and simulations need bounded mutable/readback surfaces;
- lan-observer-air needs real read-only structured facts.

Those pressures are valid, but AIR must stay an AI-first verifier-enforced IR and
package contract. Host applications own rich objects, private payloads, and
authority. AIR receives minimized bounded scalar facts and produces bounded
scalar decisions or output intents.

This RFC is planning only. It does not change parser, verifier, lowering, AIR
ABI, Host ABI, host imports, structured IO runtime behavior, tablegroup syntax,
`output.emit`, generated artifacts, or demos.

## 1. Terminology

Bounded Structured IO is the umbrella term for schema-declared, fixed-shape,
bounded input/output metadata that lets tools and hosts present structured
records while AIR itself remains scalar, deterministic, and verifier-visible.

Bounded Structured IO is not:

- runtime JSON;
- dynamic object values;
- dynamic maps;
- object identity;
- host object handles;
- ORM/database modeling;
- raw host authority;
- raw private payload transport.

## 2. Model Split

The model split is mandatory. These terms must not collapse into one another:

| Model | Layer | Meaning | Not Allowed |
| --- | --- | --- | --- |
| Bounded scalar record | package metadata / future Core candidate | A fixed-shape schema-declared record with scalar fields only. | Runtime JSON, dynamic keys, nested objects, strings, host object handles. |
| Bounded rowset | package metadata/tooling | A fixed or bounded collection of bounded scalar records. | Dynamic collection semantics, AIR runtime JSON parsing, unbounded rows. |
| Tablegroup | future source ergonomics candidate | A possible syntax for related fixed rowsets/table-like facts. | Object model, methods, dynamic allocation, runtime collection identity. |
| Declared mutable pool / slot group | future PRO-gated Core candidate | A possible fixed-capacity mutable scalar slot family with declared bounds and verifier-visible ownership. | Dynamic entity objects, GC, maps, host object handles, tablegroup implementation by another name. |
| Generated host binding | generated host/tooling artifact | Host-owned helpers derived from schemas/contracts for scalar encoding, validation, and fixtures. | Semantic source of truth, hidden host imports, host object handles, AIR runtime behavior. |
| Output summary | report/evidence/review | Human/machine summary of bounded output intents. | Payload objects, output events, side-effect expansion, new Host ABI. |
| Command buffer | package metadata/conformance | Bounded scalar output intent records tied to Output Contracts. | Host execution guarantee, arbitrary payloads, dynamic output IDs. |
| `output.emit` | Host ABI `0.11` bounded first slice | Low-frequency bounded scalar output intent host import. | Payload objects, dynamic output IDs, `output.event`, Host ABI expansion. |

## 3. Bounded Scalar Record

A bounded scalar record is a fixed-shape record whose fields are declared by a
schema and whose values are scalar, privacy-minimized AIR values.

Allowed first-slice field classes:

- integer IDs;
- enum IDs;
- scalar handles that identify host-owned objects without granting access;
- flags;
- bounded scores;
- counters;
- booleans where already accepted by the surrounding schema;
- compact storage hints as metadata only where already accepted.

Rejected field classes:

- strings;
- raw URLs;
- private text;
- tokens;
- secrets;
- credentials;
- raw packet payloads;
- JSON values;
- object/map/any fields;
- dynamic keys;
- host object handles.

The record shape is declared by package metadata. AIR should not infer fields
from runtime payloads.

## 4. Fixed Rowset

A fixed rowset is a bounded collection of bounded scalar records. It is a
package metadata/tooling contract, not an AIR dynamic collection.

Current source-of-truth path:

- `factSchemas`;
- bounded rowset schema files with `kind: "air.boundedRowsetSchema"`;
- package-check/report/evidence metadata.

Rules:

- row count is fixed or statically bounded;
- columns are schema-declared;
- rows contain scalar minimized values only;
- host/test harness owns fixture decoding;
- AIR does not parse JSON at runtime;
- AIR does not receive arbitrary objects;
- AIR does not access dynamic keys.

## 5. Tablegroup Relationship

A tablegroup is a future source ergonomics candidate for referring to related
fixed rowsets or table-like facts. It is not an object, not a runtime collection,
and not a source of dynamic allocation.

Tablegroups must not gain methods, object behavior, identity, dynamic field
lookup, inheritance, mutation APIs, host handles, or ORM/database behavior. A
tablegroup is a possible naming and source ergonomics layer over fixed bounded
metadata, not a semantic object model.

If accepted later, tablegroups must be:

- fixed-size or statically bounded;
- scalar-only;
- backed by source-of-truth schemas or declarations;
- visible in verifier/report/evidence;
- unable to carry raw private data;
- unable to imply host authority.

v0.31 does not implement tablegroup syntax.

## 6. Declared Mutable Pools / Slot Groups

Declared mutable pools or slot groups are separate future pressure from
tablegroups. They may describe fixed-capacity mutable scalar slots in a future
PRO-gated milestone, but they are not part of bounded structured IO P0 and must
not be smuggled in through tablegroup metadata.

If accepted later, declared mutable pools must remain:

- fixed-capacity;
- scalar-only;
- verifier-visible;
- report-visible;
- free of dynamic entity objects, GC, maps, host object handles, and hidden host
  authority.

v0.31 does not implement declared mutable pools.

## 7. Bounded Structured Output

Bounded structured output is a review/tooling model for presenting related
bounded output intents as a structured summary.

Source-of-truth inputs:

- Output Contract manifests;
- command buffer schemas;
- bounded `output.emit` static output IDs;
- generated output handles as derived artifacts;
- verification evidence;
- conformance/replay reports;
- evidence reports.

Rules:

- no string/object/JSON payloads;
- no dynamic output IDs;
- no hidden host imports;
- no automatic host-side action execution;
- no `output.event`, `audio.event`, or `effect.event`;
- no Host ABI expansion.

Bounded structured output must not mean:

- `output.emit` payload objects;
- `output.event`;
- host side-effect expansion;
- Host ABI `0.12`;
- arbitrary output payload data;
- platform adapter execution.

The first slice output boundary remains:

- scalar IDs and handles;
- bounded rows/summaries as package metadata, evidence, and tooling contracts;
- Output Contracts as source of truth for output IDs/intents;
- host-owned rich execution and policy decisions.

## 8. Source of Truth

Generated artifacts must not become source of truth.

Source-of-truth surfaces:

- fact schemas and bounded rowset schemas for input facts;
- Output Contract manifests;
- command buffer schemas;
- AIR state declarations;
- package manifest metadata.

Derived surfaces:

- generated state handles;
- generated output handles;
- future generated host bindings;
- Markdown evidence reports;
- package diffs.

Derived artifacts must be deterministic, freshness-checked, and report-visible.
They must not become semantic source of truth, even if future generated bindings
make authoring easier.

## 9. Generated Host Bindings Model

Generated host bindings are host/tooling artifacts generated from source-of-
truth schemas and contracts. They may help host code encode/decode minimized
scalar facts, compare evidence, and prepare conformance fixtures.

They must not:

- add AIR runtime object semantics;
- add hidden compiler exports;
- add hidden host imports;
- add host object handles;
- grant authority;
- bypass package-check;
- bypass evidence/replay;
- become source of truth.

Host kits may contain domain-specific binding code. Core accepts only the
generalized metadata, validation, diagnostics, and evidence contracts.

## 10. First Slice Candidate for v0.32

The preferred v0.32 implementation candidate, if accepted, is package
metadata/tooling first:

- no parser syntax unless separately accepted;
- scalar-only fields;
- fixed-size schemas and fixed or bounded rows;
- generated host binding metadata;
- generated binding freshness validation;
- package report visibility;
- verification evidence visibility;
- package diff visibility;
- evidence report visibility;
- replay/conformance fixture visibility;
- LSP/package-check diagnostics for schema drift.

The candidate must not add runtime structured IO values, runtime JSON parsing,
dynamic object access, tablegroup syntax, Host ABI imports, or AIR ABI changes.

## 12. AIRON Tablegroup Pressure

AIRON adds specific tablegroup pressure for readonly authored level data:

- related scalar tables should be grouped by metadata or future source
  ergonomics;
- related tables must have equal declared lengths when indexed together;
- package-check should diagnose divergent related table lengths;
- index bounds should be package-check/verifier-visible before any runtime
  syntax is accepted;
- report/evidence should show tablegroup ownership, member tables, row bounds,
  and diagnostics.

AIRON platformer rules remain demo-local. Tablegroups must not become objects,
methods, gameplay entities, actor APIs, or dynamic collections. Declared mutable
pools are a separate future PRO-gated feature and are not part of tablegroup P0.

## 13. Report / Evidence / Diff / Replay Visibility

Package report should show, where available:

- rowset schema paths and hashes;
- record names and column summaries;
- max row counts;
- tablegroup ownership/member metadata if accepted later;
- privacy policy summaries;
- output contract names/IDs/channels;
- command buffer record shapes;
- generated binding freshness;
- diagnostics.

Verification evidence should show:

- fact schema and rowset fingerprints;
- output contract fingerprints;
- command buffer metadata;
- generated artifact status;
- diagnostics;
- ABI requirements.

Package diff should show:

- fact/rowset schema deltas;
- output contract deltas;
- command buffer deltas;
- generated binding freshness deltas;
- capability/effect/Host ABI deltas where relevant.

Evidence reports should summarize structured IO metadata without raw payloads.

Conformance/replay should compare deterministic scalar records and checksums,
not raw private data.

Conformance mismatch diagnostics should identify:

- row bound exceeded;
- missing required scalar field;
- undeclared field;
- forbidden private field;
- non-scalar field;
- dynamic key/object drift;
- output ID mismatch;
- output count mismatch;
- command buffer mismatch;
- generated binding freshness mismatch;
- tablegroup length mismatch;
- tablegroup bounds mismatch;
- source-of-truth mismatch.

Diagnostics should use stable codes where implementation later adds them. They
must not collapse structured IO failures into generic package-check failure when
a specific source exists.

## 14. Verifier and Package-Check Obligations

v0.31 defines obligations before implementation.

Package-check must reject:

- runtime JSON/object/map schema drift;
- unbounded rows;
- dynamic keys;
- string/object/json/any field types;
- raw URLs, private text, tokens, secrets, credentials, raw packet payloads;
- host object handle fields;
- generated artifact source-of-truth claims;
- schema/generated binding freshness mismatches;
- divergent related table lengths if tablegroup metadata is accepted later;
- output IDs not declared by Output Contracts;
- Host ABI expansion claims without decision record.

Future verifier obligations, if syntax is accepted later:

- fixed shape proof;
- fixed or bounded row count proof;
- scalar-only field proof;
- no pointer/slice/reference escape;
- loop/budget accounting for structured access;
- no host direct object access;
- deterministic bounds behavior;
- report-visible diagnostics.

## 15. Core vs Metadata vs Binding vs Host Kit

Core may define:

- scalar type rules;
- verifier-visible syntax only after accepted RFC;
- package-check validation;
- diagnostics;
- report/evidence/diff/replay fields;
- ABI decision gates.

Package metadata owns:

- rowset schema declarations;
- Output Contracts;
- command buffer schemas;
- state metadata policies;
- generated artifact declarations.

Generated bindings own:

- host-language helper code;
- deterministic scalar encoding/decoding;
- freshness metadata;
- ergonomic names.

Host kits own:

- domain adapters;
- rich object access;
- privacy filtering;
- real authority;
- policy execution.

## 16. ABI Impact

v0.31 planning does not require AIR ABI `0.11`.

AIR ABI remains `0.10` if a future first slice is package metadata, generated
host binding metadata, validation, reporting, evidence, diff, replay, and LSP
diagnostics only.

AIR ABI may need a bump only if a future implementation changes executable
runtime contracts, calling conventions, memory layout visible to hosts, package
entrypoint semantics, or host/runtime understanding of AIR executable metadata.

v0.31 planning does not require Host ABI changes.

Host ABI may need a bump only if a future implementation adds host imports,
changes host import signatures, changes host policy semantics, or standardizes
host-visible runtime structured IO behavior.

Generated host bindings and package metadata alone do not justify an ABI bump.

## 17. Explicit Rejections

This RFC rejects:

- arbitrary JSON runtime values;
- dynamic maps;
- object identity;
- nested runtime objects;
- string payloads;
- raw URLs;
- private text;
- secrets, tokens, and credentials;
- host object handles;
- ORM/database model;
- arbitrary field names at runtime;
- schema mutation at runtime;
- dynamic row counts without package bounds;
- demo-specific platformer concepts in Core;
- `output.emit` payload objects;
- `output.event`;
- host side-effect expansion;
- Host ABI `0.12`.

## 18. API Gates and Kill Criteria

The design must stop if it starts to require:

- runtime JSON;
- dynamic object fields;
- dynamic maps;
- object identity;
- host object handles;
- host seeing object handles;
- raw host authority;
- unbounded rows;
- dynamic row counts that package-check cannot bound;
- raw private payload fields;
- ORM/database semantics;
- tablegroups with methods or object behavior;
- structured output as arbitrary payload data;
- hidden compiler exports;
- generated artifacts as source of truth;
- generated bindings as source of truth;
- package-check unable to prove row bounds;
- demo-specific platformer concepts entering Core;
- Host ABI expansion;
- performance or product claims without evidence.

See [API Gates v0.31](../API_GATES_v0_31.md).

## 19. Acceptance Checklist for Future Implementation

Before any v0.32 implementation begins, the accepted design must provide:

- static schema shape;
- fixed bounds;
- scalar-only columns and fields;
- privacy classification;
- generated binding metadata shape;
- generated binding freshness validation;
- package report visibility;
- verification evidence visibility;
- package diff visibility;
- evidence report visibility;
- replay/conformance visibility;
- stable negative diagnostics for JSON/object drift;
- negative tests for runtime JSON, dynamic objects, maps, nested objects, raw
  URLs, private text, tokens, secrets, host object handles, unbounded rows, and
  generated-artifact source-of-truth drift;
- FlowDesk-style fixture;
- lan-observer-style fixture;
- AIRON level tablegroup sketch;
- AIR ABI decision;
- Host ABI decision.

## 20. P1 Fixture Pressure

FlowDesk-style task summary fixture:

- may describe tasks, statuses, links, and notes as minimized IDs/enums/scores;
- must not put raw note text, raw URLs, tokens, or private content in AIR.

lan-observer observation fixture:

- may describe read-only structured observations as minimized scalar fields;
- must not include raw packet payloads, raw host handles, network authority, or
  dynamic maps.

AIRON level tablegroup sketch:

- may sketch readonly authored level data as scalar-only bounded tablegroup
  metadata;
- must not implement tablegroup syntax, declared mutable pools, platformer APIs,
  asset slicing, Canvas/Vite/browser behavior, or demo-specific Core helpers.

Demo pressure:

- may inform examples/kits;
- must not introduce demo-specific Core APIs.
