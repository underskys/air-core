# RFC: v0.14 Resource / Manifest Consistency

Status: draft

Target milestone: AIR v0.14

## Summary

AIR packages need deterministic consistency checks between AIR-authored semantic
IDs and resource manifests.

Core principle:

- AIR owns semantic IDs, state, rules, capability usage, and module graph.
- Manifests bind semantic IDs to host resources.
- Hosts load, render, play, or execute only declared resources through declared
  IDs and capabilities.

Resource manifests are metadata. They must not become hidden program semantics.

## Goals

- Keep semantic meaning in verified AIR modules or validated package contracts.
- Validate that AIR-referenced IDs exist in manifests.
- Validate that manifest-declared IDs are used or intentionally unused.
- Fail missing runtime resource paths.
- Reject candidate/quarantine/tmp paths as runtime references.
- Prevent hosts from inventing gameplay, policy, or operational semantics from
  resource names.
- Generalize the model beyond visual/game assets.

## Non-goals

- No new Host ABI.
- No asset downloader.
- No package registry.
- No remote resource loading semantics.
- No host object handles.
- No hidden host authority from manifest entries.
- No JSON gameplay or workflow schema as the primary verified program path.
- No demo-specific material, sprite, terrain, actor, or level semantics in Core.

## Boundary

AIR owns:

- semantic IDs;
- state;
- rules;
- capability use;
- module graph;
- generated handle/data modules;
- deterministic reports.

Manifests bind IDs to host-owned resources:

- texture paths;
- sprite paths;
- audio paths;
- material mappings;
- shader/model paths;
- host profiles;
- package metadata;
- deployment/resource metadata.

Hosts own:

- loading;
- decoding;
- rendering;
- playback;
- platform policy;
- missing-resource fallback behavior when explicitly declared.

Hosts must not infer behavior from names such as `boss_theme`, `death_zone`,
`production_secret`, or `deploy_step_7` unless AIR/package contracts declare the
corresponding semantics and capabilities.

## Valid Manifest Uses

JSON/resource manifests remain valid for host resource binding.

Examples:

```json
{
  "assets": {
    "textures": {
      "checker": {
        "path": "assets/textures/checker.png"
      }
    },
    "audioSfx": {
      "notify": {
        "path": "assets/audio/notify.wav"
      }
    },
    "materials": {
      "basic_unlit": {
        "kind": "unlit",
        "texture": "checker"
      }
    }
  }
}
```

This binds IDs to resources. It does not grant graphics or audio authority by
itself.

## Generic Use Cases

The model applies beyond games:

- service IDs bound to dashboard labels or icons;
- network endpoint IDs bound to declared endpoint metadata;
- policy IDs bound to documentation or audit report labels;
- deployment target IDs bound to environment names;
- secret scope IDs bound to host-owned secret providers;
- CI step IDs bound to display names or log collection rules;
- UI/dashboard config IDs bound to resources and presentation metadata.

## Required Package-check Validation

### AIR IDs Referenced In Manifests Exist

When a manifest references an AIR-owned ID, package-check should verify that the
ID exists in the AIR package surface.

Acceptable AIR sources:

- named constants;
- enum-like integer IDs;
- generated handle modules;
- generated data modules;
- static tables where the package contract defines the ID set.

Failure example:

```json
{
  "materials": {
    "unknown_material": {
      "texture": "checker"
    }
  }
}
```

If AIR has no `unknown_material` handle or ID, package-check should fail.

### Manifest IDs Referenced By AIR Exist

If AIR references a manifest-backed ID, package-check should verify that the
manifest declares it.

Failure examples:

- AIR calls a generated handle function that is stale and no longer maps to a
  manifest entry;
- AIR static data references an ID not present in the active manifest;
- package generated data is missing or stale.

### Missing Runtime Resource Paths Fail

Required resource paths must exist.

Missing optional resources may warn only when an explicit fallback policy exists.
Fallbacks must be declared, not silently selected.

### Candidate / Quarantine / Tmp Paths Are Not Runtime References

Runtime manifests must not reference paths that indicate non-runtime or
transitional asset state.

Rejected path fragments:

- `tmp_unused`;
- `assets_candidate`;
- `graphics_bundles`;
- `quarantine`;
- `old_bundles`;
- `assets_tmp_unused_previous`;
- `references/full_pose`.

These paths may exist in source repositories or review archives, but not as
active runtime references.

### Unused Manifest Entries Warn

Unused manifest entries should warn, not fail by default.

Package policies may promote unused entries to failure for release builds.

### Host Cannot Invent Semantics From Resource Names

Host code must not treat resource names as behavior rules.

Rejected examples:

- play audio because the asset id contains `shoot`;
- create collision because a texture id contains `wall`;
- change deployment behavior because an endpoint id contains `prod`;
- grant secret access because a manifest key contains `admin`.

Semantics require AIR/package declarations and capability/profile support.

## Report Requirements

Package reports should include:

- manifest IDs;
- AIR IDs;
- matched AIR-to-manifest bindings;
- missing AIR IDs;
- missing manifest IDs;
- missing resource paths;
- forbidden runtime path references;
- unused manifest entries;
- fallback behavior;
- generated artifact freshness status;
- capability requirements related to resource use.

JSON output must be deterministic.

## Interaction With Capabilities

Assets do not grant authority.

Examples:

- an audio file does not grant audio playback authority;
- a texture does not grant graphics capability;
- an endpoint manifest does not grant network capability;
- a secret scope manifest does not grant filesystem or secret access.

Capability use remains controlled by AIR capabilities, Host ABI imports, package
metadata, and host profiles.

## Acceptance Tests

- AIR references manifest ID: pass when manifest declares it.
- AIR references missing manifest ID: fail.
- Manifest references missing AIR ID: fail when the manifest requires AIR-owned
  ID consistency.
- Missing required file path: fail.
- Missing optional file with explicit fallback: warn.
- Runtime manifest references `tmp_unused` or `quarantine`: fail.
- Unused manifest entry: warn.
- Audio asset exists but no audio capability/import: no playback authority is
  granted.
- JSON report ordering is deterministic.

## Recommendation

Implement this as package-check/report validation over active package manifests
and generated handle/data modules. Keep JSON manifests as resource metadata and
keep semantic behavior in AIR-authored modules or explicitly validated package
contracts.
