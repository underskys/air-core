# AIR v0.16 RFC: Event and Output Contract

Status: boundary RFC

Target milestone: v0.16

## Purpose

Continue the generic event/output boundary design without implementing a new
Host ABI in v0.16 P0. Events/outputs are capability-gated host-visible
contracts, not game-specific effects.

Examples include:

- visual effects;
- audio events;
- alerts;
- notifications;
- pipeline outputs;
- DevOps action requests, alerts, audit events, and pipeline notifications;
- UI/dashboard events.

The purpose is to make host-visible outputs explicit, declared, inspectable, and
profile-gated. The purpose is not to add a game effects system.

## Scope

- event/output vocabulary;
- capability and manifest boundary expectations;
- report/package-check visibility requirements;
- rejection of debug metrics as an event bus;
- Host ABI decision criteria for a future candidate.

## Contract Constraints

A future event/output is an AIR-declared host-visible contract. It is not a
debug log, implicit state convention, or demo-side shortcut.

A future event/output contract must be:

- explicit in AIR package metadata, manifests, or accepted source contracts;
- capability-gated;
- manifest-backed by stable IDs where resources or presentation metadata are
  involved;
- host-visible through an accepted Host ABI import or equivalent declared host
  surface;
- profile-gated;
- visible in package-check;
- visible in reports;
- conformance-testable;
- explicit about which host executes which declared output.

The host may execute declared outputs. The host must not infer output semantics
from:

- `debug.metric`;
- unrelated AIR state;
- resource filenames;
- demo conventions;
- TypeScript/native side channels;
- hidden host-owned gameplay state.

`debug.metric` remains diagnostics-only. It is not an event bus, effect bus,
audio bus, alert channel, or gameplay command channel.

Event-like `debug.metric` usage is an anti-slop diagnostic. Packages may choose
to fail it through `reviewPolicy`. Hosts must still treat `debug.metric` as
diagnostic telemetry only even if old demos or generated code attempt to encode
semantic actions through metric IDs.

## Manifest-Backed Event IDs

A future output-events manifest should define stable semantic IDs before any
host-visible output can be emitted. This section defines the expected manifest
model for future promotion. v0.16 does not implement this manifest schema unless
explicitly added as a tooling-only draft.

The manifest shape is expected to include:

- numeric `id` values;
- stable human-readable `name` values;
- `channel` names such as `visual`, `audio`, `alert`, `notification`,
  `pipeline`, or `dashboard`;
- required capabilities;
- scalar argument schema for each event;
- resource bindings where applicable, such as texture, audio, icon, template,
  or dashboard widget references;
- optional profile constraints.

IDs are semantic package contracts. Manifests may bind those IDs to host
resources, but hosts must not invent semantics from filenames or resource
paths. Package-check should reject or warn on manifest/source mismatches before
any Host ABI promotion.

## Output-Events Manifest Draft

This manifest schema is a draft/tooling-only model. It does not add Host ABI,
does not implement `output.emit`, `output.event`, or `audio.event`, and does not
allow AIR modules to emit events until an accepted Host ABI exists.

Expected shape:

```json
{
  "schemaVersion": "0.16-draft",
  "events": [
    {
      "id": 17,
      "name": "policy.violation.alert",
      "channel": "alert",
      "capability": "notify",
      "args": [
        { "name": "policyId", "type": "i32" },
        { "name": "subjectId", "type": "i32" }
      ],
      "resources": [
        { "kind": "icon", "id": "policy-alert" }
      ],
      "profileConstraints": {
        "profiles": ["cli", "browser-webgpu"]
      }
    }
  ]
}
```

Fields:

- `schemaVersion`: manifest schema marker;
- `events[]`: declared semantic event IDs;
- `event.id`: stable numeric ID;
- `event.name`: stable package-visible name;
- `event.channel`: declared output channel;
- `event.capability`: required capability for the event;
- `event.args[]`: scalar argument schema, ordered as emitted;
- `event.resources[]`: optional manifest/resource bindings;
- `event.profileConstraints`: optional profile restrictions.

Draft validation rules:

- duplicate event IDs fail;
- duplicate event names fail;
- unknown channels fail unless explicitly marked experimental by the manifest
  schema/profile policy;
- missing required capability fails once the manifest is linked to
  package-check;
- missing resources fail if `event.resources[]` declares them;
- unused events warn only when AIR/report usage data exists.

Generated handles for output events are future work. The draft manifest is only
an inspectable contract shape until a Host ABI candidate is accepted.

## Profile Support

Profiles must explicitly declare supported event/output channels and imports.
Unsupported channels or imports must fail package-check with deterministic,
machine-readable diagnostics. A profile that supports visual outputs does not
implicitly support audio, DevOps action requests, alerts, or dashboard outputs.

Profile support must be visible in surface reports so AI/Codex generation can
avoid inventing unsupported event surfaces.

## Candidate ABI Shape

A possible future generic Host ABI import is:

```text
output.emit(channel:i32, id:i32, a0:i32, a1:i32, a2:i32, a3:i32, flags:i32)
```

This shape is preferred over early domain-specific imports because it keeps the
Core contract generic while allowing manifest/profile layers to define channel
meaning. It is not implemented in v0.16.

The first Host ABI candidate, if promoted later, must remain scalar-only: no
strings, dynamic payload maps, binary blobs, host object handles, or runtime
object payloads.

Alternatives remain open:

- `audio.event` is narrower and risks promoting one domain before the generic
  output boundary is proven;
- `effect.event` is similarly visual/game-biased;
- domain-specific imports can be clearer for mature domains but should come
  after manifest, report, profile, and conformance gates prove the generic
  requirement.

Conclusion for v0.16: RFC only. Host ABI remains `0.10`. Host ABI `0.11` is a
candidate only if a new output import is accepted through RFC, spec, profiles,
package-check, and tests.

## Non-goals

- No `audio.event` implementation.
- No `effect.event` implementation.
- No generic `output.emit` / `output.event` Host ABI implementation in v0.16.
- No `debug.metric` event bus.
- No game-specific `draw_actor`.
- No game-specific `draw_contra_enemy`.
- No game-specific water/platformer APIs.
- No demo-specific event APIs.
- No hidden host gameplay authority.
- No dynamic maps, GC, reflection, runtime imports, or remote imports.
- No host object handles.
- No voxel-specific Core APIs.

## Build-Time / Runtime Boundary

AIR packages should declare event/output authority explicitly. Manifests may bind
semantic event IDs to host resources or presentation metadata when an accepted
contract exists.

Output events may describe action requests, but v0.16 does not define automatic
host-side action execution. Hosts may execute declared events/outputs only
through declared capabilities and accepted future contracts. Hosts must not
infer gameplay, effects, audio, alerts, or actions from unrelated AIR state,
asset names, debug metrics, or demo conventions.

## ABI Impact

v0.16 status:

- RFC only;
- no new host imports;
- no Host ABI bump.

A future event/output Host ABI candidate requires:

- accepted RFC;
- evidence from at least two domains:
  - one interactive/game-like package;
  - one DevOps/SRE/policy/dashboard package;
- Host ABI version decision;
- profile support matrix;
- package-check diagnostics;
- report visibility;
- conformance tests;
- negative tests for `debug.metric` event-bus misuse;
- unsupported-profile tests;
- manifest mismatch tests;
- clear migration from `debug.metric` misuse.

If future implementation accepts new host imports, the likely Host ABI target is
Host ABI `0.11`. Host ABI remains `0.10` for v0.16 unless such imports are
accepted through spec/profile/tests.

A future scalar `output.emit` Host ABI import would likely require Host ABI
`0.11`, but would not necessarily require AIR ABI `0.11` if it uses existing AIR
ABI `0.10` scalar import conventions. AIR ABI `0.11` is required only if package
calling convention, memory/data layout, entrypoint semantics, or runtime package
metadata contract changes.

## Future Acceptance Criteria

A future implementation must include:

- package-check visibility for declared outputs and required capabilities;
- profile-gated support and deterministic unsupported-profile diagnostics;
- report-visible declared outputs, IDs, capabilities, and host imports;
- test fixtures covering at least one non-game output use case;
- conformance integration showing declared outputs are observable through the
  accepted contract;
- negative tests rejecting `debug.metric` as an output/event bus;
- no game-specific Core API or stdlib helper.

This RFC itself is accepted only as a boundary/design document and introduces no
public Host ABI.

Conformance/replay planning for future output streams is covered in
[`v0.16-host-conformance-replay.md`](v0.16-host-conformance-replay.md).

## Future Test Matrix

Before promotion to Host ABI `0.11`, tests must cover:

| Area | Required cases |
|---|---|
| Manifest IDs | stable numeric IDs, duplicate ID rejection, missing ID rejection |
| Capabilities | required capability accepted, missing capability rejected |
| Profiles | supported channel passes, unsupported channel/import fails |
| Reports | declared outputs, IDs, channels, capabilities, and host imports visible |
| Package-check | manifest/source mismatch fails deterministically |
| Conformance | emitted output trace matches expected scalar channel/id/arg tuples |
| Debug boundary | `debug.metric` event-bus misuse warns or fails by policy |
| Domains | at least one interactive/game-like fixture and one non-game fixture |
| Rejections | `draw_actor`, `draw_contra_enemy`, platformer water APIs, voxel APIs |

## Risks

- events may be confused with diagnostics unless `debug.metric` remains
  diagnostics-only;
- host-specific output behavior may be promoted without conformance evidence;
- game examples may bias the contract toward visual effects instead of generic
  outputs.

## Deferred Items

- event/output Host ABI candidate;

- event conformance fixtures;
- output replay model;
- host profile support decisions.
