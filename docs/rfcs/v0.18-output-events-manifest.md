# AIR v0.18 RFC: Output Contract Manifest Tooling

Status: accepted v0.18 tooling first slice

Target milestone: v0.18

## Purpose

AIR needs a reviewable way to describe host-visible output intent before any
runtime output Host ABI is promoted. This RFC defines a tooling-only
output contract manifest shape that package-check and reports can inspect.

Output events are one kind of output intent. The broader output contract covers:

- notification request;
- badge update;
- focus suggestion;
- AI budget cap;
- policy violation;
- dashboard alert;
- pipeline decision;
- interactive visual/audio intent.

This RFC does not implement `output.emit`, `output.event`, `audio.event`, or
`effect.event`. It does not add Host ABI imports and does not require Host ABI
`0.11`.

## Scope

The output contract manifest describes stable output IDs and metadata:

- `schemaVersion`;
- `kind: "air.outputContract"`;
- `outputs[]`;
- `output.id`;
- `output.name`;
- `output.channel`;
- `output.capability`;
- scalar `output.args[]`;
- optional `output.resources[]`;
- optional `output.profileConstraints`.

The manifest is a package/tooling contract. It may be used by future generated
handles, package-check, reports, and conformance planning. It does not allow AIR
modules to emit runtime output intents.

## Non-goals

- No `output.emit` implementation.
- No `output.event` implementation.
- No `audio.event` implementation.
- No `effect.event` implementation.
- No Host ABI import addition.
- No Host ABI `0.11` in this step.
- No AIR ABI change.
- No runtime event channel.
- No automatic host-side action execution.
- No dynamic payload maps.
- No strings, binary blobs, object payloads, host object handles, or runtime
  object references.
- No hidden host authority.
- No `debug.metric` event bus.
- No game-specific output APIs.

## Manifest Shape

Example:

```json
{
  "schemaVersion": "0.18",
  "kind": "air.outputContract",
  "outputs": [
    {
      "id": 10,
      "name": "priority_alert_requested",
      "channel": "notification",
      "capability": "notify.request",
      "args": [
        { "name": "task_id", "type": "i32" },
        { "name": "severity", "type": "i32" }
      ],
      "resources": [
        { "kind": "icon", "id": "priority-alert" }
      ],
      "profileConstraints": {
        "profiles": ["cli", "chrome-extension-mv3-draft"]
      }
    }
  ]
}
```

### `schemaVersion`

Required string. The v0.18 first-slice value is `0.18`.

### `kind`

Required string. The v0.18 first-slice value is `air.outputContract`.

### `outputs[]`

Required array. Each item declares one semantic output intent. The field name
is `outputs[]` because the contract covers generic output intents, not only
event streams.

### `output.id`

Required stable integer ID. IDs are package contracts, not host authority. They
must be deterministic and unique within the manifest.

### `output.name`

Required stable human-readable name. Names must be unique within the manifest
and suitable for generated handle names.

### `output.channel`

Required channel name. Candidate channels include:

- `visual`;
- `audio`;
- `alert`;
- `notification`;
- `pipeline`;
- `dashboard`;
- `audit`;
- `extension`;
- `test`.

Unknown channels fail by default unless the manifest explicitly marks the output intent
or channel as experimental and the selected policy/profile allows experimental
channels.

### `output.capability`

Required capability string. The capability names the authority required for the
future output intent. Package-check should fail a missing capability once the
manifest is connected to package metadata or AIR usage data.

### `output.args[]`

Required ordered scalar argument schema. P0 allowed types:

- `i32`;
- `bool`;
- enum-like `i32` values declared through constants or generated handles.

No strings, dynamic maps, JSON objects, binary blobs, host objects, or runtime
object payloads are allowed.

### `output.resources[]`

Optional resource bindings. These may reference icons, textures, audio clips,
templates, dashboard widgets, or other manifest-owned resources.

Resource entries should contain at least:

- `kind`;
- `id`.

Missing referenced resources fail when the resource manifest is available.

### `output.profileConstraints`

Optional profile restrictions. Profiles must explicitly support output channels
and any future imports. A profile that supports visual output does not imply
support for audio, notifications, DevOps action requests, dashboards, or browser
extension outputs.

## Validation Rules

Package-check validates the first-slice tooling contract:

- manifest parses as JSON;
- `schemaVersion` exists and is supported;
- `kind` is `air.outputContract`;
- `outputs[]` exists and is an array;
- duplicate output intent IDs fail;
- duplicate output intent names fail;
- output intent IDs are stable integers;
- output intent names are stable identifiers or documented stable names;
- unknown channels fail by default or emit an experimental warning when policy
  permits experimental channels;
- missing capability fails once connected to package-check or AIR usage data;
- missing referenced resources fail when resource manifests are available;
- scalar args use supported types only;
- non-scalar args fail;
- duplicate arg names fail;
- unused output intents warn only when usage data exists;
- generated output handle freshness is checked only if generated handles are
  accepted and present;
- no absolute paths;
- no timestamp-like fields.

Generated output handles are future/P1 unless accepted separately. This RFC
defines the manifest shape and package-check/report visibility; it does not
generate handles in the first slice.

## Package Manifest Integration

Packages reference output contract files through `air.package.json`:

```json
{
  "outputContracts": [
    "outputs/main.output.json"
  ]
}
```

The paths must be package-local. Absolute paths, URL-like paths, parent
traversal, and package-root escapes fail manifest validation. This field does
not grant output authority and does not imply runtime support.

## Report Visibility

Reports should expose:

- output contract manifest path and fingerprint;
- output intent IDs and names;
- channels;
- required capabilities;
- scalar arg schemas;
- resource references;
- profile constraints;
- generated output handle status when available;
- validation diagnostics;
- whether support is tooling-only or backed by an accepted Host ABI import.

The v0.18 first slice exposes output contract metadata under package-check and
package report `outputContracts.schemas[]`.

Reports must clearly state that v0.18 output contract manifests are tooling-only
unless a separate Host ABI promotion lands.

## Package / Profile Boundary

Manifests may declare semantic output intent, but v0.18 does not define
automatic host-side action execution. Hosts may consider output intents only
through accepted future contracts and host policy. Host implementations must not
infer semantic outputs from:

- `debug.metric`;
- filenames;
- resource paths;
- unrelated AIR state;
- demo conventions;
- hidden TypeScript/native side channels.

Profile compatibility checks should fail unsupported channels or future imports
deterministically.

There is no runtime event channel in v0.18. A manifest entry is metadata for
tooling, reports, generated handles, and future conformance planning only. It
must not be interpreted by a host as permission to perform notifications,
sounds, effects, browser action requests, pipeline decisions, dashboard updates,
or other outputs. It is metadata for intent review, not execution authority.

## ABI Impact

This RFC does not change AIR ABI.

AIR ABI remains `0.10` because the manifest is source/package metadata and does
not change executable calling convention, memory/data layout, entrypoint
semantics, or runtime-required package metadata.

This RFC does not change Host ABI.

Host ABI remains `0.10` because no host imports are added or changed. Host ABI
`0.11` is required only if a future accepted RFC adds a runtime output host
import such as a scalar `output.emit` candidate.

## Test Matrix

| Area | Valid case | Failure / warning case |
| --- | --- | --- |
| Manifest shape | `schemaVersion`, `kind`, and `outputs[]` exist | missing `schemaVersion`, wrong `kind`, unsupported schema, or non-array `outputs` fails |
| IDs | stable integer output intent IDs are unique | duplicate IDs fail |
| Names | stable output intent names are unique | duplicate names fail |
| Channels | known channel passes | unknown channel fails unless explicitly experimental and policy allows warning |
| Capabilities | output intent declares required capability | missing capability fails once package-check integration exists |
| Scalar args | ordered `i32`, `bool`, or enum-like `i32` args pass | strings, dynamic maps, JSON objects, binary blobs, host objects, or object payloads fail |
| Resources | declared resources resolve through available manifests | missing referenced resource fails |
| Usage data | used output intent is visible in report when usage data exists | unused output intent warns only when usage data exists |
| Profiles | supported channel/profile passes | unsupported profile channel fails deterministically |
| Generated handles | disabled or absent generated handles do not imply authority | stale/missing generated output handles fail only after handles are accepted |
| Runtime boundary | manifest remains tooling-only | any accepted `output.emit`, `audio.event`, `effect.event`, or runtime event channel fails v0.18 scope |
| ABI | AIR ABI and Host ABI stay `0.10` | Host ABI `0.11` requires separate accepted Host ABI RFC |

## Acceptance Tests

Future tooling tests should cover:

- valid output contract manifest passes;
- duplicate IDs fail;
- duplicate names fail;
- unknown channel fails;
- unknown experimental channel warns only when policy allows it;
- non-scalar arg fails;
- missing capability fails once package-check integration exists;
- missing resource fails when resource manifests are available;
- unused output intent warns only when usage data exists;
- unsupported profile channel fails;
- generated output handles are deferred unless explicitly enabled;
- report lists manifest and output intent metadata;
- AIR ABI remains `0.10`;
- Host ABI remains `0.10`;
- no `output.emit`, `audio.event`, or `effect.event` import is accepted.

## Open Questions

- Should output contract manifests remain a dedicated `outputContracts` package
  manifest field or later move under `manifests`?
- Which channels are stable in P0 versus experimental?
- Which diagnostic code domain should own output manifest errors?
- Should generated handle names use output intent names directly or a normalized
  namespace prefix?
- What minimum usage data is required before unused output intent warnings are reliable?
