# AIR v0.19 RFC: Full LSP MVP

Status: accepted first slice / diagnostics-only MVP implemented

Target milestone: v0.19 diagnostics-only implementation

## Purpose

AIR v0.15 introduced LSP-lite JSON diagnostics through:

```sh
airc check <file-or-package> --lsp-json
```

That interface gives editors and AI repair loops stable diagnostics without a
long-running server. v0.18 added package-visible bounded facts schema
diagnostics and Output Contract diagnostics. v0.19 adds compact table
diagnostics. v0.19 implements a diagnostics-only JSON-RPC LSP server that
reuses the existing diagnostic pipeline.

The MVP goal is not an IDE feature suite. The MVP goal is deterministic,
package-aware diagnostic publishing over standard LSP transport.

## Scope

Implemented P0 scope:

- `airc lsp --stdio`;
- JSON-RPC over stdio;
- `initialize`;
- `shutdown`;
- `textDocument/didOpen`;
- `textDocument/didChange`;
- `textDocument/didSave`;
- `textDocument/didClose`;
- `textDocument/publishDiagnostics`;
- parser diagnostics;
- verifier diagnostics;
- package-check diagnostics;
- reviewPolicy diagnostics;
- package graph awareness;
- generated artifact diagnostics;
- manifest/resource diagnostics;
- facts schema diagnostics;
- Output Contract diagnostics;
- compact table diagnostics when compact table support is present.

## Non-goals

- No VS Code extension.
- No hover in the P0 MVP.
- No go-to-definition in the P0 MVP.
- No document symbols in the P0 MVP.
- No code actions in the P0 MVP.
- No semantic tokens.
- No rename support.
- No formatting implementation beyond existing formatter reuse.
- No package registry.
- No remote workspace indexing.
- No background compiler daemon.
- No AIR ABI change.
- No Host ABI change.

## Diagnostic Architecture

The LSP server must reuse the existing diagnostics normalization and package
reporting pipeline. It must not create a second diagnostic engine.

Required properties:

- preserve stable diagnostic codes;
- preserve severity, source, path, module, symbol, fields, related metadata,
  and repair hints where available;
- keep deterministic ordering;
- avoid duplicate diagnostics;
- use existing parser, verifier, package-check, reviewPolicy, manifest,
  generated artifact, facts schema, Output Contract, and compact table
  diagnostics;
- keep the LSP envelope as an adapter over existing normalized diagnostics.

The LSP server should treat LSP-lite output as the compatibility baseline. If a
diagnostic appears in `airc check --lsp-json`, the JSON-RPC LSP server should
publish the same diagnostic code and equivalent fields unless the server has a
document-position-specific refinement.

## Package Graph Awareness

AIR packages are graph-shaped. The LSP server must understand more than a
single open file when package context is available.

The MVP should:

- detect package roots from `air.package.json` when possible;
- analyze package-local source imports;
- publish diagnostics for directly affected open files;
- surface package-level diagnostics without losing the package-level path;
- include generated artifact diagnostics when package metadata references
  generated files;
- respect package manifest profile, capability, reviewPolicy, and pathClass
  configuration.

When package context cannot be resolved, the server falls back to single-file
parser and verifier diagnostics.

The implemented MVP runs file-level parser/verifier diagnostics on
`textDocument/didOpen` and `textDocument/didChange`. It runs package-aware
diagnostics on `textDocument/didSave` when an `air.package.json` can be
discovered by walking upward from the saved file path. If no package root is
found, `didSave` keeps the file-level parser/verifier fallback and does not
fail only because package context is absent. Package-aware diagnostics reuse
the existing package-check/report path, including generated artifact,
manifest/resource, facts schema, Output Contract, compact table, and
reviewPolicy diagnostics where those checks apply. This keeps change-time
diagnostics cheap and avoids background indexing or daemon cache behavior.
Package-aware diagnostics on every keystroke are deferred.

`textDocument/didChange` uses LSP full-document synchronization (`change: 1`).
Incremental range patching is deferred.

`textDocument/didClose` removes the document from the in-memory open-document
map and publishes an empty diagnostic list for the closed URI.

## ReviewPolicy and Path Classes

The LSP server must respect reviewPolicy and pathClasses exactly as package
checks do. It must not weaken release-candidate policy behavior for editor
convenience.

Examples:

- release-candidate reviewPolicy may fail gateable diagnostics;
- generated paths may have different policy expectations than authored source;
- pathClass ambiguity should remain visible;
- `debug.metric` event-bus misuse must remain diagnostics-only and gateable.

## Transport Model

P0 transport is standard JSON-RPC over stdio:

```sh
airc lsp --stdio
```

The server should support the minimal lifecycle:

- client sends `initialize`;
- server responds with diagnostics-only text synchronization capabilities;
- client sends text document open/change/save notifications;
- client may send text document close notifications;
- server publishes diagnostics;
- client sends `shutdown`;
- client sends `exit`.

The MVP should avoid hidden background compiler state. Any caching must be
deterministic, invalidated by document version/package file changes, and safe to
disable.

## Determinism

LSP diagnostics must be deterministic:

- stable diagnostic ordering;
- stable diagnostic codes;
- stable package graph order;
- no timestamps in diagnostic payloads;
- no absolute paths unless required by the LSP URI and normalized consistently;
- no nondeterministic background indexing result ordering.

## ABI Impact

No AIR ABI change is required. LSP is tooling surface only.

No Host ABI change is required. LSP does not add host imports or executable
runtime behavior.

## Implemented Command

```sh
node bin/airc.js lsp --stdio
```

The command supports `Content-Length` framed JSON-RPC 2.0 over stdio. It handles
`initialize`, `initialized`, `shutdown`, `exit`, `textDocument/didOpen`,
`textDocument/didChange`, `textDocument/didSave`, and `textDocument/didClose`.
The MVP uses full-document didChange sync. Diagnostics are published through
`textDocument/publishDiagnostics`.

## P1 Future

After the diagnostics-only server is stable, P1 tooling may add:

- hover;
- go-to-definition;
- document symbols;
- code actions;
- AI repair prompts;
- generated handle regeneration action;
- review baseline/trend hints.

These features must remain adapters over existing AIR analysis where practical.
They must not introduce parallel semantic engines.

## Deferred

- Full VS Code extension.
- Semantic tokens.
- Rename.
- Formatting server integration beyond calling existing formatter behavior.
- Package registry.
- Remote workspace indexing.
- Background compiler daemon.

## Acceptance Tests

The v0.19 MVP includes tests for:

- open file with syntax error publishes parser diagnostics;
- didChange with full document text updates diagnostics;
- didClose clears diagnostics for the closed URI;
- CLI stdio smoke test receives valid JSON-RPC initialize/shutdown responses;
- verifier error publishes stable diagnostic code;
- package with missing generated handles publishes generated artifact
  diagnostics;
- reviewPolicy large function publishes reviewPolicy diagnostic;
- facts schema violation publishes facts diagnostic;
- Output Contract manifest violation publishes output contract diagnostic;
- compact table violation publishes table diagnostic when compact table support
  is present;
- package graph changes update affected diagnostics;
- no duplicate diagnostics;
- stable diagnostic ordering;
- `--lsp-json` and JSON-RPC LSP preserve diagnostic codes for equivalent cases.

## Open Questions

- Should the MVP publish package-level diagnostics against
  `air.package.json`, the package root URI, or the most relevant source file?
- How should unsaved generated files be represented, if at all?
- Should package graph indexing be explicit through workspace folders or lazily
  discovered from open files?
- Which LSP client capabilities are required for the first useful integration
  test?
