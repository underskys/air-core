# RFC: v0.14 Executable Package Composition

Status: draft

Target milestone: AIR v0.14

## Summary

v0.14 should make package-local authored AIR modules the source of truth for
verification, reporting, package-check, and package build. Generated or linked
output is a deterministic build artifact, not the canonical program source.

This RFC does not add public Host ABI functions and does not implement runtime
dynamic linking, remote imports, arbitrary filesystem imports, or a package
registry.

## Goals

- Verify an AIR package as an authored package-local module graph.
- Build an executable package artifact from the same graph used by verification.
- Preserve exported/private boundaries across modules.
- Lower cross-module calls deterministically.
- Preserve capability, effect, and host import origins in reports.
- Make generated/linked output reproducible and reviewable.
- Keep package execution static: no runtime module loading or dynamic imports.

## Non-goals

- No runtime dynamic linking.
- No remote imports.
- No arbitrary filesystem imports.
- No package registry.
- No host object handles.
- No demo-specific APIs.
- No new public Host ABI.
- No dynamic maps, GC, or reflection.

## Source Of Truth

The package-local authored modules are the source of truth.

Examples:

- `src/main.air`
- `src/math.air`
- `src/audio_logic.air`
- `generated/asset_handles.air`

Generated and linked files are build artifacts. They may be checked for
freshness, inspected, and bundled, but they must not replace the authored module
graph as the canonical verification input.

Package-check must be able to distinguish:

- authored modules;
- deterministic generated modules;
- linked build artifacts;
- stale or missing generated files.

## Package Entrypoint

The package manifest declares a stable entrypoint module.

Example shape:

```json
{
  "entry": "src/main.air"
}
```

The entrypoint is package-local and must resolve inside the package root.
Absolute paths, remote URLs, `file://` URLs, and path escapes outside the package
root are rejected.

The entrypoint owns package startup/export intent. Imported modules may provide
exported helpers, but they do not silently become package entrypoints.

## Module Graph

The verifier builds a deterministic package-local module graph from the
entrypoint.

Allowed imports:

```air
use "./math.air" as math
use "../shared/fixed.air" as fixed
```

Rejected imports:

```air
use "math.air" as math
use "/tmp/math.air" as math
use "file:///tmp/math.air" as math
use "https://example.com/math.air" as math
```

Rules:

- imports must be relative and package-local;
- resolved paths must remain inside the package root;
- aliases must be unique within a module;
- cycles are rejected unless a later RFC explicitly accepts them;
- missing modules are rejected;
- duplicate module identities are rejected.

## Deterministic Module Ordering

Verification, reporting, and build use the same deterministic module order.

Required ordering:

1. Resolve from the package entrypoint.
2. Normalize module paths relative to package root.
3. Traverse imports in source order.
4. Emit final graph order in stable normalized path order or in a documented
   deterministic topological order.

The chosen ordering must be stable across platforms and filesystems.

## Exported And Private Boundaries

Only exported functions may be called from another module.

Allowed:

```air
use "./math.air" as math

func run() -> i32 {
entry:
  %x:i32 = call math.add_one(41)
  return %x
}
```

Rejected:

```air
use "./math.air" as math

func run() -> i32 {
entry:
  %x:i32 = call math.internal_step(41)
  return %x
}
```

Private helpers remain private after lowering. Linked output must not make
private helpers appear as public package APIs.

## Deterministic Symbol Mangling

Linked output needs deterministic internal symbols.

Recommended scheme:

```text
<normalized-module-path-hash-or-escaped-path>__<symbol-name>
```

Requirements:

- stable across machines;
- independent of absolute checkout path;
- collision checked;
- private symbols remain internal;
- exported package symbols remain predictable and reportable.

The exact mangling can change before implementation, but the implementation
must document it and keep JSON reports stable.

## Cross-module Call Lowering

Verifier-level calls such as:

```air
%y:i32 = call math.add_one(%x)
```

lower to a deterministic internal call target in linked output.

Lowering must preserve:

- source caller module;
- target module;
- target exported symbol;
- argument and return types;
- verifier-approved capability and effect requirements.

If linked output is not enabled, package-check/report must still validate and
report the graph without pretending an executable linked artifact exists.

## Capability And Effect Origin Preservation

Reports must preserve origins across modules.

Required JSON concepts:

```json
{
  "modules": [
    {
      "path": "src/main.air",
      "imports": ["src/audio_logic.air"],
      "capabilities": ["debug"]
    },
    {
      "path": "src/audio_logic.air",
      "capabilities": ["audio"],
      "hostImports": ["audio.beep"]
    }
  ],
  "computedCapabilities": ["audio", "debug"],
  "capabilityOrigins": {
    "audio": ["src/audio_logic.air"],
    "debug": ["src/main.air"]
  },
  "hostImportOrigins": {
    "audio.beep": ["src/audio_logic.air"]
  },
  "authorityChains": [
    {
      "from": "src/main.air",
      "through": "src/audio_logic.air",
      "hostImport": "audio.beep",
      "requiredCapability": "audio"
    }
  ]
}
```

The report must not collapse package authority into a single opaque pass/fail.
AI and human reviewers need to see which module caused each requirement.

## CLI Target Shape

Exact command names may adapt to existing CLI conventions, but v0.14 should
support this behavior:

```sh
airc verify package <package-dir>
airc report package <package-dir> --json
airc package-check package <package-dir> --profile browser-webgpu --json
airc build package <package-dir> -o dist/package
```

If existing CLI conventions prefer `airc package-check <package-dir>`, the
package form may be represented as:

```sh
airc package-check <package-dir> --profile browser-webgpu --source-only --json
airc build <package-dir> --package -o dist/package
```

Required behavior:

- `verify package` validates syntax, types, module graph, exports/private
  boundaries, capabilities, effects, and host imports.
- `report package` emits deterministic human and JSON reports for the same graph.
- `package-check package` compares package requirements against selected host
  profiles and manifest/resource constraints.
- `build package` produces deterministic linked/generated executable artifacts
  from the verified graph.

## Generated And Linked Artifacts

Generated files may include:

- `generated/asset_handles.air`;
- `generated/audio_handles.air`;
- `generated/material_handles.air`;
- `generated/assets.air`;
- linked AIR or Wasm artifacts.

Rules:

- generated files are deterministic;
- generated files are derived artifacts;
- generated files must not grant authority;
- generated files are stale/missing checked;
- generated headers must not reference omitted tools in review bundles;
- linked output is not the source of truth.

## Diagnostics

Diagnostics must be deterministic and repairable.

Required examples:

- missing imported module;
- path escape outside package root;
- remote import rejected;
- duplicate alias;
- import cycle;
- missing exported symbol;
- private function called from another module;
- symbol mangle collision;
- capability mismatch between module graph and package manifest;
- linked output unavailable when build is requested.

Each diagnostic should include:

- stable code;
- module path;
- source range where available;
- repair hint;
- JSON representation.

## Acceptance Tests

### Two-module Package

Fixture:

```text
package/
  air.package.json
  src/main.air
  src/math.air
```

Expected:

- package graph verifies;
- report lists both modules;
- build output is deterministic.

### Private Function Cannot Be Called Externally

Fixture:

```air
use "./math.air" as math

func run() -> i32 {
entry:
  %x:i32 = call math.internal_add_one(1)
  return %x
}
```

Expected:

- verify/package-check fails;
- diagnostic code is stable;
- repair hint says to export the function or call an exported wrapper.

### Cross-module Exported Call Lowers

Fixture:

```air
use "./math.air" as math

func run() -> i32 {
entry:
  %x:i32 = call math.add_one(1)
  return %x
}
```

Expected:

- verify passes;
- build lowers call to deterministic linked symbol;
- linked output does not expose private helpers as package exports.

### Capability Origin Remains Visible

Fixture:

```text
src/main.air -> src/audio_logic.air -> audio.beep
```

Expected:

- computed package capabilities include `audio`;
- report lists `audio` origin as `src/audio_logic.air`;
- host import origin lists `audio.beep`;
- authority chain remains visible.

### Output Is Deterministic Across Builds

Procedure:

```sh
airc build package package -o out-a
airc build package package -o out-b
```

Expected:

- generated artifacts match byte-for-byte where timestamps are not part of the
  format;
- JSON reports match exactly;
- symbol names and module order are stable.

## Open Questions

- Should linked AIR and linked Wasm both be emitted, or should linked AIR remain
  an optional review artifact?
- Should package exported functions be declared explicitly in the package
  manifest or inferred from the entrypoint module?
- Should generated files be required in source control for release packages, or
  only reproducible from manifests?
- What is the exact symbol mangling format?

## Initial Recommendation

Implement v0.14 in two slices:

1. package verification/report/check over authored graphs with stale generated
   artifact checks;
2. deterministic package build/linking once graph reports are stable.

This keeps v0.14 focused on executable composition without turning AIR into a
runtime module system or demo-specific language.
