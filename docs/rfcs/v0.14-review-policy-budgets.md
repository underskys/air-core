# RFC: v0.14 Review Policy Budgets

Status: draft

Target milestone: AIR v0.14

## Summary

AIR packages need configurable review budgets so AI-authored modules can be
checked for structural risk without turning AIR into a style-policing language.

The policy belongs to the package, profile, or release gate. It must not be
hardcoded globally. Valid AIR can still be valid while exceeding advisory
budgets; a package policy decides which warnings become failures.

## Goals

- Make anti-slop diagnostics configurable per package/profile.
- Keep warnings and failures machine-readable.
- Allow authored, generated, and vendored paths to use different budgets.
- Make large functions, repeated literals, table-like state, and stale generated
  artifacts visible before they become unreviewable package surfaces.
- Preserve deterministic output for package-check and reports.

## Non-goals

- No new Core syntax.
- No new Host ABI.
- No demo-specific policy keys.
- No global hardcoded budget gates.
- No automatic rewrites.
- No LLM calls.
- No rejection of valid modules solely because they are stylistically ugly
  unless the package policy explicitly gates that warning.

## Policy Shape

Example:

```json
{
  "reviewPolicy": {
    "profile": "interactive",
    "pathClasses": {
      "authored": ["src/**/*.air"],
      "generated": ["generated/**/*.air"],
      "vendor": ["kits/**"]
    },
    "thresholds": {
      "largeFunctionStatements": 80,
      "largeEntryStatements": 220,
      "largeModuleLines": 400,
      "repeatedLiteralCount": 4,
      "mutableGlobalsPerModule": 24
    },
    "gates": {
      "largeEntryFunction": "fail",
      "generatedHandleStale": "fail",
      "debugMetricEventBus": "fail",
      "magicHandleCandidate": "warn"
    }
  }
}
```

The existing `aiReview` package field may remain as the current implementation
name while v0.14 evaluates whether `reviewPolicy` should become the canonical
manifest key. If both exist during migration, package-check should reject
ambiguous duplicate policy declarations or define one deterministic precedence
rule.

## Path Classes

Path classes identify how strict a budget should be.

| Class | Meaning | Default posture |
| --- | --- | --- |
| `authored` | Human/AI-authored package source. | Strictest review budgets. |
| `generated` | Deterministic generated AIR. | Different line/size budget; freshness is strict. |
| `vendor` | Vendored kit/project helper code. | Usually warning-only unless release gate opts in. |

Generated and vendor files may have larger size thresholds than authored files,
but they must not bypass authority, capability, Host ABI, or generated freshness
checks.

## Required Checks

### Max Statements Per Function

Report functions whose statement count exceeds the configured threshold.

Required fields:

- diagnostic id;
- module path;
- function name;
- statement count;
- threshold;
- path class;
- repair hint.

### Max Statements For Exported Entry / Frame / Main

Exported entrypoints, `main`, and frame-like exported functions should remain
orchestration shells when a package policy asks for that.

The report should identify:

- function name;
- whether it is exported;
- whether it is `main`;
- whether it matched frame/entry naming policy;
- statement count;
- threshold.

### Max Mutable Globals Per Module

Report modules with too many mutable globals.

This is advisory by default because some low-level fixtures may intentionally
model state directly. Interactive packages may promote the warning to failure.

### Repeated Literals

Report repeated numeric or boolean literals that suggest constants, generated
handles, or static tables.

Required fields:

- literal value;
- count;
- module path;
- representative locations where available;
- suggested target: constant, generated handle, or static table.

### Select-chain-as-table

Detect repeated `select.*` chains that look like static lookup tables.

Repair hint:

- use static readonly scalar tables for authored deterministic values;
- use generated static tables for manifest-derived values.

### Slot-family / Table-like State

Detect repeated state families such as `slot0_x`, `slot1_x`, `slot2_x` or
similar indexed naming patterns.

This should be generic. It must not use player/enemy/projectile-specific rules.

Repair hint:

- use static tables for immutable data;
- use future fixed pools only after an accepted RFC;
- split ownership by package-local module.

### `debug.metric` Event-bus Misuse

`debug.metric` is diagnostic telemetry. It must not become a hidden gameplay,
audio, effect, filesystem, network, UI, or host-action event bus.

Report event-like patterns such as:

- literal pulse values;
- many metric ids in one function;
- metric names or ids that look like actions;
- host code documented as reacting to debug metrics.

The package policy may make this warning a failure.

### Generated Artifact Freshness

Generated artifacts are deterministic derived files, not source of truth.

Required checks:

- missing generated handles;
- stale generated handles;
- missing package-declared generated modules;
- generated header references a missing generator;
- generated module lacks source-manifest trace where expected;
- generated artifact fingerprints are visible in report.

This gate should usually be `fail` for generated handle/data modules.

### Top Large Functions / Modules

Reports should list top large functions and modules even when thresholds are not
exceeded. This gives reviewers trend visibility before a package becomes hard to
review.

Required fields:

- module path;
- function name where applicable;
- statement count;
- line count where available;
- path class.

### Trend Tracking

Trend tracking is useful but optional in v0.14.

If implemented, it should compare current report metrics with a checked-in
baseline report and identify:

- functions that grew past threshold;
- modules that grew past threshold;
- repeated literal increases;
- generated artifact freshness regressions.

Trend tracking must be deterministic and must not require a remote service.

## Gate Actions

Each diagnostic can map to:

- `off`;
- `warn`;
- `fail`.

Default behavior should be conservative:

- semantic, capability, Host ABI, package/profile, and generated freshness
  violations may fail by default;
- structural anti-slop diagnostics should warn by default;
- blessed examples or release packages can promote selected warnings to fail.

## JSON Output

Package-check/report JSON must remain machine-readable.

Example shape:

```json
{
  "reviewPolicy": {
    "profile": "interactive",
    "pathClass": "authored"
  },
  "aiReview": {
    "status": "warn",
    "warnings": [
      {
        "id": "large-entry-function:frame",
        "severity": "fail",
        "module": "src/main.air",
        "function": "frame",
        "statements": 240,
        "threshold": 220,
        "repairHint": "keep exported entry/frame functions as orchestration shells and move subsystem logic into package-local modules"
      }
    ],
    "topLargeFunctions": [],
    "topLargeModules": []
  }
}
```

Ordering must be deterministic:

- sort diagnostics by id, module path, function name, then location;
- sort repair hints;
- sort path class matches by most-specific rule then path.

## Acceptance Tests

- large function warning remains deterministic;
- large exported entry/frame warning can be promoted to failure;
- mutable global budget warning can be promoted to failure;
- repeated literal warning is stable;
- select-chain-as-table warning is stable;
- slot-family/table-like state warning is stable;
- debug.metric event-bus warning can be promoted to failure;
- stale generated handles fail when policy requires freshness;
- generated/vendor path classes use their configured thresholds;
- JSON output is deterministic across repeated runs.

## Recommendation

Use the existing AI review/report machinery as the implementation path, but make
the package manifest policy explicit and package-scoped. Keep all thresholds
configurable. Do not add global style gates.
