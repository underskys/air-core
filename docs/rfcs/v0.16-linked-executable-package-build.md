# AIR v0.16 RFC: Linked Executable Package Build

Status: accepted first-slice link-plan and simple linked WAT/Wasm design

Target milestone: v0.16 link-plan metadata plus simple scalar linked WAT/Wasm output

## Purpose

Move AIR package tooling from source graph validation only toward deterministic
linked package output.

v0.13 and v0.14 made authored package-local module graphs visible and
verifiable. v0.16 `airpkg` adds deterministic package metadata artifacts. The
linked executable package build track defines how that authored module graph can
eventually lower into a single executable WAT/Wasm artifact without turning
runtime loading, remote imports, registries, or product bundling into AIR Core.

## Non-goals

This RFC does not add:

- runtime dynamic linking;
- remote imports;
- package registry behavior;
- dynamic maps;
- garbage collection;
- reflection;
- host object handles;
- game-specific APIs;
- optimizer passes;
- native product bundles;
- compressed `airpkg` archive semantics;
- event/output Host ABI.

## Source Graph As Truth

The authored package graph remains the source of truth.

Linked output is a generated artifact. Review, diagnostics, package-check,
capability origins, generated freshness, and report metadata must continue to
refer back to package-relative source modules.

Generated linked WAT/Wasm must not become the review source. If linked output
and authored source disagree, the package is stale or invalid.

## Module Order

The link plan must use deterministic stable topological ordering.

Ordering rules:

- module identity is the canonical package-relative path using `/` separators;
- paths must be normalized under the package root;
- `.` and `..` segments are resolved before graph analysis;
- package-root escape remains invalid;
- remote, absolute, and arbitrary filesystem imports remain invalid;
- imports define directed edges from caller module to imported module;
- modules are ordered topologically by dependency relation;
- ties are broken by canonical package-relative path lexicographic order;
- cycles fail before lowering.

The link plan must report:

- `moduleOrder`;
- import edges;
- cycle diagnostics if ordering fails;
- source graph hash used by the linker.

## Symbol Mangling

Linked output must use deterministic symbol names and a required symbol map.

Mangled names must:

- be derived from canonical package-relative module path plus local symbol name;
- avoid absolute paths;
- avoid platform path separators;
- avoid collisions;
- be stable across machines;
- be reversible through the symbol map, not through ad hoc string parsing.

Required symbol categories:

- functions;
- globals;
- static tables;
- generated module symbols.

Recommended internal shape:

```json
{
  "symbols": [
    {
      "kind": "function",
      "module": "src/math.air",
      "sourceName": "clamp_i32",
      "mangledName": "__air$src_math$clamp_i32",
      "visibility": "module-export",
      "signature": "(i32,i32,i32)->i32"
    }
  ]
}
```

Current first-slice mangling shape:

```text
__air$<moduleId>$<category>$<localName>$<hash>
```

`moduleId` is derived from the canonical package-relative module path. The link
report preserves a deterministic symbol map. Consumers must not infer package
semantics from raw mangled names alone.

## Cross-module Call Lowering

Calls of the form `alias.function(...)` lower to calls of the imported module's
mangled function symbol.

Validation before lowering:

- alias must resolve to a package-local imported module;
- target function must exist;
- target function must be exported by its module;
- private cross-module calls fail;
- unresolved imports fail;
- missing exported symbols fail;
- signature mismatch fails;
- capability/effect requirements propagate through the package graph.

Lowering must not weaken existing module graph rules.

## Module Exports Vs Package Exports

This RFC separates two visibility levels:

- **Module export:** visible to other package-local modules through explicit
  `use "./x.air" as alias` imports. Module exports are package-internal
  visibility by default.
- **Package export:** host-visible Wasm export selected by package manifest or
  explicit package entrypoint/export metadata.

Module exports must not automatically become host-visible package exports unless
the package manifest or compatibility fallback explicitly selects them.

Compatibility fallback:

- Existing single-file behavior may continue exporting AIR `export func`
  functions as host-visible Wasm exports.
- Multi-module package linking should warn if it relies on this fallback instead
  of manifest-declared package exports.
- The warning should be deterministic and report-visible.

## Package Entrypoint

The package manifest should drive linked entrypoint and package exports.

Existing fields:

- `entry`: authored AIR entry module;
- `wasm`: built artifact path, when present.

Minimal extension candidate:

```json
{
  "entry": "src/main.air",
  "packageExports": [
    {
      "name": "run",
      "module": "src/main.air",
      "function": "run"
    }
  ]
}
```

If `packageExports` is absent, implementation may use compatibility fallback for
single-file packages and should warn for multi-module packages.

## Generated Handles And Modules

Generated handles/modules must be checked before linking.

Required behavior:

- missing generated modules fail;
- stale generated modules fail or warn according to package policy before link;
- generated artifact origins are preserved;
- source manifest fingerprints are preserved;
- generator references are preserved;
- generated modules do not grant authority.

The linked report must include generated artifact status and fingerprints so a
consumer can tell whether linked output was produced from current source inputs.

## Static Tables

Module-local readonly scalar tables are supported.

Rules:

- static scalar tables lower as module-owned readonly data;
- table symbols use deterministic module-local mangling;
- table metadata remains report-visible;
- table size and element type are preserved.

Deferred:

- direct cross-module table access;
- tablegroups;
- record-like schemas;
- dynamic or mutable table storage.

Cross-module access should go through exported functions until a separate RFC
defines table visibility.

## Host Imports And Capabilities

Host imports remain host imports.

This RFC does not add Host ABI functions, change import signatures, or move host
authority into linked output. Link planning may deduplicate identical host
imports, but the report must preserve:

- importing module;
- origin call chain where available;
- required capability;
- host import signature;
- selected host profile compatibility.

Capability propagation remains package graph based. Linking cannot authorize a
host import that package-check rejects.

## Linked Report

The linked build/report output should include deterministic fields equivalent
to:

```json
{
  "schemaVersion": "0.16",
  "linkedWasm": {
    "enabled": true,
    "status": "pass",
    "linkedWatHash": "sha256:...",
    "linkedWasmHash": "sha256:..."
  },
  "airAbi": "0.10",
  "hostAbi": "0.10",
  "linkPlanHash": "sha256:...",
  "sourceGraphHash": "sha256:...",
  "linkedWatHash": "sha256:...",
  "linkedWasmHash": "sha256:...",
  "graph": {
    "edges": []
  },
  "moduleOrder": ["src/main.air", "src/math.air"],
  "crossModuleCalls": [],
  "symbols": [
    {
      "module": "src/math.air",
      "kind": "function",
      "sourceName": "add_one",
      "mangledName": "__air$src_math_air$fn$add_one$...",
      "wasmName": "_air_src_math_air_fn_add_one_..."
    }
  ],
  "packageExports": [],
  "hostImports": [],
  "capabilities": [],
  "generatedArtifacts": [],
  "diagnostics": []
}
```

The implemented first slice writes sidecar metadata next to the output:

```sh
node bin/airc.js build package <package-dir> --linked-wasm --profile <id> -o build/package.wasm
# sidecar: build/package.wasm.link.json
```

If linked build is not enabled, link-plan output keeps the explicit non-linked
state:

```json
{
  "linkedWasm": {
    "enabled": false,
    "status": "deferred"
  }
}
```

## ABI Impact

Decision tree:

1. AIR ABI remains `0.10` if the first implementation only emits linked WAT/Wasm
   equivalent to existing single-module runtime conventions and does not define
   new stable package entrypoint/runtime metadata semantics.
2. AIR ABI may need `0.11` if linked packages define a stable executable package
   runtime contract, new import/export layout, new memory/data representation,
   package entrypoint semantics, or runtime-required package metadata.
3. Host ABI remains unchanged unless host imports are added, removed, renamed,
   retyped, or assigned new required semantics.
4. Host ABI remains `0.10` for pure linker/report/package metadata work.

No AIR ABI or Host ABI bump is approved by this RFC alone.

## Incremental Migration

Stage 1: link plan

- build deterministic module order;
- build symbol map;
- report package exports and host imports;
- no linked WAT/Wasm output yet.
- implemented command shape:

```sh
node bin/airc.js link-plan <package-dir> --profile <id> --json
```

Stage 2: linked WAT/Wasm for simple packages

- lower simple multi-module packages;
- resolve exported cross-module calls;
- fail private/missing/signature errors before lowering;
- preserve source graph diagnostics.
- implemented command shape:

```sh
node bin/airc.js build package <package-dir> --linked-wasm --profile <id> -o <output.wasm>
```

The first slice supports package-local scalar functions, constants, module-local
static readonly scalar tables, generated handle modules, deduped existing Host
ABI imports, and direct cross-module calls resolved through the link plan.
Cross-module direct table access, cross-module mutable global sharing, optimizer
passes, target product bundles, and custom origin sections remain deferred.

Stage 3: `airpkg` integration

- include link plan and linked artifact fingerprints in `airpkg`;
- keep source graph metadata as the review source;
- expose stale linked output as generated artifact status.

Stage 4: conformance integration

- allow conformance traces to target linked package exports;
- preserve deterministic report output;
- compare behavior without browser/GPU automation.

Stage 5: ABI decision

- decide whether linked executable package semantics require AIR ABI `0.11`;
- keep Host ABI unchanged unless new host imports are accepted.

## Acceptance Tests

Required tests before implementation is considered complete:

- deterministic link plan for the same package across repeated runs;
- module order sorted by graph topology and canonical path tie-breaks;
- private cross-module call fails;
- unresolved import fails;
- missing exported symbol fails;
- signature mismatch fails;
- symbol collision fixture fails with deterministic diagnostic;
- generated handles/modules must be fresh before linking;
- stale generated artifact blocks or warns according to policy before linking;
- module-local static tables appear in symbol map and linked report;
- cross-module direct table access remains rejected/deferred;
- identical host imports are deduplicated in linked import section where safe;
- host import origins remain report-visible after dedupe;
- package exports are manifest-selected;
- compatibility fallback emits warning for multi-module packages;
- linked WAT/Wasm hashes are deterministic;
- no absolute paths or timestamps in link plan or linked report.

## Open Questions

- whether `packageExports` belongs in `air.package.json` or a build profile
  subobject;
- whether compatibility fallback should be allowed for any multi-module package
  or only verifier-only examples;
- when linked package entrypoint semantics become AIR ABI `0.11`;
- whether linked WAT should be stored in `airpkg` first or remain an adjacent
  generated artifact.
