# AIR v0.16 RFC: Host Conformance and Replay

Status: accepted first-slice design

Target milestone: v0.16

## Purpose

Define host conformance and replay evidence for AIR host profiles. Conformance
proves that a host/profile can execute or validate AIR-observable behavior
consistently. AIR packages need verifiable host boundary reports, not just
successful local execution.

## Scope

- conformance evidence vocabulary;
- replay fixture expectations;
- host profile support reporting;
- unsupported import diagnostics;
- deterministic Core-owned evidence that does not depend on active demos.

## Non-goals

- No full replay engine.
- No remote telemetry service.
- No browser GPU automation.
- No pixel-perfect rendering comparison.
- No audio playback or waveform comparison.
- No hidden host authority.
- No game-specific replay.
- No network/device probing.
- No host-side inferred events.
- No `debug.metric` event stream.
- No host object handles.
- No Host ABI changes.
- No requirement that all hosts are deterministic in wall-clock behavior.

## Trace Model

The v0.16 first slice should use deterministic JSON input traces. A trace is a
small package/profile-scoped script of observable calls and expected results.

Example shape:

```json
{
  "schemaVersion": "0.16",
  "kind": "air.conformance.trace",
  "id": "policy-audit-basic",
  "package": "policy-audit-package",
  "profile": "cli",
  "steps": [
    {
      "id": "allowed-service",
      "call": {
        "export": "is_service_allowed",
        "args": [1]
      },
      "expect": {
        "return": 1
      }
    }
  ]
}
```

Required trace fields:

- `schemaVersion`;
- `kind`;
- stable trace `id`;
- package id/name;
- profile id;
- `steps`.

Each step may contain:

- stable step `id`;
- deterministic inputs;
- exported function call name and scalar args;
- optional expected AIR-observable outputs;
- optional expected diagnostics/report fields.

The first slice must not require wall-clock time, random device state, network
probing, GPU presentation, browser permission state, or active demo assets.

## Observable Output Model

AIR-observable outputs in the first slice are:

- return values;
- exported function results;
- report-visible host import calls if the host/profile can trace them without
  changing Host ABI;
- diagnostics/report output;
- package/profile support status.

The first slice excludes:

- visual pixel diffs;
- audio waveform diffs;
- browser GPU automation;
- hidden host state;
- gameplay-domain replay assertions.

Visual/audio host conformance can be added later only after stable fixture and
comparison policy exists.

## Future Output Stream Model

A future accepted event/output contract may add declared output streams as an
AIR-observable conformance category. This is planning only. v0.16 does not
implement an event/output Host ABI, `output.emit`, `output.event`, or
`audio.event`.

An output stream is the deterministic sequence of declared host-visible outputs
emitted by an AIR package through an accepted future output contract. It is not:

- a pixel comparison stream;
- an audio playback comparison stream;
- browser/GPU automation;
- a host-inferred event stream;
- a `debug.metric` stream.

Future output event tuples should use scalar, deterministic data:

```json
{
  "channel": "alert",
  "id": 17,
  "args": [1, 0, 0, 0],
  "flags": 0,
  "origin": {
    "module": "policy.air",
    "function": "run"
  }
}
```

Tuple fields:

- `channel`: stable output channel declared by profile/manifest;
- `id`: numeric output event ID declared by manifest or package metadata;
- `args`: scalar argument list in declaration order;
- `flags`: scalar bitset for future profile-specific modifiers;
- `origin`: optional module/function/source origin when available.

Ordering must be deterministic. For a single replay step, emitted output tuples
are compared in the order the AIR execution contract observes them. Conformance
must not reorder by ID, channel, resource name, or host arrival time.

Trace fixtures may later include expected output streams:

```json
{
  "id": "policy-alert",
  "call": {
    "export": "run",
    "args": [1]
  },
  "expect": {
    "return": 1,
    "outputs": [
      {
        "channel": "alert",
        "id": 17,
        "args": [1, 0, 0, 0],
        "flags": 0
      }
    ]
  }
}
```

Future mismatch categories:

- `missing-event`: expected tuple was not emitted;
- `extra-event`: emitted tuple was not expected;
- `wrong-id`: tuple ID differs;
- `wrong-channel`: tuple channel differs;
- `wrong-args`: scalar args differ;
- `wrong-flags`: flags differ;
- `unsupported-profile`: selected profile does not support the declared output
  channel/import.

This model depends on a future accepted output contract. Until then,
conformance/replay remains limited to the implemented first-slice observable
outputs.

## Conformance Report Schema

The conformance report should be deterministic JSON:

```json
{
  "schemaVersion": "0.16",
  "kind": "air.conformance.report",
  "package": "policy-audit-package",
  "profile": "cli",
  "trace": {
    "id": "policy-audit-basic",
    "fingerprint": "sha256:..."
  },
  "status": "pass",
  "mismatches": [],
  "unsupported": {
    "profile": false,
    "features": []
  },
  "diagnostics": []
}
```

Required report fields:

- `schemaVersion`;
- `kind`;
- package id/name;
- profile id;
- trace id;
- trace fingerprint;
- status: `pass` or `fail`;
- mismatches;
- unsupported profile/features;
- diagnostics.

Reports must not contain timestamps or absolute local paths.

## CLI Shape

Implemented first-slice command:

```sh
node bin/airc.js conformance <package-dir> --profile <profile> --trace <trace.json> --json
```

Current first-slice semantics:

- package-check/profile validation runs before replay;
- built package Wasm is required;
- exported scalar function calls are replayed from the trace;
- trace JSON is deterministic and package/profile scoped;
- unsupported profile/features fail clearly;
- output is deterministic JSON;
- no Host ABI import is added by the conformance command.

## Build-Time / Runtime Boundary

AIR owns verified package semantics, capability use, host import declarations,
and package reports. Hosts own platform policy, rendering/audio/resource
loading, and declared capability implementation.

Conformance/replay fixtures should make host behavior observable through
declared inputs, outputs, imports, resources, and reports. They must not depend
on demo assets or hidden TypeScript/native logic as Core evidence.

## ABI Impact

Conformance reporting does not automatically change AIR ABI or Host ABI.

Host ABI review is required if replay/conformance introduces new host imports,
changes host import signatures, or changes required host import semantics.

## Acceptance Tests

- profile declares required conformance evidence;
- conformance fixture can be run without active demo assets;
- fixture with expected exported function result passes;
- fixture with wrong expected exported function result fails;
- unsupported imports fail deterministically;
- unsupported profile fails clearly;
- replay inputs and outputs are stable JSON or documented binary fixtures;
- reports identify host profile, ABI versions, supported imports, unsupported
  imports, and conformance status;
- report output is deterministic across runs;
- no Host ABI bump is required.

## Risks

- conformance fixtures may become too host-specific to remain portable;
- replay evidence may be overread as domain correctness;
- visual/audio comparison policy may become flaky if introduced before stable
  fixture rules.

## Deferred Items

- richer replay traces;
- visual/audio golden comparison policy;
- output stream conformance after an accepted event/output Host ABI;
- cross-host conformance dashboard;
- browser/GPU manual smoke automation;
- remote conformance result collection.
