# AIR v0.25 RFC: Host Interaction Contract

Status: design / planning

Purpose: define the contract between AIR-authored intent, package metadata,
verification/report evidence, and host-owned execution before any Host ABI
`0.11` promotion.

This RFC is documentation only. It does not add host imports, implement
`output.emit`, change AIR ABI, change Host ABI, add runtime JSON, or grant raw
host authority.

## 1. Contract Summary

The intended flow is:

```text
AI/domain intent
-> small AIR module
-> verifier/audit/report
-> backend artifact, currently Wasm/airpkg
-> strict host profile
-> host-owned execution
```

AIR owns bounded deterministic intent, scalar facts, ids/handles, policy
decisions, effect declarations, capability usage, audit/report surfaces,
package/module graph, and conformance/evidence surfaces.

Hosts own raw platform objects, files, network, DOM, GPU, DB, secrets, external
API access, real side effects, resource loading, platform permissions,
rendering, audio, and platform integration.

## 2. Current Host Interaction Without Host ABI `0.11`

Host interaction is already possible as declared intent and evidence:

- `outputContracts` describe stable output ids, channels, capability needs, and
  scalar argument contracts;
- `commandBuffers` describe bounded scalar output-intent records referencing
  Output Contract ids;
- package-check validates that command records reference declared outputs;
- reports and verification evidence expose fingerprints, command counts, used
  output ids, diagnostics, and ABI status;
- conformance replay compares deterministic expected records;
- the reference mock host policy executor applies deterministic allow/deny
  policy fixtures to command buffers and emits `air.hostInteractionEvidence`;
- host profiles say whether an existing public Host ABI profile supports the
  selected capabilities/imports/resources.

This model does not perform side effects automatically. It gives a host policy
enough information to decide whether an intent may be executed by host-owned
code.

## 3. Source Of Truth

| Surface | Source of truth |
| --- | --- |
| AIR behavior | `.air` source modules and verifier/lowering rules |
| Package graph | `air.package.json` |
| Output ids and schemas | package-local `outputContracts` |
| Command intent records | package-local `commandBuffers` |
| Host profile compatibility | selected host profile metadata |
| Evidence | verification evidence / report JSON |
| Real execution | host policy and host runtime, outside AIR Core |

Command buffers and Output Contracts are package metadata. They are not Host ABI
imports and not AIR runtime objects.

## 4. Host Policy Boundary

Host policy decides whether declared AIR output intents are allowed, denied, or
unsupported. The policy may use package metadata, selected host profile, command
records, verification evidence, and conformance traces.

Host policy must not be confused with AIR authority:

- AIR may request or describe intent;
- host policy may allow or deny intent;
- host runtime may execute side effects only under host-owned rules;
- AIR Core must not gain raw platform APIs to bypass host policy.

## 5. Report And Evidence Requirements

Host interaction evidence should distinguish:

- package declaration;
- AIR deterministic decision;
- command buffer intent;
- host profile compatibility;
- host policy decision;
- conformance result.

Evidence must avoid:

- timestamps;
- absolute paths;
- secrets/tokens/credentials;
- raw private payloads;
- raw URLs/logs/private text;
- host object handles;
- runtime JSON objects or maps as command payloads.

The implemented v0.25 verification evidence integration accepts an existing
`air.hostInteractionEvidence` artifact through:

```sh
node bin/airc.js verify package <package-dir> --profile <id> --host-evidence <hostInteractionEvidence.json> --json
```

Verification evidence embeds only a compact summary:

- status;
- policy id;
- host profile;
- decision count;
- denied capability count;
- diagnostics count;
- replay checksum.

It does not embed raw command payloads or grant host authority. If the supplied
host interaction evidence is failed or malformed, verification evidence fails
with a host interaction diagnostic.

## 6. What Requires Host ABI `0.11`

Host ABI `0.11` is required only if the runtime host boundary changes:

- a new public host import is accepted;
- an existing host import signature or semantics changes;
- `output.emit`, `output.event`, `audio.event`, or `effect.event` becomes a
  runtime import;
- host-side command-target behavior becomes public runtime ABI;
- the host must interpret new runtime-visible metadata to execute AIR calls.

Planning docs, package metadata, report fields, verification evidence, and
conformance fixtures do not require Host ABI `0.11`.

## 7. Raw Authority Rejection

The host interaction contract rejects:

- raw `chrome.*`;
- DOM/React/IndexedDB/Jira/fetch authority;
- DB/cloud SDK imports;
- host object handles;
- runtime JSON/object model;
- automatic host-side action execution;
- secrets, tokens, credentials, raw URLs, raw logs, or private text authority.

If a domain needs those capabilities, they stay host-owned and must be exposed
only through generic, capability-scoped, versioned, conformance-tested contracts
after a promotion gate.

## 8. Rollback And Compatibility

Host ABI `0.10` packages remain valid through Output Contracts, command
buffers, verification evidence, host profiles, and conformance replay.

A future Host ABI `0.11` candidate must be opt-in. Hosts without support must
fail package-check with a clear diagnostic before runtime. Where practical, a
future runtime import should have a downgrade path to command-buffer intent
metadata for verification and offline replay.

## 9. v0.25 Scope

v0.25 should define the contract, evidence, reference mock host design, and
negative-test plan. It should not implement `output.emit`, add Host ABI `0.11`,
or grant new host authority.
