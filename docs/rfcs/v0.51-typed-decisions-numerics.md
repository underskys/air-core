# AIR v0.51 Typed Decisions and Numeric Semantics

Status: Normative AIR v0.51 A2 specification.

Decision authority: `AIR-V051-DIRECT-GIT-A2-SPEC-2026-08-13-0001` and
`AIR-V051-DIRECT-GIT-A2-REVIEW-CORRECTION-2026-08-13-0002`

## Scope and Status

This RFC freezes the v0.51 semantic contract for exact `i64`, portable
`f32`/boundary `f64`, closed enums, `option<T>`, `result<T, E>`, and typed
`match`. It is a specification, conformance plan, and ABI-layout candidate.
It changes no current parser, verifier, lowerer, runtime, AIR ABI, Host ABI,
SDK, or package format. This specification authorizes no implementation,
exported ABI adoption, Host Contract version change, merge, release, or
publication. Candidate ABI and Host Contract decisions remain pending A1 final
architecture freeze and explicit human implementation authorization.

The words MUST, MUST NOT, SHOULD, and MAY are normative. A feature described
here is not admitted by a current implementation until its conformance vectors
pass on that implementation.

## Repository Audit and Decision Classes

The activation tree already accepts `i32`, `i64`, `f32`, `f64`, and `bool` in
the type layer; supports `const.i64` and `const.f64`; and lowers those constant
operations to Wasm scalar types. Existing source parsing stores numeric text as
JavaScript `Number`. It therefore cannot be treated as a precise source model
for every `i64` value, and current untyped numeric syntax is not extended by
this RFC. Existing `i32` and `f32` operations lower directly to Wasm
operations, including Wasm floating-point comparisons.

| Decision | Classification | Reason |
| --- | --- | --- |
| Existing `i32` syntax and operations | PRESERVES_EXISTING_BEHAVIOR | No v0.51 rule changes an admitted `i32` program. |
| Existing `f32` operations | PRESERVES_EXISTING_BEHAVIOR | The RFC names their portable Wasm model; it does not introduce altered arithmetic. |
| Exact signed `i64` literals and checked operations | MONOTONIC_EXTENSION | Existing acceptance of `i64` does not establish exact literal parsing or checked failure behavior. |
| Boundary-only `f64` | MONOTONIC_EXTENSION | `f64` remains a type, while general `f64` arithmetic is expressly not admitted. |
| Closed enums, option, result, and match | MONOTONIC_EXTENSION | They are new source and interface constructs. |
| Existing untyped numeric `Number(...)` parsing for new exact literals | INTENTIONAL_BREAK_REQUIRING_MIGRATION | A v0.51 implementation MUST parse exact `i64` literals without host-number loss. Existing source remains accepted under its existing compatibility lane. |
| Nested sum types, user-defined payload records, implicit conversions, general `f64` arithmetic, catchable checked arithmetic | DEFERRED | They require a later RFC and conformance corpus. |

## Common Type Rules

The first v0.51 typed-decision slice admits these value categories:

```text
primitive ::= i32 | i64 | f32 | f64 | bool
enum-type ::= a declared closed enum name
flat-value ::= primitive | enum-type
option-type ::= option<flat-value>
result-type ::= result<flat-value, error-enum-type>
decision-type ::= enum-type | option-type | result-type
```

`option<option<T>>`, `option<result<T,E>>`, `result<option<T>,E>`,
`result<result<T,E>,E2>`, slices, borrowed slices, pointers, arrays, buffers,
vectors, structs, host handles, and opaque values are not payloads in this
slice. A verifier MUST reject an unsupported payload with
`air.decision.payload_type_unsupported`.

There are no implicit numeric conversions, implicit enum-to-`i32`
conversions, truthiness conversions, or implicit option/result unwraps. Every
conversion operation named below is explicit and is part of the source type.

## Canonical Numeric Source Form

The established typed-IR form remains the canonical literal carrier:

```air
%a:i32 = const.i32 -2147483648
%b:i64 = const.i64 9223372036854775807
%c:f32 = const.f32 1.25
%d:f64 = const.f64 -0.0
%e:bool = const.bool true
```

The operation determines the literal type. A conforming v0.51 parser MUST
retain the literal spelling until it validates the target type. It MUST NOT
first convert an `i64` literal through a host floating-point number.

The canonical grammar is:

```text
integer       ::= "-"? ("0" | nonzero-digit digit*)
decimal       ::= "-"? ("0" | nonzero-digit digit*) "." digit+
                | "-"? ("0" | nonzero-digit digit*) exponent
                | decimal exponent
exponent      ::= ("e" | "E") ("+" | "-")? digit+
i32-literal   ::= integer in [-2147483648, 2147483647]
i64-literal   ::= integer in [-9223372036854775808, 9223372036854775807]
float-literal ::= decimal | integer
```

`NaN`, `Infinity`, hexadecimal float syntax, digit separators, and suffixes
are not source literals in this slice. They may be supplied only through the
typed host boundary described below. The formatter emits decimal integer text
without a leading `+` or redundant leading zero, and emits the accepted source
form for finite float literals. It does not fabricate a source spelling for a
non-finite runtime value.

For `i32` and `i64`, source `-0` is accepted and canonicalizes to `0`; integer
values have no signed-zero identity. Finite decimal `const.f32` and `const.f64`
literals MUST be converted directly once to their target IEEE 754 binary32 or
binary64 format with deterministic correctly-rounded round-to-nearest,
ties-to-even semantics. A host `Number(...)`, `Double(...)`, locale, or
intermediate wider/lower format is not semantic authority. Float `-0`, `-0.0`,
and equivalent accepted decimal spellings preserve the negative-zero sign bit.

The formatter emits an integer-looking finite float with a float-distinguishing
spelling: `const.f32 1` formats as `const.f32 1.0`, and `const.f64 -0` formats
as `const.f64 -0.0`. It never erases float negative zero.

## `i32`

`i32` remains a two's-complement signed 32-bit integer. Existing `i32`
arithmetic preserves its existing target semantics. New typed-decision
constructs never coerce an enum discriminant to `i32`; an explicit future
conversion would require a separate operation and RFC.

## Exact `i64` and Checked Arithmetic

`i64` is a two's-complement signed 64-bit integer with the inclusive range
`[-9223372036854775808, 9223372036854775807]`. Its mathematical operation
model is exact signed integer arithmetic, not JavaScript `Number` arithmetic.

The normative checked operation family is exactly:

```text
i64.checked_add
i64.checked_sub
i64.checked_mul
i64.checked_div_s
i64.checked_rem_s
i64.checked_neg
i64.to_i32_checked
i32.to_i64
```

The exact comparison family is `i64.eq`, `i64.ne`, `i64.lt_s`, `i64.le_s`,
`i64.gt_s`, and `i64.ge_s`. Each comparison is total and deterministic over
exact signed `i64` values and never uses the checked-failure path.

`checked_add`, `checked_sub`, and `checked_mul` fail on overflow.
`checked_neg(MIN)` fails on overflow; `checked_neg(0)` returns exact zero.
`checked_div_s(x, 0)` and `checked_rem_s(x, 0)` fail with division by zero.
`checked_div_s(MIN, -1)` fails on overflow. In contrast,
`checked_rem_s(MIN, -1)` returns exact `i64` zero because the mathematical
remainder is representable. A statically provable invalid expression is a
verification failure with source location.

### Canonical Runtime Failure Model

There is exactly one dynamic failure model: an operation terminates through the
stable AIR checked-numeric failure path, with code
`air.numeric.checked_failure` and a canonical reason from `overflow`,
`division_by_zero`, or `invalid_conversion`. It is not a JavaScript exception,
host-language exception, silent wraparound, saturation, `option`, or `result`.
Implementations MAY represent the failure as a target trap internally, but the
host-facing result MUST preserve the AIR code and reason.

This first slice has no catchable checked-arithmetic expression. A later
`try_checked`/`result` integration must be a new RFC; it cannot silently alter
the behavior above.

Permitted conversions are `i32.to_i64` (sign extension) and
`i64.to_i32_checked`. The latter uses the same checked-numeric failure path
when out of range. No implicit widening or narrowing is permitted.

### Static/Dynamic and Refinement Precedence

1. A statically provable invalid arithmetic expression fails verification at
   its source location.
2. A dynamic arithmetic failure uses `air.numeric.checked_failure`.
3. If arithmetic succeeds and assignment targets a refinement, the refinement
   is evaluated after arithmetic.
4. Arithmetic failure takes precedence over refinement failure.
5. A refinement failure uses the existing canonical identity
   `air.refinement.assignment_out_of_range`, not
   `air.numeric.checked_failure`.

No JavaScript, Swift, CPU, or Wasm exception text is canonical AIR evidence.

At a JavaScript host boundary, exact `i64` values use `bigint`. JSON evidence
uses the typed form `{ "type": "i64", "decimal": "-42" }`; a JSON number is
not a valid `i64` transport.

## `f32`

`f32` is IEEE 754 binary32 with Wasm binary32 operation semantics. Existing
admitted `f32` operations retain their operation order and target behavior.

- `+0.0` and `-0.0` compare equal; their sign is preserved in evidence.
- Any ordered comparison with NaN is false.
- `f32.ne` with NaN is true.
- `f32.min`, `f32.max`, and conversions retain the chosen Wasm operation's
  behavior; a later implementation MUST test it against the vector corpus.
- Finite source literals round once to binary32 at `const.f32` construction.

Cross-host semantic evidence represents finite values, infinities, and signed
zero by raw IEEE binary32 bits as eight lowercase hexadecimal digits, for
example `{ "type": "f32", "bits": "80000000" }`. A NaN result is represented
as `{ "type": "f32", "classification": "nan" }`. NaN payload and sign are
explicitly excluded from cross-host semantic equality in this slice; an
implementation MUST NOT claim payload portability merely because one engine
preserved a payload.

The host transport for finite values is a JavaScript `number` or Swift
`Float`; non-finite values use the typed evidence form when serialization is
required, because JSON has no finite numeric representation for them.

## Boundary-Only `f64`

`f64` is IEEE 754 binary64. This RFC admits `const.f64`, local/pass/return
transport, `f32.to_f64`, `f64.to_f32_checked`, and exact bit-preserving host
boundary transport. It does **not** admit general `f64` arithmetic, ordering,
or implicit conversion.

`f32.to_f64` is exact widening. `f64.to_f32_checked` has these exact outcomes:

| Input class | Result |
| --- | --- |
| finite exactly representable binary32 value | returns that binary32 value |
| finite lossy value | `air.numeric.checked_failure` / `invalid_conversion` |
| positive infinity | returns positive binary32 infinity |
| negative infinity | returns negative binary32 infinity |
| NaN | returns binary32 NaN; payload/sign portability is not claimed |
| positive zero | returns positive binary32 zero |
| negative zero | returns negative binary32 zero |

For finite values, exact representability means direct binary32 rounding and
back-conversion compare equal as binary64 values. This prevents an undocumented
lossy conversion surface.

`f64` evidence uses sixteen lowercase hexadecimal bits for finite values,
infinities, and signed zero. NaN uses
`{ "type": "f64", "classification": "nan" }`; payload and sign are excluded
from cross-host semantic equality. Host values are JavaScript `number` and
Swift `Double`, with typed evidence required for non-finite JSON transport.

## `bool`

`bool` has exactly `false` and `true`. In a Wasm scalar lane it is represented
as `i32` zero or one; any other incoming representation is invalid. Boolean
evidence is the JSON literal `false` or `true`. There is no numeric truthiness
conversion.

## Closed Enums

The canonical declaration has explicit stable discriminants:

```air
enum Admission {
  deny = 0,
  allow = 1
}

error enum ParseError {
  malformed = 1,
  unsupported = 2
}
```

```text
enum-decl       ::= ("error" SP)? "enum" SP TypeName "{" enum-case* "}"
enum-case       ::= Identifier "=" nonnegative-i32 ","
nonnegative-i32 ::= integer in [0, 2147483647]
```

Every discriminant is mandatory, unique within its enum, and fits a signed
`i32` ABI lane. Names are module-scoped and a value is written
`TypeName.caseName`. An `error enum` is still a closed enum but is eligible as
the `E` in `result<T,E>`; an ordinary enum is not. Formatter output sorts cases
by discriminant, then preserves the canonical `name = decimal,` spelling.
Declaration order has no semantic effect.

The canonical value is
`{ "type": "example.module::Admission", "discriminant": 1 }`.
The case name is evidence display data validated against the type declaration,
not a second authority. Unknown discriminants fail closed at a boundary and at
match lowering with `air.decision.enum_discriminant_invalid`.

## Canonical Type Identity and Evidence

Canonical type identities are formatter-defined ASCII strings with no optional
whitespace:

```text
primitive-type-id ::= i32 | i64 | f32 | f64 | bool
enum-type-id      ::= module-id "::" type-name
option-type-id    ::= "option<" canonical-type-id ">"
result-type-id    ::= "result<" canonical-type-id "," error-enum-type-id ">"
```

Every declared enum/error enum includes its module identity. Display names are
not authority; aliases resolve before evidence serialization; evidence never
uses an ambiguous unqualified enum name. Nested scalar evidence reuses the
scalar form, so `option<i64>` `some` contains
`{ "type": "i64", "decimal": "7" }`, never JSON number `7`.

Typed-value evidence is a canonical JSON record: object keys are serialized in
code-point ascending order, arrays preserve declared order, UTF-8 is used
without insignificant whitespace, and integers are decimal strings only where
their scalar rule requires it. This defines typed-value bytes/records only; A3
defines receipt and decision digest domains. A repository evidence serializer
may be used only when it produces exactly these bytes.

Scalar evidence is: `i32` JSON number; `i64` typed decimal object; `bool` JSON
literal; `f32`/`f64` bits or `classification: "nan"` as specified above.

## `option<T>` and `result<T,E>`

Canonical types and constructors are:

```air
%none:option<i32> = option.none<i32>
%some:option<i32> = option.some<i32> %value
%ok:result<i32, ParseError> = result.ok<i32, ParseError> %value
%err:result<i32, ParseError> = result.err<i32, ParseError> ParseError.malformed
```

Tags are stable: `option.none = 0`, `option.some = 1`, `result.ok = 0`, and
`result.err = 1`. A tag outside its declared set is invalid. Inactive payload
bytes MUST be zero in every canonical ABI/evidence representation. An
`option.some` contains exactly one `flat-value`; a `result.err` contains an
error-enum discriminant only. No implicit unwrap, default, or exception bridge
exists.

Canonical evidence is one of:

```json
{ "tag": "none", "type": "option<i32>" }
{ "tag": "some", "type": "option<i64>", "value": { "decimal": "7", "type": "i64" } }
{ "tag": "ok", "type": "result<i32,example.module::ParseError>", "value": 7 }
{ "error": { "discriminant": 1, "type": "example.module::ParseError" }, "tag": "err", "type": "result<i32,example.module::ParseError>" }
```

Equality is type-directed. Enums are equal only if canonical type identity and
discriminant match. Options satisfy `none == none`, `some(a) == some(b)` by
payload equality, and `none != some(_)`. Results satisfy `ok(a) == ok(b)` by
success equality, `err(a) == err(b)` by exact error-enum equality, and
`ok(_) != err(_)`. Invalid tags/discriminants fail; they are never merely
unequal. NaN payload equality follows scalar NaN semantics. Ordering is not
admitted for enum, option, or result.

## Typed `match`

`match` is an expression with an explicit destination type and atom-valued
arms. It has no wildcard/default arm in this slice:

```air
%out:i32 = match %decision {
  Admission.deny => %deny_value,
  Admission.allow => %allow_value
}

%out:i32 = match %maybe {
  none => %fallback,
  some(value) => %value
}

%out:i32 = match %outcome {
  ok(value) => %value,
  err(error) => %fallback
}
```

```text
match-expression ::= destination "=" "match" value "{" match-arm+ "}"
destination      ::= local-name ":" canonical-type-id
match-arm        ::= pattern SP "=>" SP arm-atom arm-separator
pattern          ::= enum-type-id "." case-name | "none" | "some(" binding ")"
                    | "ok(" binding ")" | "err(" binding ")"
arm-separator    ::= "," | ";"
arm-atom         ::= local-name | typed literal | qualified enum case
binding          ::= local identifier without `%`
```

The formatter emits one arm per line, comma separators, and enum arms sorted
by ascending discriminant; `none` then `some`, and `ok` then `err`. Source arm
order never changes selection. A duplicate arm, unknown case/tag, missing arm,
or impossible/unreachable arm is rejected. A binding is in scope only for its
arm atom; it MUST NOT shadow an existing local or another match binding. The
diagnostic locates the missing/duplicate/unknown arm when it exists, otherwise
the `match` expression. Arm atoms must type-check against the explicit
destination type; no implicit common-supertype inference occurs.

For a closed enum, every declared discriminant appears exactly once. `option`
requires `none` and `some(binding)`. `result` requires `ok(binding)` and
`err(binding)`. Refinements may narrow but never widen the declared target.

Lowering is specified as a deterministic discriminant/tag dispatch ordered by
ascending canonical tag or discriminant. It MUST take an AIR invalid-tag trap
path for an invalid dynamic tag/discriminant, never a host default. This is a
lowering shape only; no lowering is implemented by this RFC.

## ABI, Host Contract, and Layout Candidate

The following is the required candidate layout for A1 approval. It is not an
ABI version bump made by this task.

| Type | Candidate canonical layout | Alignment |
| --- | --- | --- |
| closed enum | one `i32` discriminant | 4 |
| `option<bool/i32/f32/enum>` | `tag:i32 @0`, payload word `@4` | 4 |
| `option<i64/f64>` | `tag:i32 @0`, zero padding `@4..7`, payload `@8` | 8 |
| `result<T,E>` | 16 bytes: `tag:i32 @0`, zero `@4..7`, value/error lane `@8` | 8 |

For `result<T,E>`, an `ok` uses the lane for `T`; an `err` places the error
`i32` discriminant in the low four bytes of the lane and zeroes all other
bytes. Every multi-byte scalar, tag, discriminant, padding region, and payload
lane is little-endian. All padding and inactive bytes are zero. Native Swift
`Optional<T>`, Swift `Result<T,E>`, JavaScript object, and native host enum
layouts are API conveniences only, never AIR ABI. A host binding validates AIR
type identity, tag, and discriminant before it constructs any native form.
Multi-value lowering is permitted only if its behavior and serialized canonical
layout are equivalent.

Internally, a compiler may use existing scalar lanes. An exported enum,
option, result, typed match interface descriptor, or typed evidence contract
is an **AIR ABI change candidate requiring A1 approval**, because it adds
externally observable type and layout metadata. It is also a **Host Contract
change candidate requiring A1 approval**, because JavaScript and Swift need
validated tagged-value mappings. No v0.50 ABI lane is reinterpreted.

Host mapping candidates are: JavaScript uses explicit tagged objects at JSON
and generic host boundaries; Swift uses `enum`/`Optional`/`Result` only after
the binding verifies the declared AIR type and discriminant. Neither host may
infer a case from a string alone. Unknown fields and unknown tags fail closed.

## `.airpkg` Boundary Decision

`.airpkg` is not a mandatory semantic boundary for A2, A3, or the first v0.51
Core slices. It is optional versioned transport/tooling, never an authority
source. Canonical typed semantics, evidence, and the unpacked verified artifact
layout are container-neutral. Before a Swift shipping loader relies on an
`.airpkg`, its validator MUST support every admitted AIR ABI lane. A1 decides
the shipping transport. This RFC therefore neither fixes nor extends `.airpkg`.

## Diagnostics and Migration

New stable diagnostic families are `air.numeric.*` and `air.decision.*`.
Relevant codes include `air.numeric.i64_constant_out_of_range`,
`air.numeric.checked_failure`, `air.decision.payload_type_unsupported`,
`air.decision.enum_discriminant_invalid`, `air.decision.enum_duplicate_discriminant`,
and `air.decision.match_nonexhaustive`. Diagnostics MUST include source
location when known and MUST NOT surface a raw host stack as a user diagnostic.

Existing packages remain in their declared ABI lane. A migration to an exposed
typed-decision boundary requires an A1-approved ABI/Host Contract lane and a
new interface descriptor; it must not silently reinterpret an old `i32` as an
enum or tag.

## Deferred and Non-Goals

This RFC does not admit arbitrary precision integers, unsigned integer source
types, decimal arithmetic, `f64` general arithmetic, recursive/anonymous sum
types, payload structs, wildcard matches, exception interoperation, implicit
conversion, `.airpkg` transport changes, or any automatic zero-copy claim.

## Implementation Gates

Implementation remains prohibited by this A2 document. It may begin only after
A1 approves the ABI and Host Contract candidates **and** an explicit human
implementation authorization is issued. It MUST preserve legacy v0.50 behavior
and pass every required vector before it claims this RFC's feature set.
