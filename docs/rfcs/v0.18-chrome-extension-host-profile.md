# AIR v0.18 RFC: Chrome Extension Host Profile Pressure

Status: draft RFC

Target milestone: v0.18

## Purpose

FlowDesk Air creates non-game pressure for a future Chrome Extension host
profile. The pressure is useful because Chrome extensions combine policy
decisions, local state, notifications, timers, browser permissions, storage, and
UI surfaces. AIR should be able to own deterministic bounded decisions without
owning browser authority.

This RFC defines host profile pressure only. It does not implement Chrome APIs,
does not expose raw `chrome.*` authority, and does not add Host ABI imports.

## Hard Boundary

AIR does not access `chrome.*` directly.

The host owns:

- browser permissions;
- MV3 service worker lifecycle;
- popup and DOM/React UI;
- content scripts;
- IndexedDB/Dexie and other storage implementation details;
- fetch/Jira/external API access;
- encryption, secrets, tokens, and vaults;
- raw URLs, page content, task text, notes, and private data;
- Chrome API scheduling, errors, retries, and permission prompts.

AIR receives only:

- minimized scalar facts;
- bounded fact snapshots;
- generated handles;
- package-checked data contracts.

AIR may emit bounded command intents only if a future ABI/profile accepts that
contract through RFC, Host ABI spec, profile support, package-check/report
visibility, conformance fixtures, and tests.

## Scope

This RFC defines support levels a future Chrome Extension profile may describe:

- MV3 service worker;
- popup;
- content script;
- storage;
- context menus;
- active tab;
- scripting;
- alarms;
- notifications.

The profile should describe what the host can provide, how AIR-visible facts are
minimized, and what capabilities are available. It must not grant AIR raw
browser API access.

## Support Level Model

A future profile should use explicit support levels instead of implying full
Chrome authority.

Candidate support levels:

- `unsupported`: host does not provide the feature;
- `host-owned`: host may use the feature internally, but AIR cannot access it;
- `fact-source`: host may convert feature state into bounded scalar facts;
- `command-target`: future profile may accept bounded command intents after an
  accepted event/output contract;
- `conformance-only`: feature appears only in deterministic fixtures/tests.

Candidate profile matrix:

| Profile area | Minimum v0.18 status | AIR-visible shape |
| --- | --- | --- |
| MV3 service worker | `host-owned` / `fact-source` | bounded lifecycle and wake facts only |
| popup | `host-owned` / `fact-source` | bounded view/filter/selection facts only |
| content script | `host-owned` / `fact-source` | minimized page classification facts only |
| storage | `host-owned` / `fact-source` | bounded sync/cache/version facts only |
| context menus | `host-owned` / future `command-target` | bounded action IDs only after accepted output contract |
| active tab | `host-owned` / `fact-source` | minimized tab class/trust facts only |
| scripting | `host-owned` / `conformance-only` | completion/status facts only; no script source |
| alarms | `host-owned` / future `command-target` | bounded alarm policy intent only after accepted output contract |
| notifications | `host-owned` / future `command-target` | bounded notification intent only after accepted output contract |

## Profile Areas

### MV3 Service Worker

The service worker is host-owned. It may schedule work, handle extension
events, process alarms, and maintain lifecycle state. AIR may receive minimized
scalar facts such as:

- wake reason ID;
- policy tick count;
- bounded timer state;
- pending request count;
- last error category ID.

AIR must not own service worker lifecycle, event listeners, or platform
scheduling.

### Popup

The popup is host-owned UI. AIR may receive bounded scalar facts about popup
state such as:

- current view ID;
- selected task handle;
- filter mode ID;
- visible row count.

AIR must not manipulate DOM, React state, CSS, event listeners, or browser UI
objects.

### Content Script

Content scripts are host-owned. They may extract minimized facts from pages only
under host policy. AIR may receive facts such as:

- page classification ID;
- trusted domain category ID;
- bounded link count;
- active form risk score.

AIR must not access DOM nodes, page text, raw URLs, cookies, or content script
objects.

### Storage

Chrome storage, IndexedDB, Dexie, and backup import/export are host-owned. AIR
may receive bounded facts such as:

- stored item count;
- sync status ID;
- local cache freshness bucket;
- policy version handle.

AIR must not access storage APIs, database handles, raw records, keys, or
encrypted values.

### Context Menus

Context menus are host-owned UI/platform surfaces. AIR may receive facts such
as:

- menu context ID;
- selected action ID;
- enabled policy flags.

Future command intents may request host-owned menu state changes only after an
accepted output/event contract.

### Active Tab

Active tab is host-owned browser authority. AIR may receive minimized facts such
as:

- tab class ID;
- tab trust score;
- page age bucket;
- permission state ID.

AIR must not receive raw URLs, page content, tab objects, browser handles, or
permission objects by default.

### Scripting

Chrome scripting is host-owned. AIR may receive facts about whether a host-owned
scripting action is allowed or completed. AIR must not define script source,
execute JavaScript, or hold script handles.

### Alarms

Alarms are host-owned scheduling. AIR may receive facts such as:

- alarm policy ID;
- next wake bucket;
- overdue flag;
- retry bucket.

Future bounded command intents may request alarm policy changes only after an
accepted output/event contract. No promises or callbacks are introduced into
AIR.

### Notifications

Notifications are host-owned UI/platform output. AIR may receive facts about
notification policy and may, in a future accepted output contract, request a
bounded notification intent. That future path must be capability-gated,
profile-gated, report-visible, and conformance-testable.

AIR must not call notification APIs directly.

## Fact Boundary

Chrome Extension hosts should convert rich browser/application state into
bounded structured facts before calling AIR.

Fact conversion rules:

- minimize data;
- use scalar IDs and bounded ranges;
- avoid raw private strings;
- avoid raw URLs and page content;
- avoid tokens, secrets, and notes;
- document host-owned conversions;
- make schemas package-checkable where possible.

See [Bounded Structured Facts](v0.18-bounded-structured-facts.md).

## Output Intent Boundary

AIR may emit bounded command intents only if a future Host ABI/profile accepts
an output contract.

Until then:

- output-events manifests are tooling-only;
- `debug.metric` remains diagnostics-only;
- hosts must not infer notification, alarm, menu, tab, or scripting commands
  from debug metrics or unrelated AIR state.

See [Output-Events Manifest Tooling](v0.18-output-events-manifest.md).

## Async Boundary

Chrome APIs are asynchronous, but AIR must not adopt JS promises, callbacks, or
async/await.

Future async pressure should use bounded request-handle concepts aligned with
existing bounded polling principles:

- host creates and owns async requests;
- AIR observes bounded scalar request status;
- host owns retries, permissions, errors, and scheduling;
- package-check/report expose required capabilities and profile support.

Candidate request-state facts should stay scalar and bounded:

- request handle ID;
- request kind ID;
- status ID;
- retry bucket;
- timeout bucket;
- last error category ID.

AIR must not receive a promise, callback, JavaScript object, Chrome request
object, response object, or host-side continuation.

## Non-goals

- No raw Chrome APIs in AIR.
- No raw `chrome.*`.
- No DOM/React authority.
- No IndexedDB/Dexie access.
- No fetch/Jira access.
- No secrets, tokens, encryption keys, or vault authority.
- No arbitrary JSON object model.
- No JS promises or async/await.
- No host object handles.
- No runtime imports.
- No Host ABI change.
- No AIR ABI change.
- No extension-specific Core semantics.

## ABI Impact

This RFC does not change AIR ABI.

AIR ABI remains `0.10` because this profile is a planning/profile document and
does not change executable representation, calling convention, memory/data
layout, entrypoint semantics, or runtime-required package metadata.

This RFC does not change Host ABI.

Host ABI remains `0.10` because no host imports are added or changed. A future
extension command/fact ABI would require separate RFC/spec/profile/tests and
independent evidence beyond FlowDesk Air.

## Acceptance Tests

Future profile/tooling tests should cover:

- profile declares support levels for each Chrome extension area;
- raw `chrome.*` imports fail strict Host ABI validation;
- profile-supported facts are scalar and bounded;
- private text, raw URLs, tokens, and notes are absent from default reports;
- unsupported profile feature fails deterministically;
- output command intents remain rejected until an accepted output/event contract
  exists;
- `debug.metric` cannot be used as notification/alarm/menu/tab/scripting event
  bus;
- AIR ABI remains `0.10`;
- Host ABI remains `0.10`.

## Open Questions

- Which support levels are stable enough for a profile schema?
- Should Chrome Extension profiles live in `data/host_profiles/` only after
  tooling exists, or remain RFC-only until evidence is broader?
- How should privacy classifications map to browser-owned data categories?
- What second non-FlowDesk extension-like use case is required before promotion?
