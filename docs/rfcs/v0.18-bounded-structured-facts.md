# AIR v0.18 RFC: Bounded Structured Facts

Status: draft RFC

Target milestone: v0.18

## Purpose

AIR needs ergonomic structured inputs without becoming a dynamic object runtime.
Current `i32`/`bool` scalar parameters are sufficient for small decisions, but
they do not scale for bounded task summaries, policy facts, dashboard state,
network allowlists, CI pipeline facts, or interactive package inputs.

This RFC defines a bounded, deterministic, package-checked data contract model:

- bounded fact snapshots;
- static schemas;
- fixed-size scalar tables;
- tablegroups as RFC / possible first slice;
- generated handles;
- package-checked data contracts;
- report visibility;
- conformance compatibility.

The design goal is reviewable structured facts with explicit bounds, stable
metadata, deterministic diagnostics, and no hidden host authority.

This is not a JSON format for AIR runtime objects. It is a
boundary-of-authority contract that lets hosts present minimized, bounded scalar
facts to AIR while keeping rich application state and side-effect authority
outside AIR.

v0.20 extends this direction with bounded rowset schema metadata through the
existing `factSchemas` package metadata path. See
[AIR v0.20 RFC: Bounded Rowset Schema Metadata](v0.20-bounded-rowsets.md).
Rowset schemas are package metadata/tooling contracts, not tablegroups or AIR
runtime JSON objects.

## Contract Taxonomy

Bounded structured facts follow this authority pipeline:

```text
Host rich state
-> minimized facts
-> AIR bounded schema
-> AIR deterministic decision
-> output intent
-> host policy execution
```

Each stage has an explicit owner:

| Layer | Owns |
| --- | --- |
| Host | Raw objects, URLs, strings, secrets, Chrome APIs, IndexedDB, DOM/React, browser permissions, encryption, external APIs, and rich application state. |
| AIR | IDs, flags, counters, bounded scalar facts, static table reads, and deterministic decisions. |
| Manifest/schema | Shape, limits, enum IDs, privacy policy, generated handle definitions, and package-visible data contract metadata. |
| Report | Usage, violations, missing or stale generated state, schema diagnostics, privacy classifications, and repair hints. |
| Host policy | Execution permission, side-effect authorization, browser/platform authority, output intent filtering, and final action dispatch. |

AIR may compute an output intent as a scalar decision, but host policy owns
whether that intent becomes an action. This is especially important for browser,
DevOps, notification, dashboard, and workflow automation use cases.

## Scope

This RFC covers source/package/tooling design for structured facts:

- schema files that define bounded fact shapes;
- scalar-only fact fields;
- fixed maximum row counts;
- static readonly scalar tables;
- tablegroups that keep related scalar tables aligned;
- generated symbolic handles for schema IDs, field IDs, enum-like values, and
  tablegroup IDs;
- package-check validation of schema/fact/table consistency;
- report-visible metadata and diagnostics;
- conformance fixtures that use deterministic fact snapshots.

Runtime loading and host imports are out of scope for v0.18 unless a separate
RFC changes the executable package contract.

## Use Cases

- FlowDesk task/status/link/note summaries after the host minimizes rich
  browser state into scalar facts;
- DevOps/SRE policy facts, service capability matrices, and deployment target
  tables;
- network allowlists, endpoint classes, and policy IDs;
- CI pipeline facts, step statuses, and gate decisions;
- dashboards that score bounded rows of state;
- interactive demos that need bounded state summaries without game-specific Core
  APIs.

## Non-goals

- No arbitrary JSON object model inside AIR.
- No dynamic maps.
- No GC.
- No reflection.
- No host object handles.
- No raw browser APIs.
- No DOM/React, IndexedDB/Dexie, fetch/Jira, token, secret, URL, or private text
  authority in AIR.
- No JS promises or async/await in AIR.
- No runtime imports.
- No mutable dynamic containers.
- No unbounded arrays.
- No implicit host-owned source-of-truth transformation hidden from reports.

## Data Model

### Bounded Fact Schema

A bounded fact schema defines one or more fact collections with:

- stable numeric `id`;
- stable `name`;
- fixed `maxRows`;
- scalar field list;
- optional field ranges;
- optional enum-like ID sets;
- optional privacy classification;
- optional capability/profile requirements;
- optional generated handle metadata.

Schema-level privacy metadata is intentionally small:

```json
{
  "privacyPolicy": {
    "defaultClassification": "minimized",
    "forbiddenByDefault": ["raw_text", "raw_url", "token", "secret", "note"]
  }
}
```

Allowed privacy classifications in the first implementation:

- `public`;
- `minimized`;
- `sensitive`;
- `forbidden`.

`privacyPolicy.forbiddenByDefault[]` is a stable marker list, not a policy DSL.
Examples include `raw_text`, `raw_url`, `token`, `secret`, and `note`.

Allowed P0 field types:

- `i32`;
- `bool`;
- enum-like `i32` IDs declared through constants or generated handles.

Deferred field types:

- fixed byte/text views;
- packed bitsets;
- f32/fixed-point policy if needed by a separate RFC.

Example draft schema:

```json
{
  "schemaVersion": "0.18-draft",
  "facts": [
    {
      "id": 1,
      "name": "task_summary",
      "maxRows": 128,
      "privacy": "minimized",
      "capability": "policy.score",
      "fields": [
        { "name": "task_id", "type": "i32", "semantic": "generated_handle" },
        { "name": "status_id", "type": "i32", "enum": "task_status" },
        { "name": "priority", "type": "i32", "range": [0, 100] },
        { "name": "has_blocker", "type": "bool" },
        { "name": "age_hours", "type": "i32", "range": [0, 8760] }
      ]
    }
  ]
}
```

Candidate bounded facts schema JSON:

```json
{
  "schemaVersion": "0.18-draft",
  "package": "policy_audit_package",
  "privacyPolicy": {
    "defaultClassification": "minimized",
    "forbiddenByDefault": ["raw_text", "raw_url", "token", "secret", "note"]
  },
  "enums": [
    {
      "name": "task_status",
      "values": [
        { "name": "todo", "id": 1 },
        { "name": "blocked", "id": 2 },
        { "name": "done", "id": 3 }
      ]
    }
  ],
  "facts": [
    {
      "id": 1,
      "name": "task_summary",
      "maxRows": 128,
      "privacy": "minimized",
      "capability": "policy.score",
      "fields": [
        { "name": "task_id", "type": "i32", "semantic": "generated_handle" },
        { "name": "status_id", "type": "i32", "enum": "task_status" },
        { "name": "priority", "type": "i32", "range": [0, 100] },
        { "name": "has_blocker", "type": "bool" },
        { "name": "age_hours", "type": "i32", "range": [0, 8760] }
      ],
      "tablegroup": {
        "name": "task_summary_tables",
        "columns": ["task_id", "status_id", "priority", "has_blocker", "age_hours"]
      }
    }
  ],
  "generatedHandles": {
    "module": "generated/task_fact_handles.air",
    "generator": "tools/generate_fact_handles.js"
  }
}
```

This JSON is a candidate schema shape for tooling discussion. It is not runtime
AIR syntax, not a dynamic JSON object model inside AIR, and not an accepted
package manifest extension until a follow-up implementation task accepts it.

### Bounded Fact Snapshot

A fact snapshot is deterministic test/package input data that conforms to a
schema. It is not a runtime import and does not grant host authority.

Example draft snapshot:

```json
{
  "schemaVersion": "0.18-draft",
  "schema": "facts/task_policy.facts.json",
  "rows": {
    "task_summary": [
      {
        "task_id": 101,
        "status_id": 2,
        "priority": 80,
        "has_blocker": false,
        "age_hours": 12
      }
    ]
  }
}
```

Snapshot rules:

- no timestamps;
- no absolute paths;
- stable key ordering when emitted by tools;
- scalar values only;
- row count must be less than or equal to `maxRows`;
- unknown fields fail;
- missing required fields fail;
- values outside declared ranges fail;
- privacy-sensitive raw text, URLs, tokens, notes, or secrets are forbidden
  unless a host policy explicitly permits them.

## Fixed-Size Scalar Tables

AIR already supports static readonly scalar tables as deterministic data. v0.18
fact schemas should integrate with that model rather than introduce dynamic
containers.

Rules:

- table sizes are known at compile/package-check time;
- tables are readonly unless a separate mutable-pool RFC is accepted;
- access remains deterministic and guarded;
- table metadata appears in package reports;
- generated tables are derived artifacts and must pass freshness checks.

## Tablegroups

Tablegroups are RFC/P1 only in v0.18. They are the likely future ergonomic
bridge between scalar tables and structured facts, but they are not implemented
by the current bounded facts schema validator first slice and are not accepted
AIR syntax.

A tablegroup groups several scalar tables under one schema and shared length.
The syntax below is RFC-only candidate syntax:

```text
tablegroup task_summary length 128
  task_id: i32
  status_id: i32
  priority: i32
  has_blocker: bool
  age_hours: i32
end
```

Required tablegroup properties:

- tablegroups are fixed-size;
- every column has the same fixed length;
- column types are scalar;
- tablegroups are readonly first;
- row count is bounded and known;
- length is compile-time/package-check known;
- direct dynamic row allocation is not allowed;
- tablegroup metadata is report-visible;
- package-check catches mismatched table lengths;
- generated handle freshness applies to generated tablegroups.

Explicit non-goals:

- no methods;
- no references;
- no dynamic allocation;
- no maps;
- no GC;
- no object identity;
- no host object handles;
- no runtime imports;
- no mutable row/state model in the first slice.

Relationship to the current first slice:

- bounded facts schema validation is the active v0.18 tooling first slice;
- tablegroups may become future AIR source ergonomics for reading aligned
  fixed-size scalar data;
- tablegroups must lower to static scalar tables unless a future accepted ABI
  RFC explicitly changes runtime representation;
- tablegroups must not become objects, records with identity, host handles, or
  dynamically allocated containers.

Possible future first slice after RFC acceptance:

- schema/report/package-check only;
- generated readonly AIR tables from a fact schema;
- no new runtime representation.

Deferred:

- cross-module mutable tablegroup access;
- record-like syntax;
- fixed mutable pools;
- runtime row mutation;
- dynamic row allocation.

ABI policy:

- AIR ABI remains `0.10` if tablegroups are source-level sugar over static
  scalar tables and preserve the existing scalar table runtime representation;
- AIR ABI `0.11` is considered only if tablegroups require a new executable
  runtime representation, calling convention, memory/data layout, package
  metadata contract, or entrypoint semantics;
- Host ABI remains `0.10` because tablegroups do not add host imports or host
  authority.

Future tablegroup test plan:

- candidate syntax is rejected until a tablegroup RFC is accepted;
- schema metadata for aligned scalar columns validates without runtime objects;
- mismatched table lengths fail package-check;
- non-scalar columns fail;
- mutable tablegroups fail in readonly-first mode;
- dynamic allocation markers fail;
- maps, references, host handles, and object identity markers fail;
- generated readonly scalar tables are deterministic when generation is
  accepted;
- generated tablegroup handles are checked for freshness when generation is
  accepted;
- reports list tablegroup metadata without leaking raw private data;
- AIR ABI remains `0.10` for source-level sugar over static scalar tables.

## Privacy Boundaries

Bounded structured facts must preserve AIR's authority boundary. AIR should see
the minimum scalar facts needed for deterministic decisions, not raw application
objects or private data.

Privacy is P0 for this RFC. A bounded facts schema must carry privacy metadata
for fact collections, and privacy classification must be visible in
package-check/report output. The first implementation may enforce only basic
metadata and shape checks, but the boundary itself is not optional.

Host-owned data that is forbidden by default:

- raw task text;
- raw notes;
- raw URLs;
- tokens;
- secrets;
- encryption keys;
- browser permission objects;
- DOM nodes;
- IndexedDB/Dexie records;
- fetch/Jira response objects.

Privacy rules:

- schemas must declare privacy classification for each fact collection;
- schema-level `privacyPolicy.defaultClassification` may set the default
  classification for the schema;
- schema-level `privacyPolicy.forbiddenByDefault[]` may list stable forbidden
  raw-data markers;
- fact-level `privacy` may override the schema default with one of `public`,
  `minimized`, `sensitive`, or `forbidden`;
- column-level `privacy` may further classify individual scalar columns when
  useful;
- raw private data must not enter AIR facts;
- reports must list classifications without printing sensitive source values;
- snapshots should use generated handles or scalar IDs instead of private text;
- package-check should reject forbidden raw-data markers when detectable;
- host policy may explicitly allow additional report data, but the default is
  no leakage;
- conformance fixtures should use synthetic/minimized values.

Reports must not expose raw task text, URLs, tokens, secrets, private notes, raw
browser state, or host-owned object payloads unless an explicit host policy
allows that data to be reported. Even when host policy allows additional data,
AIR Core reports should prefer IDs, enum names, counts, classifications, and
fingerprints over raw values.

## Generated Handles

Generated handles may provide stable symbolic IDs for:

- fact schema IDs;
- fact collection IDs;
- field IDs;
- enum-like scalar values;
- tablegroup IDs;
- snapshot fixture IDs.

Rules:

- generated handles are deterministic derived artifacts;
- handles do not grant authority;
- stale or missing handles fail package-check according to policy;
- generator origin and fingerprint appear in reports where available;
- generated files are not source of truth.

## Package-Checked Data Contracts

Package-check should validate:

- fact schema file existence;
- schema version support;
- duplicate schema/fact/field IDs;
- duplicate fact/field names;
- unsupported field types;
- unbounded or excessive `maxRows`;
- tablegroup column length mismatches;
- generated handle freshness;
- snapshot row shape;
- snapshot scalar type correctness;
- declared privacy policy;
- no absolute paths;
- no timestamp-like fields;
- no dynamic objects or nested JSON payloads.

Failures use deterministic `air.facts.*` diagnostics. Package-check and report
output must preserve those codes instead of collapsing bounded facts failures
into generic package-check diagnostics. This keeps facts schema failures
compatible with LSP-lite JSON diagnostics, future Full LSP diagnostics, and AI
repair loops.

## Report Visibility

Package reports should expose:

- fact schemas by package-relative path;
- schema fingerprints;
- fact collection IDs, names, field counts, and max rows;
- tablegroups and column metadata;
- generated handle status;
- snapshot fixture fingerprints when present;
- capabilities/profile constraints;
- privacy classification;
- diagnostics and repair hints;
- whether the facts are source-level/tooling-only or runtime-required.

Facts diagnostics are stable and machine-readable. Examples include
`air.facts.non_scalar_column`, `air.facts.duplicate_column`,
`air.facts.dynamic_or_unbounded`, `air.facts.absolute_path`,
`air.facts.timestamp_field`, and `air.facts.privacy_invalid`.

Reports must avoid leaking sensitive task text, URLs, tokens, raw notes, or
private browser state by default.

## Conformance Compatibility

Conformance should be able to reference deterministic fact snapshots as fixture
inputs.

First-slice conformance requirements:

- fixture schema fingerprint is recorded;
- snapshot fingerprint is recorded;
- expected exported scalar results can be compared;
- report output is deterministic;
- no browser, network, IndexedDB, DOM, or host-object access is required;
- unsupported profile/schema paths fail clearly.

Future conformance may compare output streams only after an event/output Host
ABI is separately accepted.

## Build-Time / Runtime Boundary

Build-time tooling may parse rich JSON files, run generators, and prepare
fixtures.

Runtime AIR must not require:

- Node;
- npm install;
- Python;
- Codex;
- source AIR repo;
- build scripts;
- browser APIs;
- raw JSON parsing;
- external service access.

The host may convert rich application objects into bounded scalar facts before
calling AIR. That conversion must be documented, package-checked where possible,
and report-visible as a boundary, not hidden source-of-truth behavior.

## ABI Impact

v0.18 source-level schemas, static tables, tablegroups-as-metadata, generated
handles, package-check validation, reports, and conformance fixtures do not
require an AIR ABI bump.

AIR ABI remains `0.10` unless a later accepted implementation changes:

- executable runtime representation;
- calling convention;
- import/export layout;
- memory/data layout;
- package entrypoint runtime semantics;
- runtime-required package metadata.

Host ABI remains `0.10` unless new host imports or changed host import
semantics are accepted. Bounded fact schemas do not expose raw host authority or
require Host ABI changes by themselves.

## Test Matrix

| Area | Valid case | Failure / warning case |
| --- | --- | --- |
| Schema shape | schema with `schemaVersion`, bounded `facts[]`, scalar fields, and stable IDs passes | missing `schemaVersion`, duplicate fact IDs, duplicate field names, unsupported field types fail |
| Bounds | `maxRows` is fixed and within policy | unbounded or excessive `maxRows` fails |
| Snapshot shape | snapshot rows conform to schema and stay within `maxRows` | missing required field, extra field, wrong scalar type, or out-of-range scalar fails |
| Tablegroups | every column has the same fixed length and scalar type | mismatched table lengths fail |
| Generated handles | generated handle module fingerprint matches schema/generator | stale, missing, or untraced generated handles fail |
| Dynamic data rejection | scalar-only rows and tables pass | nested JSON objects, dynamic maps, arrays of objects, host handles, or runtime imports fail |
| Privacy | minimized scalar IDs appear in reports | raw text, raw URLs, tokens, notes, or secrets fail or are redacted according to policy |
| Reports | schema, tablegroup, snapshot, privacy, and handle metadata are listed | report omits schema/tablegroup ownership or leaks forbidden data |
| Conformance | fixture records schema and snapshot fingerprints and compares scalar outputs | unsupported profile/schema path fails clearly |
| ABI | source/tooling-only schemas leave AIR ABI and Host ABI at `0.10` | runtime representation or new host import requires explicit ABI decision |

## Acceptance Tests

Required future tests:

- valid bounded fact schema passes;
- duplicate fact IDs fail;
- duplicate field names fail;
- unsupported field type fails;
- unbounded `maxRows` fails;
- mismatched table lengths fail;
- generated handle freshness is checked;
- dynamic objects/nested JSON payloads fail;
- snapshot with missing required field fails;
- snapshot with extra field fails;
- snapshot with out-of-range scalar fails;
- package-check catches schema mismatch;
- report lists schema metadata;
- report lists tablegroup metadata;
- conformance fixture records schema/snapshot fingerprints;
- no absolute paths or timestamps appear in emitted metadata;
- AIR ABI remains `0.10`;
- Host ABI remains `0.10`.

## Open Questions

- Should the first slice validate JSON schema files only, or also generate AIR
  readonly tables from them?
- Should tablegroups be syntax, manifest metadata, or generated AIR modules in
  the first implementation slice?
- What maximum default `maxRows` should reviewPolicy recommend by profile?
- Which privacy classifications are required for reports?
- Should `bool` table columns lower as `i32` tables or get a separate report
  type only?
- Which diagnostic codes should be assigned under `air.package`, `air.manifest`,
  or a new `air.facts` domain?
