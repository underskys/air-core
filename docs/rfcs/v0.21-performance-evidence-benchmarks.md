# AIR v0.21 RFC: Performance Evidence and Benchmarks

Status: planning / benchmark evidence design

Purpose: define what "High-Speed AI" means in measurable engineering terms.
This RFC does not implement optimizer passes, change compiler semantics, change
AIR ABI, change Host ABI, or add benchmark-only language features.

## 1. Performance Dimensions

Performance claims must name the dimension being measured. AIR should not use a
single speed multiplier as a substitute for evidence.

Dimensions:

- AI generation speed / repair loop speed: time from generated AIR candidate to
  normalized diagnostics and actionable repair hints;
- verification speed: parser/verifier time for one module or package graph;
- package-check speed: package manifest, schema, Output Contract, command
  buffer, profile, generated artifact, and reviewPolicy validation time;
- Wasm binary size: emitted `.wasm` bytes for linked package output;
- WAT size: emitted `.wat` bytes for readable linked output;
- runtime throughput: deterministic exported function or batch decision calls
  per second under controlled host conditions;
- JS/Wasm crossing count: number of calls across the host/Wasm boundary for one
  decision or batch;
- host calls per frame / decision: number of host-visible calls needed to
  complete a frame, policy decision, or batch decision;
- batch decision throughput: rows or decisions processed per run;
- memory/static table byte size: bytes consumed by static scalar or compact
  tables, including equivalent `i32` comparison where applicable;
- conformance replay time: time to run deterministic scalar or batch fixtures
  and produce replay evidence.

## 2. What x10-x200 May Mean

`x10`-`x200` is a target for batch-heavy host-interaction scenarios. It is not
yet a measured release fact.

If AIR reaches that range, the likely sources are:

- fewer host crossings;
- command buffers;
- compact storage;
- batching;
- generated handles;
- eliminating repeated scalar calls.

The target must not be advertised as achieved until benchmark fixtures, stable
JSON output, and reviewed results exist.

## 3. Benchmark Fixtures

Proposed benchmark fixtures:

- scalar micro-call baseline: many small scalar calls that model the current
  ergonomic baseline;
- bounded rowset batch decision: one package receives minimized bounded facts
  through rowset-shaped host/test input;
- command buffer output intents: one package emits bounded scalar output intent
  records instead of repeated host calls;
- compact table lookup: compare `i32` static table lookup against compact
  `u8`/`u16`/`i16` static table lookup and storage size;
- FlowDesk-style batch policy: task/status/link/note summary pressure using
  minimized facts only;
- AirOps-style incident batch: incident/ops pressure using minimized incident
  observations and output intents;
- WebGPU/visual optional non-P0: visual host measurements can be useful later,
  but they are browser/GPU-dependent and not a Core P0 benchmark gate.

## 4. Metrics

Each benchmark should collect:

- verifier time;
- package-check time;
- linked build time;
- Wasm size;
- WAT size;
- static table bytes;
- runtime calls;
- host crossing count;
- output command count;
- replay checksum time.

Metrics must be reported separately. For example, a package may improve host
crossing count while increasing verification time, or reduce static table bytes
without changing runtime throughput.

## 5. Non-goals

- no fake speed claims;
- no benchmark-only language features;
- no optimizing demos at the expense of Core truth;
- no Host ABI bump;
- no AIR ABI bump;
- no tablegroups implementation;
- no optimizer pass implementation in this RFC.

## 6. Acceptance For Future Implementation

Future implementation should include:

- deterministic benchmark runner;
- stable JSON output;
- no wall-clock noise unless controlled and labeled;
- CI-friendly baseline;
- explicit fixture names and package hashes;
- machine-readable metric names and units;
- regression thresholds later, after baseline variance is understood.

First accepted implementation should fail closed on missing fixture metadata and
should not promote any benchmark result into public claims without checked-in
evidence.

## ABI Status

- AIR ABI remains `0.10`.
- Host ABI remains `0.10`.
- This benchmark plan adds no runtime authority, host imports, or language
  features.
