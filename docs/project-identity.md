Project name: AIR

Expansion: AI Intermediate Representation

Pronunciation: "air"

Historical name: AirLang. AirLang is a legacy/internal development name and may
appear in older documents, branches, scripts, and review artifacts.

File extension: `.air`

CLI: `airc`

AIR is the project name. `air-core` is the npm package. `airc` is the CLI.

Public npm package name: `air-core`. The package is the transport; the
project/product name is AIR and the CLI is `airc`. The package is named
`air-core` (not `airlang`) to avoid brand/search collision with the
unrelated active Rust project `airlang` ("Air", a minimalist language) on
crates.io. The legacy `airlang` name may still appear in older branches,
scripts, and review artifacts.

## Longer Description

AIR is an AI-first verified intermediate representation and package contract
for small portable AI-authored modules. It is designed for reviewable,
capability-scoped modules that can be generated by AI, checked by machines,
inspected by humans, and executed by explicit host runtimes.

AIR source files use the `.air` extension. The `airc` CLI formats, verifies,
explains, audits, lowers, and checks AIR modules and packages. Wasm is the
current primary executable/lowering target, while AIR preserves explicit
capabilities, effects, memory rules, Host ABI imports, manifests, and package
compatibility reports.

Hosts run AIR modules in browser, native, WebGPU, Metal, CLI, embedded, or other
environments. Hosts own real devices and platform services. AIR owns portable
verified module behavior.

## What AIR Is

AIR is:

- an AI-first verified intermediate representation;
- a portable package contract with Wasm as the current primary executable
  target;
- a strict capability/effect/memory/ABI verification layer;
- a reviewable format for generated tools, simulations, controllers, policies,
  and interactive modules;
- a boundary between AI-generated module logic and host-owned platform runtime.

## What AIR Is Not

AIR is not:

- a replacement for Rust, Swift, Zig, C++, Python, TypeScript, Unity, Unreal,
  WebGPU, Metal, or native runtimes;
- a browser framework;
- a game engine;
- a package registry;
- a general-purpose dynamic scripting language;
- an owner of DOM, GPU devices, filesystems, sockets, audio devices, windows, or
  platform objects.

## Layer Model

- AIR Core: portable IR semantics, verifier, lowering, audit, effects, memory,
  calls, control flow, and strict Host ABI validation.
- AIR Stdlib: pure deterministic helper modules that are backend-neutral,
  resource-free, and project-neutral.
- AIR Host ABI: capability-qualified imports that let AIR modules request host
  behavior through verified signatures.
- AIR packages: package-local modules, manifests, assets, generated handles,
  compatibility metadata, and reports.
- Hosts: browser, native, CLI, embedded, or engine runtimes that own real
  platform devices, services, policies, assets, and execution.
- Demos/project kits: project-specific examples, assets, art direction,
  gameplay, UI behavior, and request evidence.

## Positioning

AIR sits between AI-generated intent and host execution:

```text
AI / human intent
-> .air module
-> airc verify / audit / report
-> backend artifact, currently Wasm / AIR package
-> host runtime
-> visible or operational result
```

AIR keeps generated code reviewable by making authority explicit. AI can write
module logic, but AIR verifies the module, the host runs it, and a human decides
whether the package should be accepted.
